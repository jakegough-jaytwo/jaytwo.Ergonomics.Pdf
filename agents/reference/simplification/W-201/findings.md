## Recommendation

Keep assembly's existing fresh identity: `/Info` contains only `/Producer (jaytwo.Pdf)`, document XMP is absent, and the output has a new ID. Do not select an input's title, author, timestamps, custom metadata or profile identifiers, even for extraction from one source. Keep omission of viewer preferences, PageMode and PageLayout. Omission means PDF/viewer defaults; it cannot promise identical presentation or print settings in every application.

Align initial-view policy with the unadopted W-192 R192-5 and W-197 A5a proposals: omit a valid destination array or a single GoTo open action without Next, report W-192's per-occurrence InitialViewDropped count, and refuse malformed navigation and other actions. A URI or Launch action is active even without JavaScript; absence of a script is insufficient for admission. **Current assembly silently omits the URI fixture**; the proposed refusal is not shipped. W-192/W-197 own its implementation and counts. This item does not reopen link-action, attachment, tag or label policy.

Business use: an extracted invoice bundle or combined dossier should describe the newly assembled document, not inherit one input's author, document ID, fullscreen request or asserted archival profile. This supports predictable automation but deliberately loses useful business catalogue fields and print instructions. Exact wording, explicit exclusions, recovery and follow-up scope are in [proposal.md](proposal.md). No conformance follows from new identity or removal of profile markers.

## Caller loss, recovery and limits

Fresh identity costs catalogue searchability, source provenance/custom integration data, original timestamps, print scaling/duplex/tray/copy/range hints and chosen opening view. Combining inputs can have conflicting titles, authors and print instructions; arbitrary first-input selection hides that choice. No measured customer demand or corpus refusal/loss prevalence is supplied by these five synthetic fixtures.

For business title/author/custom data, the host retains input metadata before assembly, chooses values for the *new* document, then edits the assembled output. The measured cost is a reopen, two or three setters and one incremental save, plus host value selection/XML authoring. This adds an I/O pass; throughput and peak allocation were not measured. An application can stage both phases before publication, but this probe does not test workflow/path publication faults. There is no current high-level assembly option for copying arbitrary viewer preferences or setting an opening action; recovery for those settings needs an external capable editor or a separately approved feature. Do not prescribe raw PDF manipulation through engine internals.

Source PDF/A/UA/X identity or XMP document IDs must not be restored automatically. A caller needing a conforming deliverable needs a separate suitable validation/conversion workflow; neither library offers conversion or conformance validation. Source-associated attachments, output intents/color management, page/XObject metadata, signatures, encryption permissions, tags and labels were not qualified by these fixtures. Their existing contracts and separately scoped investigations remain binding. Removing the document packet is not a sanitization guarantee for metadata reachable elsewhere or text painted in pages.

Credential burden is unchanged: encrypted sources still need passwords, unencrypted-output consent and existing per-input permission checks. No new credential is introduced by fresh identity. The present probes use unencrypted inputs only; W-201 does not claim to rerun permission or signature qualification. Recovery cannot bypass an unknown password or turn a retained signature into a valid signature on a derivative.

## Complexity and disposition

Retain the existing assembly whitelist, new Info and ID creation, resource ownership/budgets, output version selection, new-file writer and failure guarantees. Do not add an identity selection option, XMP parser/profile detector, metadata merge algorithm or viewer copier. No runtime responsibility is deleted: that code is already absent. Estimated retained core for this choice is the approximately ten-line Info/ID construction block plus the existing fresh-catalog construction; no production LOC saving is measured. Documentation and focused regression assertions add responsibility. W-200 retains ordinary synchronization; W-192/W-197 own action preflight/counts. Their costs must not be attributed to W-201 again.

Proposed follow-up is a small owner-approved contract-clarification/regression item, approximately 1–2 engineer days (0.5–1 for wording/public docs, 0.5–1 for focused identity/viewer fixtures and independent checks). This is an estimate from one shared engine path and two public entry points, not measured implementation time. Expected runtime changes: zero unless focused tests expose a defect; such a defect requires a scoped follow-up and permanent regression. No new public API/package, protected-file edit or queue insertion is authorized here. The recommendation can be adopted independently of W-200, but integrated initial-view wording depends on owner disposition of W-192/W-197. The action-refusal slice is not complete merely because this identity research is done.
