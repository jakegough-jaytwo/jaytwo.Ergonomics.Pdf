# W-198 Gate 2 proposal — not adopted

## Exact proposed contract

> `bool PdfAcroFormEditor.AbandonXfa()` deliberately abandons the XFA representation of a hybrid form and retains its supported AcroForm representation. It removes only the AcroForm `/XFA` entry. It does not decode XFA, transfer datasets into field values, execute scripts, generate replacement pages, or guarantee equivalence of the two representations. Fields, widgets, current values, appearances and unrelated pending edits remain. A successful change returns true; when no XFA is present it returns false and adds no pending change. Incremental output retains the old bytes, including historical XFA packets; this operation is not data sanitization.
>
> Classification uses the existing R12 rules. Dynamic or XFA-only forms throw `PdfUnsupportedFormException`. For a hybrid, any certification, including unresolved certification treated as P1, throws `PdfCertificationLockedException`; any approval signature or document timestamp throws `PdfSignatureConflictException`. The existing structural signature definition applies and does not validate signatures. `/UR3` alone does not count as an approval signature. `AllowBreakingSignatures` does not override these refusals. After these checks, a user password must permit general document modification or `PdfEncryptionRestrictedException` is thrown; an owner password bypasses password permission bits, not certification or signature checks.
>
> Reader rights must be explicitly removed before abandoning XFA. A hybrid still carrying catalog `/Perms /UR3` throws `PdfUnsupportedFormException` with a diagnostic directing the caller to the explicit rights-removal operation. Abandoning XFA never removes rights as a side effect. W-199 defines and names that separate operation. Absence of XFA is a read-only no-op even on a signed, certified or restricted document; it does not serve as permission to perform any later operation.
>
> Validation order is: ordinary disposed/argument checks; bounded XFA classification; no-XFA no-op; dynamic/XFA-only refusal; certification refusal; signature refusal; modification permission; remaining usage-rights refusal; transactional dictionary edit. Malformed required structures throw the existing `PdfParseException`, and existing bounded traversal failures retain their existing typed failures. No raw PDF objects become public. No new catch-all error type or host exception details are introduced.
>
> Every failed preparation restores exactly the engine state from before that call, including XFA, rights, dirty objects and previously pending unrelated edits. If explicit rights removal succeeded in an earlier call, a later failed XFA preparation leaves that successful removal pending. This is per-operation rollback, not a transaction across both calls. A second abandonment on the resulting no-XFA state returns false. A save/output failure follows the existing editor destination-restoration guarantee and retains pending edits; successful in-memory rollback does not establish physical destination safety.
>
> A nonempty fill/bulk fill or flatten of a hybrid form throws `PdfUnsupportedFormException` directing the caller to explicit preparation; it neither removes XFA nor changes rights. Empty operations remain no-ops. Existing dynamic/XFA-only refusals remain. The hybrid check runs before planning/applying fields; no signed hybrid conversion is permitted. Assembly refuses any supported XFA representation with `PdfAssemblyNotSupportedException` before output and never converts it implicitly. Explicit preparation does not waive other assembly restrictions.
>
> Preparation edits are visible to reads, extraction and concatenation through the same open document without saving first. Existing assembly permission and explicit unencrypted-output-consent requirements still apply. Preparation does not write or publish a destination. Workflow Combine gains no implicit preparation or preparation option in this first slice. Callers using file-based Combine may explicitly save a prepared artifact and reopen it; callers using engine assembly may prepare and assemble with the same document.

This intentionally changes W4's implicit unsigned-hybrid fill conversion and its fill-permission semantics, the corresponding flatten behavior, and A5's hybrid acceptance/omission policy. D-48's signed-hybrid protection remains; its automatic rights-removal wording needs coordinated supersession with W-199. R12 classification stays unchanged. Exact protected-file patches must be presented for owner wording approval with implementation tickets; no protected wording is edited here.

Update shipped contracts only in the adopting implementation transaction.
