# W-208: async-source simplification options, measured for W-138

Research only. Baseline `0b042d785e070ae8791afe6d822daec24b8e6c6e` (W-210 completion commit; the ticketing baseline `82a8385` is the older reference). Nothing here is adopted, shipped or applied. Protected files, W-138, W-109, `docs/spec/` and `agents/state/current.md` queue order are not edited. Authoritative PDF references were not needed: no question here depends on an ISO 32000 rule, only on how the engine reads a source.

## 1. What is being decided

W-138 owns the API design for asynchronous inspection. This item supplies compatibility and performance evidence to it, and tests the opposite option (removal) with the same instruments. Three options are compared:

| Option | Meaning |
| --- | --- |
| **Retain** | `OpenAsync` and `IPdfSource.ReadAsync` stay as shipped (spec R13, W20, D-55). Inspection, synchronous opens and synchronous saves read through `IPdfSource.Read`. |
| **Complete** | W-138's candidates (async accessors, an explicit async load step, a source capability flag). Not designed here; the evidence below constrains them. |
| **Remove** | Delete the asynchronous source path and keep only synchronous reads; callers wrap in `Task.Run`. |

## 2. Method and bounds

Fixture: generated by `gen_fixture.py` (deterministic, seed 208): 51,960,955 bytes, 12,000 pages in a two-level tree, 400 widget fields, classic xref, raw content streams. qpdf 12.3.2 `--check` reports no syntax or stream errors. SHA-256 `88327ec9...d537d` (`execution.json`). This is one 52 MB file, not a gigabyte spike; a larger run needs separate approval.

Instrument: `probe/Program.cs` and `probe/Types.cs`, public API of `jaytwo.Pdf` and `jaytwo.Ergonomics.Pdf` only, net10.0 Release, Windows 11, 8 logical processors, .NET 10.0.13. `RangeSource` is an `IPdfSource` over the local file with a fixed per-read latency: a synchronous `Read` blocks the thread (`Thread.Sleep`); `ReadAsync` yields (`Task.Delay`). `SyncOnlyStream` is a seekable `Stream` that overrides only `Read`. "Local" below means latency 0. "Delayed" is 10 to 50 ms per read, as stated. These are simulations of range-request latency, not a real remote service, SMB share or HTTP server.

Every number below is **measured** unless marked **inferred**. The saved run is `observations.jsonl`; the concurrency rows were noisy (below).

## 3. Measured results

### 3.1 Opening is sparse and identical sync versus async

| | Sync `Open` | `OpenAsync` |
| --- | --- | --- |
| Source reads | 10 | 10 (0 synchronous) |
| Bytes read | 557,244 (1.07% of the file) | 557,244 |
| Allocated, local | 2,558,272 B | 2,561,984 B (+0.15%) |
| Allocated, 10 ms reads | 2,558,272 B | 2,563,664 B (+0.21%) |
| Median of 5, local | 11.3 ms | 13.0 ms (earlier run 11.6 / 12.3 ms) |
| Median of 5, 10 ms reads | 160.5 ms | 158.2 ms |

The async shape costs about 0.2% allocation and about 1 to 2 ms of fixed time on a local source; it is indistinguishable at 10 ms latency. Both are sequential chains of 10 dependent reads, so `OpenAsync` buys thread availability, not lower latency (**inferred** for any remote source; the dependency is visible in the read count, not separately instrumented).

### 3.2 Cancellation

At 50 ms per read, cancelling 120 ms into `OpenAsync`: the task completed with `OperationCanceledException` 0.8 ms after the request, started 0 reads afterward, and disposed the source once (`leaveOpen: false`). A synchronous open has no token. Inspection after open has no token either: `Pages` blocked the calling thread 1,764 ms (28 reads) at 50 ms per read, `AcroForm.Fields` 128 ms in the same document (2 reads, objects already resolved by `Pages`; compare 30 reads on a fresh document).

### 3.3 Which members still read synchronously after `OpenAsync` (W-138 evidence)

Fresh document per row, local source. Every row has `asyncReads = 0` after the open.

| Member | Sync reads | Bytes |
| --- | ---: | ---: |
| `PageCount`, `Pages` | 28 | 1,835,008 |
| `Signatures`, `Revisions` | 31 | 1,966,106 |
| `AcroForm.HasFields`, `IsHybridXfa`, `IsXfaOnly`, `Fields`, `GetFields`, `Export` | 30 | 1,966,080 |
| `AcroForm.NeedAppearances` | 2 | 131,072 |

| `Editor.Pages` | 28 | 1,835,008 |
| `Editor.Metadata.Title` set | 3 | 196,608 |
| `Editor.Pages[0].Rotation` set (after `Editor.Pages`) | 0 | 0 |

**15 of the 17 document-side members measured read the source synchronously; the two that do not are state captured at open.** The editor's mutating members read synchronously on first use. Members not individually measured but sharing a measured path (**inferred** from the code, not run): the eight `Metadata` text getters and indexer (`GetInfoText`), `Attachments` indexer, `TryGetValue` and enumeration (`ListAttachments`), `OpenXmp`, `OpenAttachment`, `AcroFormEditor` writes, `Flatten`, and the synchronous `Sign`, `SaveIncremental`, `ExtractPages` and `Concatenate`. The lexical member list is `inventory.json` (`public_members_by_file_not_verified_by_probe`), which was not checked member by member.

The reads are sequential and their bytes can exceed the 1 MiB retained-window ceiling (`Pages` read 1.8 MB, `Signatures` 1.97 MB) because windows are released and refilled (D-49). Whatever W-138 chooses cannot hold those reads as retained windows: an explicit load step must retain parsed results, which is a new retention rule beside D-49 item 4 (**inferred**).

### 3.4 Saves

| | Sync `SaveIncremental` | `SaveIncrementalAsync` |
| --- | --- | --- |
| Reads (prefix copy of 52 MB to an empty destination) | 51 sync | 50 async + 1 sync |
| Peak threads blocked in a read | 1 | 1 |
| Allocated | 1,071,008 B | 1,077,512 B |
| Time, local | 34.4 ms | 28.4 ms |
| Time, 10 ms reads | 788 ms | 820 ms |

The asynchronous save still makes one synchronous read (the appendix), as W-138's problem statement says.

The workflow layer on an asynchronous path (`PdfWorkflow.From(source).WithTitle(...).Fill("f0", "x").RotatePage(1, 90).SaveAsync(file)`): 92 reads, **32 synchronous (35%)** and 60 asynchronous, 54.5 MB read, 1.5 to 1.7 s at 10 ms per read. The 32 synchronous reads account for about 320 ms of blocked thread time (**inferred**: reads times latency).

### 3.5 Concurrency and blocking (64 concurrent operations, 20 ms per read)

| Scenario | Wall | Peak threads blocked in a read |
| --- | ---: | ---: |
| 64 × `OpenAsync` | 313 ms (3 runs: 313 to 332) | 0 |
| 64 × `Task.Run(Open)` (the removal proxy) | 1,516 ms (3 runs: 1,243 to 1,516) | 23 to 28 |
| 64 × `OpenAsync` then `Task.Run(Pages)` | 7,099 ms (3 runs: 5,205 to 7,248) | 25 to 28 |
| 64 × `OpenAsync` then `Pages` inline | 6,958 ms (3 runs: 6,049 to 6,958) | 28 to 33 |
| 64 × `OpenAsync(Stream)`, stream overrides only `Read` | 647 ms (2 runs: 615 to 933) | 31 to 51 |

Three runs were observed; only the last is retained in `observations.jsonl`, the first two are quoted from the session. Thread-pool injection makes the blocking rows noisy, so read them as ranges, not as benchmarks. The pattern is stable: asynchronous reads keep blocked threads at zero; every synchronous read path ties a pool thread for the whole read. Opening asynchronously and then inspecting synchronously moves the blocking later without removing it.

A seekable `Stream` that is not natively asynchronous (here, `Read` only) makes `OpenAsync(Stream)` look asynchronous while the base class runs each read on a pool thread: 51 threads blocked at 64 concurrent opens. `OpenAsync(Stream)` therefore helps only when the stream's own `ReadAsync` is truly asynchronous (**measured** for the Read-only case, **inferred** for the truly asynchronous case, not instrumented). A stream also shares one position, so the adapter's seek-then-read is not atomic; the engine's no-concurrent-reads rule (spec R13) is what makes that safe.

### 3.6 Unrelated observation: page extraction reads in proportion to the file

`Editor.ExtractPages` of two pages read 12,523 times, 820,584,408 bytes (15.8 times the file), and did the same for pages 6000 and 6001 (no annotations) and page 1 alone. Opening, `Pages` and a save read 1% to 100% of the file by contrast. The cause is **not investigated**; reads tracking page count (about 12,000) while W-162's closeout says traversal retains only selected pages suggests a whole-page-tree traversal that refills a window per page object (**inferred**, one fixture, one run). It is outside this item's scope and not counted in any option. It is recorded so the owner can route it, for example to W-211 or a page-extraction work item.

## 4. Responsibility inventory (lexical counts, `inventory.json`)

- Public asynchronous API of `jaytwo.Pdf`: `OpenAsync` ×4, `SaveIncrementalAsync` ×2, `SignAsync` ×2 on the editor; `IPdfSource.ReadAsync`; the signer, timestamp and provider interfaces (`SignHashAsync`, `GetTimeStampTokenAsync`, `CreateContentsAsync`) and three public provider classes. `jaytwo.Ergonomics.Pdf`: 12 public `…Async` members (save, append, sign, timestamp, export, combine).
- Async-shaped engine internals: `ValueTask` appears 63 times across 19 files and `useAsync` 83 times; the cursor, lexer, parser, cross-reference reader, loader and object store carry them (D-55). 21 `PdfSync.Result` sites run the same code synchronously.
- Tests: `SourceTests.cs` has 9 lines mentioning `OpenAsync`; `AsyncTests.cs` is 783 lines with 14 facts or theories covering save, sign, timestamp and cancellation (no `OpenAsync`).
- Spec: R13 and W20 are `Exists`; `ACCEPTANCE.md` lines 8 to 11 and 135 to 136 pin `OpenAsync` reads and cancellation.

Signer, timestamp and output async are independent of source inspection: they use no cursor and no source read, so any of the three options leaves them and the owner-accepted dependency set unchanged (**inferred** from file ownership in `inventory.json`).

## 5. Option comparison

| | Retain | Complete (W-138) | Remove |
| --- | --- | --- | --- |
| Business use served | Non-blocking open, cancel, async save on slow storage; blocking inspection | Non-blocking inspection on remote adapters (R5) | Sync-only callers; simplest mental model |
| Loss | Inspection and sync saves block (§3.3 to §3.5) | Larger public surface; new retention rule | Cancellation of opens; thread-pool starvation (§3.2, §3.5: 1.2 to 1.5 s versus 0.3 s for 64 concurrent opens); contradicts R13 and W20 |
| Recovery for the loss | Caller wraps inspection in `Task.Run`, which is measurably slower (§3.5) | Not applicable | Caller wraps `Open` in `Task.Run` and gives up cancellation |
| Responsibility deleted | None | None | Public: 4 `OpenAsync` overloads, `IPdfSource.ReadAsync`, the stream adapter's async path, 9 `SourceTests` lines and two spec rows. Internal async shape stays unless D-55 is reversed |
| Responsibility added | None | ≥ 30 async twins, or a load step plus a retention rule, or a capability flag | None |
| Effort (inferred) | 0 | Owned by W-138; evidence only here | Public-only removal about 1 to 2 days (delete overloads, tests, doc and spec text); reversing D-55 to a synchronous parser multi-day to multi-week, not recommended |
| Residual risk | Blocked threads on remote sources | Retention cap conflicts with D-49 item 4 | Reverses a closed owner decision (D-55), spec rows R13 and W20, and R5's remote-adapter premise |

Effort ranges are **inferred** from file and mention counts only; no implementation was attempted. The "savings" of removal are almost all public surface and tests, because the engine's single async-shaped implementation must stay for asynchronous save and sign (§3.4) unless D-55 is also reversed.

## 6. Constraints W-138 must keep (from the evidence)

1. Reads per inspection are sequential and can exceed 1 MiB read in total, so a load step cannot be a window prefetch (§3.3).
2. `OpenAsync` already holds cancellation, ownership and disposal semantics (§3.2). Any new step must keep them: a cancelled step publishes no partial state and disposes an owned source once.
3. A capability flag that refuses synchronous reads would turn every one of the 15 measured members and the synchronous save into a refusal on such a source. It is cheap to build but is a compatibility choice, not a performance fix (**inferred**; refusal was not instrumented).
4. The `Stream` adapter cannot be assumed asynchronous (§3.5): the engine can only be as asynchronous as the stream's own `ReadAsync`.
5. Wall time per sequential chain is unchanged by `async`; any latency gain must come from a prefetch or parallel-read design that does not exist today (**inferred**).

## 7. Recommendation

- **Retain** `OpenAsync` and `IPdfSource.ReadAsync`. Removal's measured costs (cancellation, concurrent opens about 4 to 5 times slower and thread-starving) and its contradiction of Exists spec rows R13 and W20 and closed decision D-55 outweigh savings that are mostly public surface.
- **W-138 stays the inspection API-design owner**, still `proposed`. Attach §3.3 and §6 as its evidence; the proposal text is in `proposal.md`. No status, queue or dependency change is made here.
- **W-109 stays `proposed` and after W-138**, as its own notes already say. This item did not measure decode counts, so it supplies no new W-109 evidence; it adds only that an async load step and an object-stream cache would both sit above the source and need one retention rule (**inferred**).
- Route §3.6 (extraction read amplification) to the owner separately.

## 8. Not measured or not claimed

- A real remote service, SMB or NFS share, HTTP range server, gigabyte file, or thousands of pages beyond 12,000. Latency is simulated with sleeps and delays.
- Peak memory (only allocated bytes), net48, netstandard2.0, Linux, other frameworks, encrypted files, attachment content streams, signing, or signature-bearing fixtures.
- Per-member costs beyond one fresh-document read each; timings are medians of 5 on one machine, with noisy concurrency rows.
- The truly asynchronous `Stream` case, a capability-flag refusal, and any W-138 candidate implementation.
- Independent review; W-188's missing review attachments remain a gap.
