## Business capability and migration

| Integration | Retain option | If providers are removed |
| --- | --- | --- |
| Host RSA/PKCS#11/cloud raw-sign operation | Use current built-in provider, or workflow raw signer convenience. | Move engine callers to new raw-signer entry points. Preserve RSA PKCS#1 v1.5, ECDSA P-256/P-384 P1363, SHA-256/384/512, certificate-chain delivery and cancellation. Host still owns keys, mechanism selection and credentials; do not double hash. |
| Service receives PDF ranges or their digest and returns complete CMS | Current live async provider callback can perform request/wait/return with the exact context. | No general adapter. The service must offer an operation signing the library's signed-attribute digest with the required scheme, plus export the correct public certificate/chain. Change endpoint/protocol, permissions and possibly provider/vendor; private-key export is not a requirement or assumed recovery. If the service lacks that operation, this library path is unavailable. |
| Caller controls CMS signed/unsigned attributes, corporate policies or extra signers | Provider supplies complete compliant CMS; caller owns correctness and any external verification. | No public custom-attribute injection exists in the raw signer contract. Rebuilding a CMS around its result changes the bytes being signed and is not a drop-in fix. Drop the requirement, obtain separately approved functionality, or use another signing path. A synthetic custom attribute is measured; actual policy-service requirements are unmeasured. |
| Async two-phase remote transaction inside one execution | Provider can submit, await and return CMS while the document/editor and context remain alive. | Raw-sign services can do this only around the library-selected digest. Complete-CMS service transaction is lost as above. Current context is not a serializable durable prepare/complete API; retaining it does not promise resume after disposal/process restart. A durable offline signing protocol is not supplied by either path. |
| RFC 3161 signature timestamp or separate document timestamp | Existing built-ins plus ITimestampAuthority. | Authority contract, HTTP/request checks and both placements remain. No credential recovery improvement; host still configures TSA/network policy. |
| Further PDF approval signature on an already signed PDF | Another editor/workflow execution, subject to permissions and certification. | Retain this countersigning workflow, prefix preservation and locks. Do not confuse it with CMS counterSignature attributes; no new CMS countersignature builder is promised. |

Minimal working examples are `probe/Program.cs` (`CompleteCms` vs `RawSigner` and both callers). The external complete-CMS service is modeled locally, not contacted. Existing workflow migration is `workflow.SignAsync(destination, signer, options, authority, token)` instead of passing `new CmsDetachedSignatureProvider(signer, authority)`; file output also passes save options. Engine proposed signatures are specified in `proposal.md` and are not compilable current APIs.

## Complexity accounting and recommendation

Measured current surface: 4 engine provider entry points, 4 workflow provider entry points, 4 workflow raw-signer entry points, 4 workflow Timestamp entry points. There are 2 public extension types (interface + context) and 2 public concrete providers. The interface is 29 source lines, context 57, CMS builder 453, timestamp builder 79 (physical lines including comments/blanks; not a complexity metric).

Candidate N in the proposal makes those 4 provider/context types internal and removes 8 public provider-taking entry points. It adds 4 engine raw-signer and 4 engine Timestamp entry points to retain sync/async and source/destination variants: net **zero public terminal methods removed**, 4 public types hidden. Public context has 5 properties and 1 stream-opening method; provider has 1 property and 1 callback. Built-in public constructors/callbacks cease to be extension APIs. Keeping the existing internal protocol means the 86 interface/context lines remain; all 532 builder lines and supporting DER, certificates, token parsing, HTTP, range streams, appendix and writer logic remain. No measured runtime LOC, allocations, performance or security reduction is claimed. Avoid adding these overlapping numbers together.

Responsibility actually deleted: public complete-Contents extensibility, custom-provider compliance guidance and testing of its public overloads. Responsibility retained/added: raw signer/TSA hosting, CMS construction/checks, public replacement APIs, test seams and migration docs. The engine kind-mismatch check can become unreachable by public choice but may remain useful internally; it is not a broad branch-deletion justification. Arbitrary-output compliance obligations disappear only for the removed boundary; externally returned raw signatures and TSA tokens still require the documented trust boundaries.

Recommendation is retain pending a deliberate product choice; optionally improve engine convenience in a separately approved additive item. The 3 passing probes demonstrate a real capability loss and no CMS-runtime deletion. They do not measure consumer frequency, ecosystem refusal percentages or a business value threshold. Candidate N becomes reasonable only if Jake accepts those losses and the estimated migration cost. Do not approve seed-policy narrowing or forensics removal by association.

Planning estimate (inferred, not timed): 1–2 engineer-days for additive engine APIs/docs/focused tests; 2–4 for repository caller migration, hiding types, public-only workflow test replacements and focused compatibility checks; 1–2 for a named signing integration checkpoint if the owner requires refreshed matrix/interop. Basis: 8 engine replacement methods, 45 referenced files, 17 test doubles, no DER rewrite. Unknown external integrations and independent review are outside these estimates and can dominate effort. No package release, push, implementation or queue insertion is authorized here.
