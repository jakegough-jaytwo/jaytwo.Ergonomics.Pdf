# W-204: retain workflow staging and last-value-wins

Research completed 2026-10-26 at `b1e946c5aaee4dbba85495079da37b3a6ecaa438`, after W-201's completion commit. Single executing agent; no independent human or fresh-context review claimed. This is an evidence-backed recommendation, not Gate 2 adoption or product implementation.

## Recommendation and authority

Retain F5 unchanged: one atomic bulk fill containing each field's last declared value; one combined flatten after it; other operations replayed in declaration order. Keep the engine bulk API's duplicate-name rejection. The workflow and engine expose different abstractions deliberately. Do not classify duplicate rejection or global declaration order as behavior-preserving cleanup.

`observations.json` contains 22 workflow and 12 direct-engine scenarios. `inspection.json` holds pypdf's values, page rotation, title, attachment names, extracted flattened text, NeedAppearances, output hashes and diagnostics. `summary.json` records 192 successful assertions. Across the 22 workflows, 16 succeed and six refuse at execution as expected. Each successful workflow preserves the input prefix and appends one revision. The failed same-stream append leaves the input unchanged. ## Applicable precedent and its limits

- [pypdf 6.21.1 PdfWriter API](https://pypdf.readthedocs.io/en/6.21.1/modules/PdfWriter.html#pypdf.PdfWriter.update_page_form_field_values) accepts a mapping of field names to values, and its flatten option paints appearances without removing widgets. `precedent.json` measures two legal successive updates (different and identical values), ending at Ada. This supports assignment/override composition; a mapping cannot itself represent duplicate keys. It is an imperative API and supplies no precedent for a deferred builder's atomicity or staging.
- [PDFBox 3.0.5 PDTextField source](https://github.com/apache/pdfbox/blob/3.0.5/pdfbox/src/main/java/org/apache/pdfbox/pdmodel/interactive/form/PDTextField.java#L219) writes a field value and applies the change. This is source-only analogous setter precedent; no PDFBox execution, bulk transaction or builder-order equivalence is claimed.
- pypdf's fill-and-flatten comparison followed by widget removal paints Ada, but qpdf returns 3 with dangling AcroForm-field warnings. That comparison is **not** a clean structural pass or equivalent flatten cleanup. The other two pypdf comparison outputs and all 29 input/current-library/direct-engine outputs pass qpdf with exit 0: 31 clean checks, one warning result. pypdf also emits an xref-subsection diagnostic on 24 current-library incremental outputs; the exact per-file messages are retained in `inspection.json`. qpdf accepts those outputs. No tool warning is promoted to a repository defect without a violated contract or standard finding.

The pypdf observations and PDFBox source do not establish encryption, certification, field-lock, rollback, signature or appearance equivalence. No licensed Aspose execution, general library ranking or representative production corpus measurement was undertaken.

## Alternatives, impact and recovery

| Alternative | Benefit | Loss / migration / responsibility |
| --- | --- | --- |
| Retain current policy (recommended) | Helpers can compose defaults, overrides and flatten intentions; one engine transaction validates effective form values. Existing errors and output order remain predictable. | Intermediate mistaken assignments can be hidden by later correction. Caller validates data provenance and conflicting business inputs before building the workflow when that distinction matters. No new credentials or migration. |
| Reject every repeated name at description | Detect accidental duplicate keys before opening input; avoids defining value equality. | Also rejects idempotent repeats and defaults/overrides. Caller must merge with ordinal keys and validate before building, or use direct sequential calls and own their different atomicity. The workflow still needs a name set, bulk-fill collection, flatten stage and operation list. No demonstrated complexity deletion. |
| Reject only contradictory repeats | Preserves identical retries, flags different assignments. | Must define equality across text, Boolean, names, None and ordered value lists, and specify error/recovery behavior. The current public value representation does not make business equivalence a universal policy. No implementation or equality design is approved. |
| Replay all operations strictly in declaration order | Fluent spelling matches execution order. | Breaks flatten-before-fill helpers, changes NoRotate outcomes, sticky appearances, partial pending edits and diagnostic precedence. Keeping atomic bulk fill would require barriers or extra planning; dropping it would weaken a guarantee. Callers must reorder operations; direct engine remains available for explicit control. |

Read-only counterfactual classification of the 22 workflow descriptions: nine repeat a fill name; seven of those currently succeed. Reject-all would newly refuse **7/16 currently successful synthetic workflows** (also 7/22 of all synthetic workflows), and move two already refused workflows' errors earlier. Of the nine, one repeats only an identical text value; the other eight contain plainly distinct values. Reject-only-different would newly refuse 6/16 successful workflows, subject to an as-yet unapproved equality definition. These are deliberately selected examples, not population incidence or a corpus pass rate. The two refusal counts overlap; they are alternatives and must not be summed. Under retention, newly refused workflows are 0/22.

Recovery if a rejection policy were later adopted: accumulate values in an ordinal dictionary, explicitly resolve overrides, then call `FillForm` once. Preserve one atomic call; retry with a new builder after terminal failure. Catching a proposed description-time duplicate error would itself need a defined builder-state guarantee. No additional password/signer credentials are caused by merging, but original authentication, permissions, locks, consent and signer requirements remain. Do not infer permission to bypass them. Manual merging adds host validation/code and does not eliminate the library's batching or lifecycle responsibilities.

Complexity estimate (inference, not a benchmark): retention needs no runtime implementation; owner adoption/clarification would be approximately 0.25–0.5 engineering day. A reject-all change with migration documentation and focused tests is approximately 1–2 days; reject-only-conflicts approximately 2–4 days because equality and partial-description failure state need decisions. Global declaration order is a larger redesign, approximately 3–5 days at minimum, and incompatible with F5 without an owner-approved contract change. These ranges assume existing infrastructure and exclude broader compatibility sampling or qualification. No LOC, throughput, allocation or maintenance savings were measured. W-185/W-186 already own lifecycle/checkpoint consolidation; their savings are not counted here. Signing provider questions remain W-202/W-203; ownership/publication research remains W-205/W-206. No duplicated implementation or general policy framework is proposed.
