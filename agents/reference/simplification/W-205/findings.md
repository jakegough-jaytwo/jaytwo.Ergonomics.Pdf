# W-205: retain separate state recovery and publication

Research completed 2026-10-26 against `d17c35f0a55abb8d33aebea922dae3819cf7eff9`, after W-204's committed closeout. One executing agent; no fresh-context or independent human review claimed. This packet is research and draft wording, not Gate 2 approval or implementation.

## Recommendation

Retain W-186's concrete object-store checkpoint, W-185's shared file-publication lifecycle, and the documented pending-edit lifetime. Do not introduce a transaction framework, discard pending changes on editor disposal, or route file outputs directly to their final pathname. No unresolved pending-lifetime contract problem was found: `PdfDocumentEditor` remarks, ACCEPTANCE Opening, `EditorTests`, and the new failure/continuation probes explicitly agree that disposing an editor neither saves nor discards changes.

Recommend one narrow workflow correction for owner approval: a restoration exception of an unexpected type during final signed-stream copying should not mask the original output exception. Retain signing-specific diagnostics. Broader diagnostic unification is an optional contract/API expansion with no demonstrated simplification benefit here; do not adopt it as cleanup. Exact wording and a scoped implementation draft are in `proposal.md`.

Authority inspected: AGENTS.md signing-failure paragraph and engine/workflow boundary; phase-1 section 2, section 6 and F2-F4/F12/F17-F21; ACCEPTANCE Opening, Sealing and Workflows; behavior Engine guarantees and signing-restoration text; D-66; W-151/W-185/W-186; simplification charter PLAN 15/O 09. ## Measured evidence

Reproduce with `powershell -NoProfile -ExecutionPolicy Bypass -File agents/reference/simplification/W-205/run.ps1`. The runner builds a disposable net10.0 public-API probe in ignored `out/W-205`, restoring only from the local package cache with online vulnerability lookup disabled for that offline restore. Product build warnings remain errors. Input is a deterministic 329-byte synthetic one-page classic-xref PDF generated by `MakePdf`; SHA-256 is in `observations.json`. No customer-corpus incidence is inferred. Probe-only MemoryStreams and whole-file arrays are bounded experiment material, not product code.

`observations.json` records 25 cases, 146 successful assertions. Fourteen engine output cases cover distinct copy, append, finalization and restoration seams across save, CMS-kind signing and document-timestamp-kind signing. They begin with a pending title. Every case retains the original output exception and pending title. Signing/timestamp failures report both kinds of failed restoration; ordinary saves intentionally report none. After explicitly repairing physical target length/position, the probe disposes the failed editor, opens another, saves the pending title, verifies the input prefix and verifies no signature leaked. Two more engine provider-failure cases show no output and the same pending-state continuation.

The injected finalization Length failures are checked by their captured stacks: all four reach `FinishWrite`, including same-stream `AcceptAppend` and cross-stream source rebinding. The probe preallocates its tiny fault-stream backing store so MemoryStream capacity growth cannot accidentally trigger Length failure during serialization. Earlier exploratory injections exposed that probe pitfall; only the corrected run is the retained result.

Five workflow-stream cases demonstrate: successful recovery; failed truncation leaves 17 bytes; failed position restoration leaves length zero; a destination Flush error is recovered; and unexpected restoration failure masks the original copy error. All builders are consumed, providers are called once, inputs are unchanged, and borrowed streams remain open. There is no structured rollback diagnostic on these final-copy failures, even though the preceding signing stage completed privately. The probe uses opaque four-byte provider contents for fault-path control: it does **not** establish a valid CMS signature, RFC 3161 token, or cryptographic verification. The supported built-in authority adapter is separately exercised with a throwing authority: one invocation, generic PdfTimestampException, no inner exception or secret text, and no output.

Three async file-terminal cases cover provider failure with a prior destination, post-provider cancellation, and a publication collision created during provider execution. The existing destination bytes survive the provider failure; the collision directory survives failed publication; cancellation publishes no output. Temporary siblings are absent afterward in all three. This does not inject file Flush(true), deletion failure, power loss or every filesystem race.

Existing tests run on Windows net10.0: 54 engine tests passed (checkpoint, editor lifetime, signing partial-write/finalization/owned-source disposal, hostile Exception.Data, cancellation and authority redaction); 32 workflow tests passed, zero failed, three platform cases skipped. The workflow selection includes file saves, signer/authority failures, cancellation, overflow, stream-copy recovery, one-run ownership and certification refusal. Exact commands and skip names are in `verification.txt`. These runs use real existing signer/authority scaffolding where selected; no new independent cryptographic or rendering validation is claimed.

## Observed diagnostic-masking problem

Trigger: a caller-supplied writable seekable destination writes 17 bytes during final workflow signed-stream copying then throws an IOException. Its SetLength(0) throws an InvalidOperationException. Current result: `WorkflowFiles.CopyAsync`'s restoration filter does not catch that type; the InvalidOperationException replaces the original IOException, and 17 output bytes remain. Name in the probe: `workflow-copy-unexpected-restoration`.

Expected recommendation: preserve the original operation failure regardless of restoration exception type, keeping recovery best effort. This follows W-205's explicit original-failure requirement and the engine's existing preservation design. F20 currently promises best-effort recovery and unchanged engine exception categories, but does not explicitly promise identity for arbitrary final-copy output exceptions. Treat explicit workflow identity wording as a contract clarification/strengthening requiring Gate 2, not as an already shipped universal diagnostic guarantee.

Impact: callers lose the first failure needed to diagnose the write; unsuccessful restoration still leaves partial bytes. Severity: Medium reliability/diagnostic issue in a custom-stream edge case, not evidence of a cryptographic or disclosure defect. Disposition: proposed narrow correction with a permanent regression in the implementation draft. W-205 excludes runtime/test-suite edits; its disposable reproduction is not represented as the permanent regression or a shipped fix. Stop short of expanding signing diagnostics to all destinations without a separate API case. Host signer/authority redaction remains unchanged; ordinary output exceptions are not host-signing exceptions.

## Business use, costs and alternatives

| Choice | Useful behavior / responsibility | Loss, recovery, cost |
| --- | --- | --- |
| Retain checkpoints, lifetime, staging (recommended) | A caller can recover an earlier fill/title after failed signing, dispose the editor and save through another. A business output pathname receives completed processing/signing. | No new refusal or credential burden. Retains per-operation helper restoration, disk staging, ownership and filesystem limitations. No runtime deletion attributed to W-205. |
| Narrow final-copy exception correction (recommended for approval) | Original I/O/cancellation failure remains the primary failure even when the custom stream fails unexpectedly during recovery. | Removes one exception-type policy filter; adds permanent regression and explicit documentation. Does not remove the copy loop, recovery code, staging or diagnostics ownership. Some callers catching the masking restoration type would see the original type instead; document the correction. No PDF capability lost. |
| Unify diagnostics across save/sign/workflow | Could make failed truncation versus seeking observable for more output families. | Adds public reporting/API decisions (current type lives in engine Signatures and its Restore method is internal). Workflow cannot call engine internals or own engine invariants. Do not expose raw internals or add a runtime dependency to share it. No caller demand or deletion benefit demonstrated; defer. |
| One transaction framework or direct-to-final-path writes | Superficial common lifecycle vocabulary or less staging. | Framework adds state/ownership branches; direct writes lose F17/F20 protection. Neither is recommended or authorized. |
| Discard pending edits on editor disposal | Makes editor disposal an implicit abort. | Breaks explicit supported lifetime and measured recovery; cannot be described as cleanup. No concrete current contract problem, so no ticket proposed. |

Recovery remains explicit: direct-engine caller inspects signing diagnostics, verifies/repairs a damaged same-stream target before retry, and can use a fresh destination. The successful probe continuation deliberately repairs targets first. Workflow caller uses a fresh builder and separate empty destination, cleans up or repairs partial caller-owned output, and makes an explicit new signer/authority call when needed. No automatic retries are added. Original passwords, signing credentials, permissions, certification/locks and source-snapshot obligations remain; a replacement credential, new PDF capability or extra consent is not required by retention or the narrow correction.

Estimated effort (inference based on the single CopyAsync filter and existing fault-test infrastructure): retain current architecture/lifetime, no implementation; narrow correction plus permanent sync/async regression, docs and focused checks, approximately 0.5-1 engineering day. A general diagnostic/API expansion is at least 2-4 days before broader compatibility checks, but lacks a demonstrated requirement; this is a planning range, not a measured benchmark. No LOC, performance, allocation or maintenance savings were measured. W-185/W-186 already own consolidation savings; count none again. W-206 owns alias policy research. W-200's metadata atomicity proposal and W-202/W-203 provider/seed choices remain separate.
