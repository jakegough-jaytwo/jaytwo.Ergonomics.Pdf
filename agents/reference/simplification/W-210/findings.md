# W-210: signature-forensics scope assessment

Research at `f78114b9c4e12aff9c475ec2cb8f97f29b8e82ab`, 2026-10-26. Recommendation: **retain the structural listing and the revision list as shipped; treat "remove public forensic properties" and "remove the rich CMS reader" as two separate, optional, owner-priced cuts; do not take either as a simplification default.** If Jake wants one cut, the rich CMS reader (cut B) is the only one that deletes a hostile-input parser; the revision/coverage properties (cut A) delete little code and the most-asked question ("did something change after this signature?") with it. ## Candidates

All counts are physical lines or lexical hits, inferred unless marked measured; savings overlap and must not be summed.

### Retain (R)

Keep R9, R10 and the reader. Add W-158 documentation. Cost: none beyond W-158. Residual: the reader stays a hostile-input parser reached from `Signatures`, and `Signatures` stays all-or-nothing on one malformed CMS (strictness W-158 is asked to keep documenting).

### Cut A: remove public revision/coverage properties, keep the reader

- **A1, revision attribution only.** Remove `ByteRangeRevisionNumber`, `PdfRevision.EndsAtSignatureByteRange`, and (A1+) `Revisions`/`PdfRevision` altogether.
- **A2, plus coverage hints.** Also remove `ByteRangeStatus`, `ByteRangeEnd`, `HasLaterRevisions`, keeping the raw `ByteRange`.
- Lost caller use cases: "which revision does this signature close?" and "was the file changed after signing?" (the latter is only possible by comparing `ByteRangeEnd` with the file length, which a caller can do with the retained `ByteRange` and its own length; the xref-based `HasLaterRevisions` nuance, bytes after the end that add no xref section are not a revision, would be lost). Under A2, "is this ByteRange self-consistent?" moves to the caller; that is the check W-150 added to stop the old API implying more than it knew.
- Retained safety consumers: all of them (none use the inspector).
- Responsibility actually removed: the footer reader (about 123 + 63 lines), `PdfRevision`, `RevisionSection` and its recording (A1+/A2); under A2 also `ByteRangeStatusOf`/`ContentsSpan` (about 135 + 49). The reader, `PdfSignatureInfo` and its CMS properties stay. Approximate deletable runtime lines: A1+ about 230, A2 about 415, before replacing any test code.
- Compatibility/recovery: pre-1.0 so no package break; documented contract change (spec R9/R10 text, `ACCEPTANCE.md` rows, `behavior.md`, README example). Recovery for callers: compare `ByteRangeEnd` with file length, or use pyHanko/qpdf; no credential burden.
- Tests: `RevisionTests` (293), parts of `SignatureInspectionTests`, `LargeWorkloadTests`, `XrefStreamAppendTests`, `OutputCheck` (comparison project) change; `ByteRangeStatus` has 22 test lines in 2 files, all inspection-specific (`test_oracle.json`: oracle reads 0).
- Effort (inferred): A1+ 1–2 engineer-days; A2 2–3. Basis: about 8 files with oracle reads, docs in 5 places, no format code.
- Residual risk: the very question W-158 must teach readers to ask ("what is after this signature?") loses its built-in answer. A caller who reads it wrong gets a worse outcome than a caller using `HasLaterRevisions`.

### Cut B: remove the rich CMS reader, keep the structural listing and revisions

- Remove the 7 CMS-derived members; keep `FieldName`, `HasSignatureValueDictionary`, `SubFilter`, `/M`, text fields, `ByteRange*`, `HasLaterRevisions`, `CertificationLevel`, `Revisions`.
- Lost caller use cases: show who signed and with what algorithm; list embedded certificates; show a time-stamp token's time; display a PAdES-T indicator. These are the use cases people pair with an external validator.
- Retained safety consumers: all; the reader is not used by any.
- Responsibility actually removed: a parser for hostile `/Contents` BER (680 lines), its 65,536-choice limit and allocation obligations (W-18 row), the BER indefinite-length tolerated quirk and its GPO fixture handling, the CMS fuzz target/seeds (about 250 lines plus 6 seed files), and `Signatures`' all-or-nothing failure on one bad CMS (P2). Responsibility retained: strict `Rfc3161TimeStampToken` validation for signing (672 lines), `DerCodec`, and the signing builders. Restoring the reader later would be new work; no cheaper rebuild from `DerCodec` is claimed.
- Compatibility/recovery: documented in P5. The caller needs `ByteRange` (retained), its own source bytes, and a CMS library; an `ETSI.RFC3161` document timestamp is recoverable the same way. Not recoverable for dictionaries the library reports as `GapNotContents`.
- Tests: CMS tests in `SignatureInspectionTests` (about lines 140–250), `CmsFuzzTests`, `SignatureInspectionInteropTests` assertions comparing pyHanko/asn1crypto fields, and 1–3 oracle files per member (`WriterQuirkTests`, `LargeWorkloadTests`, `WorkflowSigningInteropTests`, `SignatureSeedValueTests`, `DssCases`). The pyHanko/`pdfsig` agreement claim in `ACCEPTANCE.md` line 125 shrinks to the retained members.
- Effort (inferred): 2–4 engineer-days. Basis: 18 files reference `PdfSignatureInfo`, 7 members, one parser file, fuzz target and seeds, ACCEPTANCE/behavior edits including the quirk removal, plus the owner spec edit. Unknown external consumers could dominate.
- Residual risk: signer-identity display is the most requested "inspection" feature in generic PDF libraries (inferred from the shape of the API surface, not measured demand); removing it makes `Signatures` much less useful to a review UI, and the strictness benefit disappears only if nothing else parses `/Contents`.

### Cut C: basic listing only (A2 + B)

Keeps `FieldName`, `HasSignatureValueDictionary`, `SubFilter`, `/M`, text fields, `ByteRange`, `CertificationLevel`. `PdfSignatureInfo` shrinks from 21 to about 10 members. It is the cheapest surface to document, but it deletes both the self-consistency check and the revision answer. **Not recommended**: its runtime savings are the sum of two disjoint regions, with overlapping model and test edits; the combined removal still leaves signing, timestamp validation and xref reading untouched. Do not credit it with their sum.

### Not a candidate: per-signature failure isolation

Making `Signatures` return an entry with a "CMS unreadable" marker instead of throwing would change a documented guarantee (`ACCEPTANCE.md` 124) and add API. Out of scope; W-158 is to keep documenting strict behavior.

## Recommendation

1. Retain R9 and R10 as shipped unless Jake accepts a concrete lost use case. The evidence does not show a safety consumer, a measured defect, or measured demand for removal; the only measured benefit is code and fuzz-surface size.
2. If Jake wants to simplify, price **cut B** first (it is the only candidate that deletes parser risk and one failure mode) and decide independently on **A1+** (revision list) — they do not depend on each other. Do not take A2 without a replacement for the self-consistency check; do not take C.
3. Whatever is decided, **W-158 is retained and proceeds** (proposal.md, section 3). Its five definitions and fail-closed statements do not name any removable property.
4. Follow-up implementation, if any, gets two separate owner-approved items (cut A, cut B), each with its own allowed paths, spec edits, `ACCEPTANCE.md`/`behavior.md` rows and a named signing/inspection verification checkpoint.
