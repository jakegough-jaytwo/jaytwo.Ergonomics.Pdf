# W-203: retain W-151 seed enforcement

Research completed 2026-10-26 against `7efb97a8e3597f6669a3549598e50d6b04cca401`, after W-202 was done and committed. Recommendation: retain the shipped W-151 policy. Blanket refusal reduces the checker, but removes useful signing without deleting the surrounding signing responsibilities. This packet is research and an unadopted alternative, not an implementation or owner approval.

## Comparison and reproducibility

`python agents/reference/simplification/W-203/measure.py` generates the exact alternative `candidate-checker.cs.txt` and revision/hash-bound `inventory.json`. `powershell -NoProfile -ExecutionPolicy Bypass -File agents/reference/simplification/W-203/run.ps1` builds the unchanged net10 engine and the disposable public-API probe, then builds the engine sources in a temporary project with only the checker replaced and runs the same probe in a separate process. It never changes product sources or their outputs to load the candidate. Inputs are tiny, generated one-page PDFs with an indirect SV dictionary and one invisible existing signature widget. All credentials are disposable local test keys; no service or token is contacted. `execution.json` binds assemblies and probe hashes. The temporary build uses compiler warnings as errors; it does not reproduce StyleCop, assembly metadata/friend declarations, other frameworks or release settings.

Precise candidate **R203**: refuse any present, non-null top-level mandatory entry among Filter/SubFilter/V/LegalAttestation/AddRevInfo/DigestMethod and, for effective PDF 2.0, LockDocument/AppearanceFilter. Refuse mandatory Reasons even when absent, because absence requires omission. Retain the existing nested certificate checker, including Browser enrollment exceptions and advisory signature-policy treatment. Refuse every non-null MDP/P, including approval-only P=0, and every nonzero nested TimeStamp/Ff, including a standalone timestamp without a URL. Preserve flag parsing, null resolution, effective-version semantics and existing treatment of unknown flags/private entries. An absent flag-controlled optional key otherwise creates no new constraint. This is deliberately different from `Ff != 0`, refusing every SV dictionary, dropping seeds, or forbidding all existing signing fields.

The probe's descriptor-only admission model is separately compared with the actual candidate assembly. All 28 fixtures agree. The candidate assembly executes the real field-owner lookup, parser, object resolution and signing path; it does not use a replacement PDF parser. Both engines are also called without the model gate.

`observations.json` records the current engine plus descriptor gate; `candidate-observations.json` records the compiled candidate. Accepted CMS uses the built-in CmsDetachedSignatureProvider over a local RSA-2048 raw signer. .NET System.Security.Cryptography.Pkcs 10.0.0.0 `SignedCms.CheckSignature(true)` checks CMS signature mathematics over captured signed PDF bytes. It does not check PDF seed conformance, PAdES classification, revision coverage, trust, revocation, field-lock validity or rendering. In particular, `pades-format` proves CMS signature integrity for that format request, not independently classified PAdES conformance. Opaque timestamp contents are deliberately only preflight evidence. Each accepted operation preserves the original PDF prefix and calls the provider once. Each refused operation leaves source bytes and the empty destination unchanged and calls no provider. Pending-edit and same-stream retry behavior is covered by the rerun W-151 tests, not newly demonstrated by this probe.

The lost CMS fixture IDs are `filter`, `ordered-format`, `pades-format`, `parser-capability`, `reason`, `reason-omitted`, `reason-unicode`, `no-revocation`, `digest`, `no-document-lock`, `auto-document-lock`, and `approval-only`. Concrete business losses are issuer-designated signing technology/encoding, bilingual or exact contractual approval reasons, a required digest, an express no-revocation request, an expressly unlocked document, and approval-only signing. These are valid requests under today's public contract; this packet does not call every synthetic input universally standards-conformant. Retained positive controls exercise unconstrained fields, optional incompatible values, absent flagged entries, mandatory Browser enrollment, advisory policy, and PDF 1.7 ignoring the new PDF 2.0 flags.

## Current policy, safety purpose and effect of each cut

Source references are revision-bound by `inventory.json`. `PdfSignatureSeedValues.Check` is at lines 17–102; helpers at 104–253; Get/Flags/Refuse at 256–282. `PdfSigner.SealExistingField`, lines 262–322, checks every distinct value owner before setting V. ACCEPTANCE.md 114–117 and docs/behavior.md 151–155 define shipped behavior. W-151's completed record and approved `w-151-owner-disposition.md` remain authoritative and unchanged.

For each deleted satisfiability helper, R203 refuses its entire applicable mandatory domain before invoking a provider. Therefore it cannot newly accept a mismatching mandatory value through that helper. Certificate checks are copied unchanged; MDP and timestamp changes are strict additional refusals; object resolution and other write gates remain. This is a local safety argument with bounded execution evidence, not an exhaustive hostile-input proof. The sample includes seven distinct current refusals: handler, ordered format, digest, reason, nested certificate, nested timestamp and certification. Existing malformed arrays/flags, indirect ownership, version differences, locks, omission, pending edits and async retry are also internally tested by 74/74 current-engine W-151 cases rerun on net10. Candidate versions of those 74 tests were not run and would intentionally fail compatibility expectations. No new confirmed shipped defect was found.

## Provider and assembly interactions

W-202 recommends retaining public providers. R203 can be applied with either provider boundary, and W-202 removal would not make the 15 rejected cases disappear as business needs. Its proposed internal builders still need digest/format/time-stamp checks and field-owner preflight. Removing opaque providers may permit stronger future capability knowledge, but W-202 explicitly leaves seed policy unchanged and does not authorize certificate inspection, TSA endpoint inference or a mechanism exception. Do not count provider API reduction or retained CMS/RFC3161 code as R203 savings. Raw HSM/cloud integration cost is nonzero and separate; no seed refusal is repaired merely by migrating a complete-CMS service to a raw signer.

W-194's proposed assembly slice A preserves satisfiable mandatory Filter/SubFilter/V/Reasons/DigestMethod/AddRevInfo=false/MDP0/LockDocument=false-or-auto for later signing. R203 would turn those preserved fields into unusable signing targets unless the assembly proposal is expressly narrowed or its later-signing contract remains W-151. W-194 is not implemented: current assembly omits signature fields. This packet adds no preserved-field end-to-end signing claim. An issuer may need to regenerate a supported original; silently deleting SV, choosing a new unconstrained field or flattening away a designated signing location is not a migration. W-194 Include-lock creation/remapping remains a separate approval that cannot be counted as removed by R203.

## Cost, recommendation and limits

Retain W-151. R203 removes four local satisfiability helpers and matching logic, not PDF parsing, owner discovery, mandatory classification, certificate policy, existing lock/permission enforcement, CMS construction, RFC3161, profiles, algorithms, private staging, reservation limits, rollback diagnostics or tests of these guarantees. It adds a support boundary, refusals and issuer-recovery documentation. The 182 physical lines and 28 lexical conditionals saved are real local draft measurements; maintenance benefit, defects prevented, customer prevalence, runtime/memory gain and total codebase impact are unmeasured. Do not count removed regression expectations as product savings or double-count W-202/W-194 work.

Recovery would require a compatible issuer-produced field/document or another signing product. A password/owner credential does not override seed or certification restrictions; no extra key or credential makes R203 admit its excluded mandatory domain. Issuer coordination, regenerated documents and service/credential migration can exceed the engineering deletion cost. No automatic stripping or fallback field creation is proposed. Existing unconstrained/advisory signing remains usable.

Estimated effort if narrowing is approved: 1–2 engineering days for the checker change and focused contract/tests, plus 1–2 days for docs, representative caller migration and W-194 reconciliation. Basis: four localized helpers and one call site, known compatibility cases and cross-record public assertions; not measured implementation time. A named integration checkpoint is separately estimated at 1–2 days if paired with provider/assembly work, excluding unknown customer migration time and external review. Retain costs no runtime implementation; this packet supplies the decision evidence. See `proposal.md` for exact decision wording and conditional follow-up scopes.

Limitations: synthetic selected corpus, RSA-2048/SHA256 only, current Windows/net10 only, no real customer distribution, no remote provider/TSA, no token/hardware, no valid candidate timestamp token, no candidate full W-151 suite, fuzz, resource campaign, PDF-aware verification/profile classification, rendering, other frameworks or Docker checkpoint. No release/production qualification or independent fresh-context review is claimed. W-188's four unavailable review attachments and independent reconciliation remain unresolved as already recorded by W-202; they are not replaced by this single-agent experiment. Gate 2 adoption and any implementation remain owner decisions.
