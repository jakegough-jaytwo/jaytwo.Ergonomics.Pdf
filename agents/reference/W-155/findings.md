# W-155 encryption interoperability findings

Research at runtime source revision `0486719` (2026-10-26). No runtime, test-suite, protected-file or shipped-contract change. Existing owner notes in W-155 are preserved; the classifications here supersede their **unverified** hypotheses as research evidence only. This is not a release qualification or an independent human review.

## Inputs and reproduction

- Python 3.13.17, pypdf 6.21.1, qpdf 12.3.2; SDK 10.0.402. `manifest.json` records producer class and SHA-256 for every input. `cases.tsv` records the public test passwords as base64 (not secrets), input and save mode.
- 108 tiny cases. pypdf and qpdf produce the cryptography independently of this repository. Malformed lengths, explicit Crypt streams and direct Info use documented surgery on pypdf envelopes, with regenerated classic-xref offsets. These are synthetic variants, **not real-world producer fixtures** and not proof that a tolerated quirk is needed. `base.pdf` is the plaintext qpdf input.
- Windows: net10.0/10.0.13, net8.0/8.0.31, net6.0/6.0.36, net48 host loading netstandard2.0, and netstandard2.0 on net8.0. Each TSV starts with the **actual engine target**. Linux: net10.0/10.0.13, net8.0/8.0.32, net6.0/6.0.36 in existing image `jaytwo_ergonomics_pdf_w182_4cae92b__builder:latest`, plus net10 with `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1`. This runs the current Windows-built managed assemblies, not the image's older engine. No Docker integration checkpoint is claimed.
- `Program.cs` uses public APIs: open; read Title; read `probe.bin`; selected cases edit Title to `saved`, add an empty attachment, and save. Nine save probes record `prefix=True`. `independent.json` contains qpdf structural and attachment checks, pypdf input reads and saved-output reads. `summary.json` validates all nine saved titles, preserved payloads, empty attachments and the raw stored length (32 bytes for AES empty streams; zero for RC4/plaintext).

## Public references and producer cautions

- [RFC 4013 sections 2-2.5](https://www.rfc-editor.org/rfc/rfc4013.html), [RFC 3454 sections 4-7 and appendices B-D](https://www.rfc-editor.org/rfc/rfc3454.html): normalization version, full scalar tables and stored-string/query distinction. A platform's current `Normalize` and category tables do not establish SASLprep conformance. `r6-unicode32-query` supplies Python's `ucd_3_2_0` NFKC bytes explicitly; it tests a query interpretation, not independent real-world authoring.
- [qpdf CLI Unicode password documentation](https://qpdf.readthedocs.io/en/stable/cli.html#unicode-passwords): auto/unicode legacy transcoding and alternative encodings on open. The installed 12.3.2 measurements, not the evolving web version, establish results here.
- [pypdf encryption source](https://pypdf.readthedocs.io/en/6.21.2/_modules/pypdf/_encryption.html); the **installed 6.21.1 source** was inspected for `_encode_password` and `_saslprep`. It applies SASLprep for V>=5, including R5, normalizes with current Python Unicode data, and falls back to raw UTF-8 on preparation errors. Consequently its R5 normalized-file failures do not by themselves establish an engine defect. `r5-raw-nfkc` and qpdf force-R5 distinguish this from the truncation defect. The online source is a navigation reference, not a claim to have run 6.21.2.

## Handoff and limits

There are two supported-contract discrepancies that require correction, not a choice of a weaker contract: 127-byte password handling and explicit Crypt stream reads. Incomplete scalar preparation also leaks platform-dependent authentication/error behavior. **Affected runtime work stops here**: W-214/W-215/W-216 are proposed narrow follow-ups, not implementation or queue insertion. Each carries a reproducible input and permanent red assertion. D-67 is **proposed** for owner review of fallback/tolerance policy before W-217. The current queue advances to W-190 after this research; no R5/security exit claim follows.

All normal modern hosts agree (62 read successes, 46 controlled failures); net48 differs only on the supplementary noncharacter, with a raw exception. Invariant Linux differs on three normalization cases. Results are per input and operation, not a proof that all Unicode or all encrypted PDFs are handled. Owner-only reads were additionally measured on Windows net10 (`owner.tsv`), not across every runtime. No performance, rendering, signing, fuzzing, full framework **test-suite** matrix or release gate was run. No real-world file establishes padded O/U, bit-unit CF Length, malformed AES empties or direct Info as an approved writer quirk. Those limitations prevent silently converting tolerance observations into policy.
