# D-60. The R2 workflow contract

## Context

Reset stage R2 builds `jaytwo.Ergonomics.Pdf` workflows (`reset-plan.md` section 8), but `docs/spec/` had no workflow requirements. W-141 put nine design questions to an outside expert who had no access to the code, then checked the answer against the engine. `agents/reference/r2-workflow-proposal.md` holds the full proposal: the review, the API sketch, and the caller-code comparison.

## Decision

1. A workflow binds one input through `PdfWorkflow.From` (a `Stream` or an `IPdfSource`) or `FromFile` (a path). It reads nothing until a terminal call and copies its arguments when they are described. Once a terminal call has begun, the builder rejects any mutation and any further or concurrent execution, including after a failure or cancellation.
2. The workflow never disposes a caller-supplied stream or `IPdfSource`, even after a failure or cancellation. It disposes the engine objects and adapters it creates without closing the borrowed resource beneath them. Files it opens from paths are owned for the run only.
3. A run applies every operation through one `PdfDocumentEditor` and saves once. Fills merge into one bulk fill that holds only the last declared value of each field, applied before any flatten. Every other operation replays on the editor in declaration order with engine semantics: no normalization, no suppressed engine exception, and no inferred final state. The workflow adds no PDF validation policy of its own.
4. Engine exceptions propagate unchanged. Argument errors, workflow-shape errors, and conflicts detectable without reading the document are thrown before the input opens. No destination is written until every operation has been applied.
5. The outputs are a stream (empty, writable, seekable), a path (a temporary sibling, then `File.Move`, or `File.Replace` with `Overwrite`), and an explicit `AppendToSource`. Non-seekable destinations are rejected, and an output path equal to the input path is rejected.
6. Pages are numbered from 1, as `PdfPage.Number` is. A page number below 1 is rejected when described, and one above the page count is rejected before output.
7. `AttachFile` takes its MIME type from the caller when supplied. Otherwise it uses a fixed table matched without regard to case: `.xml` `text/xml`, `.json` `application/json`, `.pdf` `application/pdf`, `.csv` `text/csv`, `.txt` `text/plain`. Any other extension leaves it unspecified.
8. Signing stays out of the workflow until stage R4. Flatten and rotation on a signed document need `AllowBreakingExistingSignatures()`, which never relaxes certification, FieldMDP, or password permissions.
9. The read shortcuts are form export only.

## Consequences

- The requirement rows F1 to F16 are in `docs/spec/phase-1.md` section 6.7 with status New. Fills and flatten requests are the only operations the workflow merges (F5). Output is semantically equivalent to the direct-engine operations, with the source as an exact prefix; byte identity is tested only where the operations write no clock-dependent value (F4). W-141 refined the acceptance criteria of W-142 to W-145.
- A change to an attachment stream's content between description and the run cannot be detected without reading the stream when it is described, which F1 forbids. The engine detects a change between its add-time and save-time reads.
- W-145 implements form export only.
- Remote sources are not advertised as nonblocking until W-138 settles asynchronous inspection.
