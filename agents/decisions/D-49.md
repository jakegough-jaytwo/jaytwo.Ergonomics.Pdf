# D-49. Bounded source reads: retained cursor windows per operation, deterministic I/O tripwires

## Context

W-79 recorded that signing the filled 500-page object-stream form reads 142 times its size, and flattening the 1,000-page form reads 410 times, and attributed both to the engine keeping one clean object stream decoded. A measurement on 2026-10-22 (same fixture shape, 250 to 4,000 pages, net8.0, Release) showed otherwise:

- The multiple is constant with size (flatten 357.1 to 408.3 times, sign 141.2 to 143.5 times), and time grows linearly (flatten 0.16 s at 250 pages to 1.05 s at 4,000).
- Measured directly from the read log: at 1,000 pages, flatten reads 399 MB in 6,386 reads, of which 5.9 MB is in reads that start inside object streams. Sign reads 139 MB, of which 5.9 MB starts inside object streams. Nearly every read is a full 64 KiB.
- Inferred from the code and a replay of that log: `PdfCursor.Seek` discards its 64 KiB window, so the next read refills 64 KiB even when the target object is a few hundred bytes and was in the discarded window. Replaying the logged reads against a cursor that keeps its last four 64 KiB windows predicts flatten falling from 399 MB to about 2.7 MB at 1,000 pages, and from 1.6 GB to about 10.5 MB at 4,000, so roughly 98% or more of the bytes are repeated window refills, not object-stream decoding. The replay treats a read that starts inside a retained window as free, so these are estimates.
- Object-stream re-decoding is real but smaller: each of the 41 streams of the 1,000-page form is decoded 4.7 to 7.5 times per operation (578 KB decoded once). Access is cyclic across all streams. In a replay at 1,000 pages, an LRU of 2 to 32 streams removes about 14% of decodes for field reads and bulk fill, about 5% for sign, and under 1% for flatten; none removes the repeats unless all 41 streams fit. Holding every stream the operation touches (about 0.6 KB per page here) removes them. A fixed byte ceiling is a cliff: 1 MiB removes them at 1,000 pages and saves almost nothing at 2,000.
- Dirty retention already keeps every stream an edited object came from, so bulk fill and flatten end holding all of them; only read-only work and sign stay at one.

The charter's sparse design exists to keep large files fast and memory bounded. Callers use local disks and slower local storage such as SMB or NFS shares and cold disks, where repeated reads cost real I/O. Remote range-request streams are out of scope.

## Decision

1. **Goal.** Predictable scaling: the source bytes, read calls, and decode work of an operation are proportionate to the objects it touches, not to a buffer size or to how often it revisits a region. Memory has fixed, documented ceilings; it is not minimized for its own sake.
2. **Meaning of sparse.** Memory follows the operation's working set under fixed, documented ceilings. Retaining fixed-size, short-lived bytes is preferred to fetching them again.
3. **Cursor windows.** `PdfCursor` keeps the most recently filled 64 KiB windows, least recently used first out, and serves a seek that lands in a retained window without I/O. The retained windows are capped at 1 MiB per open document; the window count, between 4 and 16, is set from measurements after the change. A fill stays 64 KiB; there is no small first read after a seek, because it adds read calls.
4. **Lifetime.** Retained windows are released when each public operation returns, normally or by exception, the way `ObjectStreamLease` releases clean object streams. No source byte read in one public operation is served in another. Within an operation that appends to its own source, a window that ended at the earlier end of the stream is never taken as end of file.
5. **Contract and tripwires.** `README.md` makes no promise about read multiples. The design rule is that fetching an object costs I/O proportional to that object, and re-reading bytes the cursor still holds within the operation costs none. Tests gate three deterministic numbers per fixed fixture: source bytes read, read calls, and decoded bytes. Thresholds are absolute, set from post-change measurements plus headroom, and a change that raises one updates its threshold in the same commit with a reason. Wall-clock time stays reported and ungated.
6. **Object streams.** The policy stays: at most one clean decoded object stream, plus streams kept for dirty objects. Holding every clean stream an operation touches, under a hard cap such as 16 or 32 MiB and falling back to today's behavior above it, is approved for 1.x polish. A signing field snapshot and stream-aware flatten planning remain alternatives if that proves insufficient.
7. **Sequencing.** The cursor change lands before the 1.0 release checks.

## Consequences

- One internal class and the operation lease change. There is no public API change, no new dependency, and no change to the bytes written.
- Parse failures keep their exception types and reported offsets. The 32 MiB and 64 MiB decompression caps are unchanged. Nothing scans the whole file.
- The cursor sits under every fuzz target, so all eight G8 targets are rerun from the changed code at the campaign's predeclared allocation, and the G7 measurements in `agents/evidence/qualification/memory-budgets.md` are recorded again.
- W-79's explanation of the read multiples is superseded by the Context above.
- Rejected: a small LRU of decoded object streams (cyclic access defeats it: at most about 14% fewer decodes, and under 1% for flatten); a fixed byte ceiling for object streams (a cliff); a read multiple of the file size as a product promise (the wrong yardstick, blind to read calls and decode work, and binding on the implementation); a small first read after a seek (more read calls, the costlier side on shared storage); document-lifetime windows (a new rule against modifying the source, and invalidation, for no measured gain); disk-backed spill (unneeded at 1 MiB); deferring the cursor change past 1.0 (1.0 would read 140 to 410 times on slower local storage, which is in scope).
- Open: whether real-world forms (Acrobat, iText, Word export) show the same access pattern; whether a measurement on a real SMB share is part of the evidence.
