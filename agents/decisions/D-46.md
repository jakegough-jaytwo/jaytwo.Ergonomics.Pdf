# D-46. Only the signature /Contents stays plaintext in an encrypted file

## Context

`AGENTS.md` said "Leave signature dictionaries plaintext", and spec §7.4 said "Signature dictionaries stay plaintext". On a password-encrypted file, `Sign` therefore wrote `/M`, `/Reason`, `/Location`, `/ContactInfo`, and `/Name` in plaintext, and the reader skipped every string in a dictionary whose `/Type` is `/Sig` or `/DocTimeStamp`. W-14 found that other readers decrypt those strings with the document key, as ISO 32000-1 7.6.1 requires for every string outside the trailer `/ID`, the encryption dictionary, and encrypted streams: pypdf 6.21.1 read `/M` as an empty string, and Poppler `pdfsig` 26.08.0 crashed when it fell back to the decrypted `/M`. Poppler (merge request 718) and pyHanko 0.38.0 exempt only `/Contents`, which is written into a gap reserved before the digest. pyHanko writes `/M`, `/Reason`, and its FieldMDP field names as ciphertext, so the library also read those names as ciphertext. W-97 set out two options: A, encrypt every signature dictionary string except `/Contents`, or B, keep the behavior and document it.

## Decision

Option A. In an encrypted file, the signature `/Contents` is the one plaintext string. Every other string in a signature dictionary (`/Type /Sig` or `/Type /DocTimeStamp`) is encrypted on write and decrypted on read with the document's string cipher, under the number and generation of the object that holds it, like any other string. That covers the strings the library writes in a new signature dictionary and the strings of a signature dictionary already in the file, including field names in its `/Reference` transform parameters, and a dictionary the library writes again because the object that holds it changed. `/Contents` is neither decrypted nor encrypted. A signature dictionary without `/Type` is treated like any other dictionary, as before.

The owner approved these edits, applied verbatim:

- `AGENTS.md`: "Leave signature dictionaries plaintext." becomes "Leave the signature `/Contents` plaintext."
- `docs/spec/phase-1.md` §7.4: "Signature dictionaries stay plaintext." becomes "The signature `/Contents` stays plaintext."
- `.agents/skills/pdf-signing-change/references/signing-matrix.md`: the row "Encrypted PDF: signature dictionary strings stay plaintext; the rest of the revision is encrypted | library tests; pyHanko with the password" becomes "Encrypted PDF: the signature `/Contents` stays plaintext; every other string in the signature dictionary and the rest of the revision is encrypted | library tests; pypdf, pyHanko, and `pdfsig` with the password".

`QUALIFICATION.md` has no such sentence and is unchanged.

## Consequences

W-97 implements it, with `ACCEPTANCE.md` and `README.md`. The `/ByteRange` covers the encrypted strings; their length is known when the dictionary is written, before the digest. A FieldMDP lock written by pyHanko on an encrypted file now applies to the named fields; on the W-97 samples the library had failed every fill with a parse error, because it read those names as ciphertext. Reading stays strict: a signature dictionary string written in plaintext in an AES-encrypted file, as the library itself wrote before W-97, is not a valid ciphertext and fails as any such string does, with `PdfParseException` when the object is loaded; under RC4 it reads as garbage, as it does in pypdf and Poppler. The library is at 0.1.0, before the 1.0 release.
