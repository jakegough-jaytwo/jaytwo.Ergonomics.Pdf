# D-62. Security hardening is its own phase

## Context

W-148 through W-159 form a consolidated security-hardening backlog. W-167 and W-168 split the work-budget investigation from W-149, and W-169 and W-170 are corrections discovered while reviewing that work and W-150. The backlog needs a named scheduling boundary that does not interrupt the reset stages that establish the final product architecture.

## Decision

1. The security-hardening work is a distinct phase after reset stage R4 signing and before reset stage R5 advanced capabilities.
2. The phase consists of W-148 through W-159 and their split or corrective items W-167 through W-170, except that W-154 runs during R3 because W-164 requires its authentication and permission correction for encrypted input. Items already done remain completed security-hardening work; the remaining phase items run in the order recorded in `agents/state/current.md`.
3. The phase is complete when every included item is done or cancelled through an owner-approved disposition. R5 work does not begin before that exit.
4. This scheduling phase does not add product scope, change a security guarantee, or alter the R0-to-R5 architecture in `reset-plan.md`.

## Consequences

- Security research, implementation, and hosting guidance have one visible scheduling boundary and exit condition.
- R3 assembly and R4 signing run before the remaining security work.
- W-154 is the narrow scheduling exception: it remains security hardening, but runs as an R3 prerequisite before W-164.
- The complete R4 implementation sequence must be planned and inserted ahead of the security phase before R4 begins.
- R5 advanced-capability work follows the security phase.

## Authority

The owner, 2026-10-24. The owner directed that the security-related work items be reorganized into their own phase, then clarified that it belongs after signing and before advanced capabilities.
