# D-44. Signing an existing empty field keeps usage rights that grant it

## Context

Spec §7.3 keeps a Reader-extended file's `/UR3` signature only when its UR3 transform parameters grant the write, and it listed no right for signing, so W-67 removed `/UR3` on every `Sign`. ISO 32000-1 Table 255 defines `/Signature` `Modify` as permission to apply a digital signature to an existing signature form field, and every Reader-extended form in the corpus grants it. W-67 also read replacing an attachment of the same name as `/EF` `Modify`, which §7.3 did not say.

## Decision

A `Sign` into an existing empty signature field keeps `/UR3` when the transform's `/Signature` array lists `Modify`. A `Sign` that creates a new signature field and a document timestamp remove `/UR3`, as does every transform that is absent, unresolved, malformed, unknown, or insufficient. Replacing an attachment that has the same name is `/EF` `Modify`. §7.3 of `docs/spec/phase-1.md` is replaced with the owner's text:

> When the catalog `/Perms` has a `/UR3` signature, a write keeps it when its transform parameters grant that operation:
>
> - `/Form` `FillIn` for fills;
> - `/EF` `Create`, `Delete`, or `Modify` for attachment edits; replacing an attachment that has the same name is `Modify`;
> - `/Signature` `Modify` for `Sign` into an existing empty signature field (ISO 32000-1 Table 255).
>
> Any other write removes `/UR3` from `/Perms` in the same revision, so Adobe Reader drops the extended features silently instead of reporting a broken document. A `Sign` that creates a new signature field and a document timestamp are such writes.

## Consequences

W-87 implements it, with `ACCEPTANCE.md` and `README.md`. The usage-rights signature is still not validated, and the legacy `/Perms /UR` entry is still not read. Whether a `Sign` that removes `/UR3` from a certified file breaks its certification is W-88. No Adobe Reader was available to confirm Reader's behavior on the output.

## Authority

The owner, 2026-10-20, under W-87.
