# D-67. Proposed encryption interoperability correction and tolerance policy

## Context

W-155 measured seven encryption edge-case families at `0486719`. [Findings](../reference/W-155/findings.md) include independently produced qpdf/pypdf encryption, 108 public-API cases across runtime families and permanent red assertions. The investigation does not authorize changing an encryption guarantee or the closed writer-quirk policy.

## Decision

**Proposal for Jake; not adopted:**

1. Preserve standards-based password processing. Correct exact 127-byte truncation in W-214. Correct scalar validation and typed failures in W-216. Do not add a raw-UTF-8, Latin-1 or WinAnsi retry. qpdf raw-soft-hyphen R6 files remain rejected unless the owner separately adopts a fixture-backed tolerance with exact wording.
2. Correct explicit Identity and StdCF per-stream Crypt handling in W-215 without adding EFOpen or public-key encryption.
3. In W-217, reject incorrectly sized O/U/OE/UE/Perms values rather than using prefixes. R5/R6 O/U require 48 bytes, OE/UE 32, Perms16; legacy O/U require32. Existing reader acceptance is not producer evidence for a new tolerance.
4. Reject direct trailer Info rather than inventing a classic-trailer encryption key. Proposed shipped-contract wording: "A trailer /Info value must be an indirect reference. A direct dictionary is rejected with PdfParseException; its strings are not interpreted using an invented object identifier."
5. Retain optional CF Length for PDF1.7. Do not apply PDF2's required entry retrospectively. For standard-handler explicit CF Length, use byte units (AESV2=16, AESV3=32); retaining bit units requires a real producer fixture and a separately approved quirk. Do not change R4 top-level omission/default handling or add smaller V4 RC4 keys without version-specific standard reconciliation and an independent fixture. Proposed length wording: "Encryption key-value strings have the exact sizes specified for their security-handler revision. Standard-handler crypt-filter lengths use bytes; the presence requirement follows the PDF version."
6. W-216 must present the exact Unicode3.2 query/unassigned-character policy and invariant-globalization handling before implementation where it changes accepted passwords. The existing incomplete checks do not authorize raw fallback or a new authentication equivalence.

## Consequences

Some malformed files currently tolerated would be refused, so this needs explicit owner approval and corresponding shipped-contract edits. Proposed text above is not shipped behavior and changes no protected file. Follow-up items remain proposed and unqueued. No algorithms or runtime dependencies are added; encryption remains supported.

## Authority

Prepared 2026-10-26 under W-155. **Jake must approve the policy and exact protected wording; no approval has been inferred.** Standards-backed defect correction and tolerance adoption are separate scopes. The reference findings identify which producer observations are not conforming-file evidence.
