# D-64. R4 signing terminals, staging, and qualification

## Context

W-172 plans reset stage R4 after the completed R3 checkpoint and before security hardening (D-62). The owner adopted the signing design after an external design review and repository capability checks. This is target behavior; it does not claim the workflow terminals are shipped.

## Decision

1. Signing and document timestamps are dedicated workflow terminals, with synchronous and asynchronous forms and separate stream and file outputs. Each execution supports one signature or one document timestamp. A CMS signature may include an embedded RFC 3161 signature timestamp; that token is not a second PDF revision. Multiple signatures or a signature followed by a document timestamp in one execution are deferred.
2. Keep existing engine interfaces, algorithms, options, and defaults. The common signing convenience accepts `IPdfExternalSigner` and optional `ITimestampAuthority`; an advanced overload accepts the existing `IPdfSignatureProvider`. Document timestamps use the existing authority and provider. No engine API migration is scheduled without a demonstrated need.
3. Ordinary edits are staged before signing, producing an ordinary edit revision when changes exist and a separate signature or document-timestamp revision through the same editor. An unchanged input gains only the signature or document-timestamp revision. Use private seekable file staging with bounded buffers, never a whole-document managed allocation. Do not reopen the document or create a second editor to sign the staged output.
4. Complete signing, including any signature timestamp, before publishing a file or copying to the caller's stream. Preserve existing ownership, overwrite, alias, flush, cancellation, exception, and output-failure guarantees. In particular, final-copy cancellation or I/O failure has best-effort stream rollback; arbitrary streams do not acquire an atomic-publication guarantee.
5. Signing-to-source conveniences and automatic signer/TSA retries are excluded. A reservation failure leaves unpublished staging disposable and requires a new caller-initiated execution to try again.
6. R4 qualification includes pinned test-only DSS and JDK profile classification, direct CMS fuzzing, refreshed direct-engine and workflow signing interoperability evidence, and an explicit integration exit checkpoint. Profile classification, cryptographic verification, and trust-policy results are separate claims. No runtime signature validation, trust service, new format or algorithm, B-LT/B-LTA, package release, or broad security-hardening scope is added.
7. Preserve one editor session. Propose exact protected-document wording before changing it. The proposal in `agents/reference/r4-signing-proposal.md` is pending approval; this decision approves the direction, not that proposal's exact wording.

## Consequences

- Queue W-179, W-180, W-103, W-104, W-181, and W-182 before the remaining security phase. W-179 applies only wording expressly approved by the owner; implementation follows it.
- W-103 and W-104 are retained and reassessed for the engine boundary. W-181 owns the fresh campaign and interoperability record; it does not rewrite the completed W-18 evidence.
- Public behavior documentation and requirement status change with implementation, not with this planning transaction. Release qualification and packaging remain suspended under D-54.

## Authority

The owner, 2026-10-25: adopted the seven-point R4 direction, explicitly required one editor session, and required exact protected-document wording to be proposed before modification.
