# W-61 charter reset plan review

## Task

Independent review of `agents/reference/charter-reset-plan.md`, with the goal of reaching consensus before charter, workflow, or queue changes begin.

## Review position

I agree with the reset's direction: adopt the Phase 1 target, update the governing documents before feature work, slim process that does not protect product outcomes, and rebuild the queue around the new scope. I recommend approval after the plan incorporates the concrete changes below. None requires reopening D-38 or D-39.

## Findings to resolve

### 1. A1 needs an explicit end to the `New`/`Change` exception

The proposed precedence rule removes today's immediate stall, but it leaves a permanent blind spot: `docs/spec/phase-1.md` can continue to label a requirement `New` or `Change` after implementation, so shipped behavior could diverge forever without becoming a defined disagreement.

Proposed consensus text: a feature item must atomically update its requirement status to `Exists`, update `ACCEPTANCE.md` and the shipped-behavior sections of `README.md`, and add the required evidence. Until then, the requirement is target behavior and must not be advertised as shipped. Once the item lands, a contradiction among implementation, `ACCEPTANCE.md`, `README.md`, and the now-`Exists` requirement is a disagreement.

This also resolves two timing problems in the current plan:

- `README.md` must not present the full Phase 1 list as current capability; label it explicitly as the 1.0 target and keep current support separately visible.
- `README.md` must not say `Microsoft.Bcl.AsyncInterfaces` is a shipped dependency until the async item actually adds it. `AGENTS.md` may record the owner's authorization earlier.

### 2. A2/A3 must state the PDF 2.0 output boundary introduced by associated files

W9 uses `/AF` and `/AFRelationship`, which are generic PDF 2.0 associated-file features (also used by PDF/A-3). Section 7.5 correctly uses catalog `/Version` for an incremental version increase, but A2 does not currently say to rewrite the charter's “Read PDF 1.0 through PDF 1.7” version bullet. Without that change, the new charter can still contradict its own attachment target.

Proposed change: explicitly state that Phase 1 opens PDF 1.0–1.7 plus the supported PDF 2.0 structures in R1, and that an incremental write using a PDF 2.0 feature raises catalog `/Version` to `/2.0` while preserving the header. The W9 item should test the resulting effective version and document whether PDF/A-3 conformance is claimed (my recommendation: do not claim PDF/A conformance merely because the associated-file keys are written).

The catalog-version mechanism is supported by PDF 32000-1, and `/AFRelationship` is identified as PDF 2.0 in the PDF 2.0 text/errata: [PDF 32000-1 catalog `Version`](https://opensource.adobe.com/dc-acrobat-sdk-docs/standards/pdfstandards/pdf/PDF32000_2008.pdf), [PDF 2.0 file-specification entries](https://pdf-issues.pdfa.org/32000-2-2020/clause07.html).

### 3. B1 removes workflows, but it must not discard evidence artifacts required by the new gates

Calling the corpus manifest the “one valuable artifact” is too strong. Phase 1 G7 still requires repeatable workload/baseline records, and G1–G10 still require a fresh evidence inventory tied to commits, fixtures, tools, and outcomes. Those artifacts remain valuable even if dedicated interop, performance, conformance, and release skills are unnecessary.

Proposed change: cancel the four not-yet-created skills, but explicitly re-home the minimum durable artifacts:

- corpus manifest and validator under W-13 / `pdf-change-verification`;
- performance workload and baseline record under G7 / `pdf-change-verification`;
- qualification evidence inventory and freshness check under A5;
- release gate summary generated from that inventory, not maintained as a second board.

The clause-to-contract map can wait unless a concrete conformance problem justifies it.

### 4. Keep superseded decisions instead of implementing B2

I recommend keeping D-01–D-08, D-11, and D-04 in place with their terminal status. D-34 through D-36 removed bulky role-era material after distilling it into decisions; they are not precedent for deleting the decisions themselves. Ten small decision records cost essentially nothing when not read, while deletion breaks validator references or forces exceptions/annotations and makes the authority chain harder to audit.

Consensus proposal: replace B2 with “verify terminal statuses and remove superseded decisions from active navigation.” Do not delete them.

### 5. B3 is sound only if `task-check` validates the staged owner, not the working tree or HEAD owner

I support activation-plus-work in one commit. The current two-commit rule's useful protection is that every non-record path is checked against an already committed active item's `allowed_changes`. Preserve that protection by making the staged transaction self-describing:

- parse the work item from the staged index;
- require exactly one staged `active` item and no second active item in the staged repository state;
- use that staged item's `allowed_changes` for every staged path;
- validate the staged repository state, not merely the worktree;
- add tests for unrelated pre-staged files, two activations, an activation with a disallowed path, and activation plus allowed work.

With those conditions, B3 removes ceremony without weakening the boundary.

### 6. C2 contradicts its own signing-order rationale

C3 says the second-verifier harness comes first, but C2 places the async signer at sequence 8 and W-14 at sequence 9. Put W-14 before every signing behavior change, then extend its cases as ECDSA, digests, and PAdES land. This avoids accepting new signature code with only the old verifier path.

The corpus can remain before the API reshape if item 4 is limited to fixtures, provenance, manifest validation, and format probes. Feature-specific API tests should be added by the later feature items so item 7 does not immediately rewrite them.

### 7. Make the fuzz blocker list complete and objective

C3 names items 6, 12, 13, and 16 as parser-surface work, but W-40 indirect filters (5) and usage-rights parsing (17) also change hostile-input surfaces; attachment metadata/relationships (15) may as well. Replace the informal list with explicit dependencies on every pre-campaign parser/CMS item, or state that the campaign begins only after all Phase 1 input surfaces are frozen.

A5 also needs objective gate language:

- replace “about 30” with a minimum number of distinct, meaningful files plus the four required categories;
- define campaign completion by named targets, seeds/corpus, per-input limits, coverage/health observations, and triage/rerun results within D-23's compute cap—“one campaign” alone can be arbitrarily small;
- expire evidence when relevant production code, test oracle, fixture, tool configuration, or gate definition changes, not only when “the code it covers” changes.

### 8. Add cross-cutting acceptance requirements to every new mutation item

The plan should require each new write to cover:

- encrypted input under owner and user passwords, including permission refusal;
- same-cipher encryption of new strings/streams and preservation of `/Encrypt` and `/ID`;
- prefix preservation and unchanged destination on every documented failure;
- certification, approval-signature, FieldMDP, and usage-rights behavior where applicable;
- sync/async equivalence and cancellation rollback for the async item.

For flatten specifically, retain the adopted distinction: DocMDP blocks flatten at every `P`; an approval signature requires explicit opt-in; signed signature fields are never flattened. The tests should show that the earlier signature's bytes remain cryptographically intact while an independent verifier reports the expected later modification.

## Standards checks

The questioned technical directions are otherwise consistent with the cited standards:

- PAdES B-B uses `/ETSI.CAdES.detached`, requires the signing-certificate reference (v2 for the Phase 1 SHA-2 algorithms), carries claimed signing time in signature-dictionary `/M`, and omits CMS `signing-time`. A signature timestamp advances it to B-T. See [ETSI EN 319 142-1 V1.2.1](https://www.etsi.org/deliver/etsi_EN/319100_319199/31914201/01.02.01_60/en_31914201v010201p.pdf).
- The flatten placement reference is correct: ISO 32000-1 §12.5.5 maps the appearance `/BBox` through its `/Matrix`, then scales/translates that result to the annotation `/Rect`. See [PDF 32000-1:2008](https://opensource.adobe.com/dc-acrobat-sdk-docs/standards/pdfstandards/pdf/PDF32000_2008.pdf).
- Treating a linearized file's first-page and main cross-reference sections as one logical revision is correct; the first-page trailer points back to the main table as part of the linearized layout, not an incremental edit. See [Adobe PDF Reference 1.7, Appendix F](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/pdfreference1.7old.pdf).
- `/Form /FillIn` and `/EF /Create`, `/Delete`, or `/Modify` are the relevant UR3 rights, but the implementation item should require resolving the actual signature `/Reference`, `/TransformMethod`, and `/TransformParams` and rejecting unknown/malformed forms conservatively. See [PDF 32000-1 UR transform parameters](https://opensource.adobe.com/dc-acrobat-sdk-docs/standards/pdfstandards/pdf/PDF32000_2008.pdf).

### Counterproposal for disposition 3: no `/2.0` raise in Phase 1

I agree with the diagnosis. The charter's "PDF 1.0 through 1.7" bullet must be rewritten, and PDF/A conformance must not be claimed. I disagree with the remedy of raising the catalog `/Version` to `/2.0` when `/AF` is written:

1. **It breaks the motivating use case.** W9 exists for Factur-X and ZUGFeRD, which are PDF/A-3 files. ISO 19005-3 is based on ISO 32000-1 and itself sanctions `/AF` and `/AFRelationship` in a 1.7 file. Raising a PDF/A-3 invoice's effective version to 2.0 makes it claim a base standard that PDF/A-3 is not defined against, which invites rejection by conformance validators such as veraPDF for a file that was valid before we touched it. I have not run veraPDF on such a file; the W9 item should, if veraPDF is added to the toolset.
2. **2.0 is a heavier claim than one key.** A file whose effective version is 2.0 is judged against ISO 32000-2's deprecations, for example RC4 encryption (security revisions 2 to 4) and the Info dictionary. Phase 1 deliberately preserves both. Raising to 2.0 to cover one dictionary key would make files claim conformance they do not have.
3. **The library already writes these keys at 1.x.** `Attachments.Add` writes `/AFRelationship /Unspecified` and adds the file to catalog `/AF` today (`PdfEngine.cs` lines 782 and 2798). That is shipped behavior.
4. **ISO 32000-1 tells readers to ignore unknown keys.** A 1.x reader ignores `/AF`, and the attachment stays fully reachable through `/EmbeddedFiles`. Writing `/AF` is therefore a compatible extension, not a feature the declared version needs.

Proposed rule for spec §7.5, W9, and the A2 version bullet:

- Phase 1 opens PDF 1.0 to 1.7 plus the PDF 2.0 structures listed in R1.
- An incremental write raises catalog `/Version` only up to `/1.7`, and only when a feature it writes is defined in ISO 32000-1 at a later version than the file's effective version. Example: `/PageMode /UseAttachments` is PDF 1.6.
- Phase 1 never raises a file to `/2.0`.
- `/AF` and `/AFRelationship` are written as PDF 2.0 and ISO 19005-3 associated-file keys that ISO 32000-1 readers ignore. They never trigger a version raise.
- The W9 item tests the resulting effective version, including a PDF/A-3 input whose effective version stays 1.7.
- No PDF/A conformance is claimed. README says so. Appending to a PDF/A file is not guaranteed to keep it conformant.

Spec §7.5 currently names `/AF` as an example of a raising feature. If you agree, that example is corrected under the A3/A2 item. It is a spec change, so I will flag it to the owner for confirmation.

If you prefer a raise to `/2.0` when the input is already 1.7 and not PDF/A, I would accept that as a narrower variant. But detecting PDF/A means reading XMP on every attachment write, and I think "never 2.0 in Phase 1" is simpler and safer.

### Disposition 3 agreed: no automatic `/2.0` raise in Phase 1

I accept the author's counterproposal. PDF/A-3 introduced associated files as an extension to its ISO 32000-1/PDF 1.7 base, and raising such an input to effective PDF 2.0 would defeat the compatibility goal. The existing implementation also confirms that `/AFRelationship /Unspecified` and catalog `/AF` are already shipped without a 2.0 raise.

Please make these details explicit in the agreed revision:

- Treat writing `/AF` and `/AFRelationship` without a 2.0 raise as a deliberate, documented compatibility extension to generic PDF 1.x, not as strict ISO 32000-1 conformance.
- Distinguish the PDF/A-3 relationship subset (`Source`, `Data`, `Alternative`, `Supplement`, `Unspecified`) from values that come from PDF 2.0. A PDF/A-3 input is not promised to remain conformant when the caller selects a relationship outside the PDF/A-3 subset.
- Say that the feature supplies associated-file primitives useful to Factur-X/ZUGFeRD; it does not by itself claim PDF/A-3, Factur-X, or ZUGFeRD conformance. Those formats require additional metadata/profile rules outside W9.
- Keep the proposed W9 checks: effective version remains 1.7 for a representative PDF/A-3 input, `/EmbeddedFiles` remains the backward-compatible discovery path, and no PDF/A claim is made. A veraPDF observation is valuable if available, but it should be credited only for the profile property it actually checks.

This is consistent with the PDF Association's description that PDF/A-3 added associated files to its PDF 1.7 base, while PDF 2.0 later adopted the feature: [ISO 19005-3 overview](https://pdfa.org/resource/iso-19005-3-pdf-a-3/), [associated-files overview](https://pdfa.org/files-inside-pdf/). Full Factur-X construction additionally requires profile-specific XMP metadata and an extension schema: [Factur-X/PDF-A-3 requirements overview](https://pdfa.org/frances-e-invoicing-mandate-puts-factur-x-and-pdfa-3-at-the-center-of-compliance/).

Because this corrects adopted spec section 7.5, I agree it must be flagged for owner confirmation rather than silently changed.

### Disposition 8 agreed: conservative UR3 handling means removal

Confirmed. For a write otherwise permitted by password permissions, DocMDP, and FieldMDP, an absent, unresolvable, malformed, unknown, or insufficient UR3 transform should cause `/UR3` to be removed from `/Perms` in the same revision and the write to proceed. The library should not preserve a rights signature it cannot prove permits the change. A structural failure that prevents safely reading or rewriting the document remains an ordinary parse failure; this rule does not require repairing arbitrary corruption.
