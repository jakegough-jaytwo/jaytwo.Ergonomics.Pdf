# W-53. Derive the task-check owner from HEAD

## Problem

`task_check` finds the active item from the staged/working records. When a commit closes the active item (`active` to `done`), no item is active in that state, so the check falls back to record-only mode and rejects every other staged path. W-52's closing transaction staged `agents/work-items/W-52.md` and `agents/evidence/checkpoints/2026-10-19-W-52.md`, which is in W-52's `allowed_changes`, and the check failed.

## Why now

Every closing commit of an item that touches more than its own record trips the same false failure.

## Scope and exclusions

Read the owner from the work items as they are in HEAD. Keep the record-only rule first. Extract the ownership decision into a pure function with unit tests. Do not change the plan, other tooling, or product code.

## Acceptance criteria

Closing the HEAD-active item with an allowed extra path passes. A path outside `allowed_changes` fails and is named. A record-only change of one work-item file passes with no active item. A non-record-only change with no HEAD-active item fails. Replaying W-52's closing transaction against the fixed check passes with owner W-52.

## Evidence required

`make agents-test`, `make agents-check`, and `make task-check` results per commit, plus the W-52 replay output.

## Notes

- 2026-10-19: Opened after W-52's closing transaction was made while `task-check` was failing.
- 2026-10-19: Owner is now resolved from HEAD by the pure `resolve_owner`; replayed W-52's closing transaction successfully and closed.

## Closeout

Tests: `make agents-test` passed (6 tests, 4 new for `resolve_owner`); `make agents-check` and `make task-check` passed on each commit. The W-52 closing transaction was replayed against the W-53 fix; `python tools/agents/workflow.py task-check` printed `task-check: OK` (exit 0, owner W-52 as the only HEAD-active item), and the scratch worktree was removed. W-53 records activation, the fix, and the W-52 note.
