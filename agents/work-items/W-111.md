# W-111. Compare the G7 workloads with iText

## Problem

The large-file work (D-20, W-79, W-108) is meant to make the library fast and sparse, but its evidence is absolute: `agents/evidence/qualification/memory-budgets.md` records heap growth, time, and source I/O for this library alone. Nothing shows how those numbers compare with an established .NET PDF library doing the same work on the same files.

## Why now

The owner asked on 2026-10-22 for a like-for-like comparison with iText: "it's true we aren't competing, but the point of all these optimizations are basically performance."

## Scope and exclusions

- Move the G7 fixture generators (`FixtureWriter`, the dense, form, and attachment-payload writers, and the qpdf object-stream copy) out of `LargeWorkloadTests` into an internal `G7Fixtures` class in the test project. The move preserves the fixture bytes; `LargeWorkloadTests` behavior and thresholds do not change.
- A comparison project, `test/jaytwo.Ergonomics.Pdf.Comparison`, xUnit on `net10.0`, that compiles `G7Fixtures`, `WorkloadMeter`, `ProbeStream`, `ExternalTool`, and `TestCompat` from the test project as linked files and references iText Core 9.8.0 (`itext`, `itext.bouncy-castle-adapter`). It is not in `jaytwo.Ergonomics.Pdf.sln`, so Jenkins, `make build`, `make quiet-test`, and the Docker image never restore or run it.
- For each workload, one test per library performing the same operation on the same cached fixture. The library writes are incremental; iText runs in append mode (`StampingProperties.UseAppendMode`), so both outputs keep the source as a byte prefix. Each test checks its output outside the measured window: prefix preserved, and the result read back by this library.
- Workloads: dense 1 GiB inspect, metadata edit, and sign; 1 GiB compressed attachment add and extract; 500-page object-stream form extraction, metadata edit, bulk fill, and sign; 1,000-page flatten; AES-256 xref-stream 1 GiB inspect. iText opens files by path, its fastest input. Dense inspect also runs iText from a `Stream`, the input this library takes.
- Each test runs in its own Release process (`make compare-itext`), with a cold pass and warm passes. It records wall time, peak managed-heap growth (`WorkloadMeter`), allocated bytes, and the process's peak working set. A script tabulates the results.
- Record one run in `agents/evidence/itext-comparison.md`.
- Excluded: any library change, any change to G7 budgets or thresholds, a CI gate on the comparison, and claims about iText beyond the measured runs. Signature inspection and revision listing are excluded because iText's APIs for them do different work (`SignatureUtil` parses and hashes for verification; its revision count covers signatures only).

## Acceptance criteria

- `LargeWorkloadTests` passes unchanged after the extraction, and its fixture-dependent output hashes match the pre-move run.
- `make compare-itext` runs every workload for both libraries in separate processes and prints a table of the results.
- Every iText output passes its correctness check, so the two libraries are compared doing the same work.
- `agents/evidence/itext-comparison.md` records the environment, versions, method, and one full run.

## Evidence required

Internally tested: the comparison tests run and pass. The measurements are evidence about this machine and these fixtures, not a G7 gate.

## Notes

- 2026-10-22: iText Core is AGPL-3.0 or commercial. The owner asked for this comparison after that was raised; the package is referenced only by the comparison project, which is never packed, shipped, or built in CI.
