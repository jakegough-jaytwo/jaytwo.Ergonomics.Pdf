# W-92. Check adding an attachment to a signed document

## Problem

W-90 found that on a document with an earlier signature, pyHanko 0.38.0 reports an attachment add as `OTHER` (`Dict keys differ: {..., '/AF', ...}`), because the library also writes the catalog `/AF` array (spec §7.5, W9). Recipients who check signatures with pyHanko would see the earlier signature reported as modified after an attachment is added. This happens with or without `/UR3` and predates W-90. Attachment edits are allowed on a document with approval signatures (spec §7.2) and blocked at every certification level, so this concerns approval signatures and document timestamps.

## Why now

The owner approved this research on 2026-10-20 after the W-90 report.

## Scope and exclusions

- Establish whether `/AF` is the only reason: add an attachment to an approval-signed document with and without the catalog `/AF` entry (the latter built by hand or with another tool) and record pyHanko's modification level and reason for each. Include a document timestamp as the earlier signature, and the corpus file `cms-40b-pyhanko-approved`.
- Check what other available validators report, for example Poppler `pdfsig`, and how other writers (pypdf, qpdf, pyHanko's own embedding helpers) add an embedded file to a signed document, by running them where available or reading their source.
- Record what ISO 32000-1 12.8 and ETSI EN 319 142-1 say about modifications after an approval signature, and whether either treats an embedded-file addition as permitted.
- If pyHanko accepts the add without `/AF`, propose options to the owner in plain business terms, for example: skip `/AF` on signed documents, keep writing it and document the pyHanko verdict, or let the caller choose. Include the effect on PDF/A-3 and e-invoice callers who need `/AF`. Do not choose between them in this item.
- Excluded: behavior changes, and spec, `AGENTS.md`, or `QUALIFICATION.md` edits.

## Acceptance criteria

The cases, each validator's verdict, and the standards' position are recorded in Notes, and either no change is needed or a proposal is in front of the owner.

## Evidence required

pyHanko difference analysis of each case, plus any other validator that is available.

Modification detection is optional, "specified by a signature reference dictionary" (12.8.1, 12.8.2.1). 12.8 sets no limit on later changes for an approval signature without a reference dictionary. Only DocMDP (12.8.2.2, Table 254) and FieldMDP (12.8.2.4, Table 256) restrict changes. DocMDP `P` 2 permits "filling in forms, instantiating page templates, and signing", and `P` 3 adds annotations; neither lists embedded files, which matches the library blocking attachment edits at every certification level (spec §7.2). FieldMDP covers "the values of a list of form fields" only. The one place 12.8 names embedded files is the UR transform (12.8.2.3, Table 255, `/EF`: "Create, Delete, Modify, and Import, which shall permit the user to perform the named operation on named embedded files"), which concerns Reader usage rights, not signatures. So ISO 32000-1 neither permits nor forbids an embedded-file addition after an approval signature; which later changes to accept is the validator's policy.

- 2026-10-20: The question is answered: `/AF` is not the only cause. pyHanko reports any embedded-file addition after a signature as `OTHER`, with or without `/AF`, from every writer tried, because its policy has no rule for the catalog `/Names` or `/AF`. Dropping `/AF` on signed documents would not change its verdict and would cost PDF/A-3 and e-invoice callers. No change to the `/AF` behavior is warranted by this evidence. ## Proposal for the owner

**When it happens.** A customer takes a PDF that someone has already signed or time-stamped and adds an attachment to it with this library, for example a supporting document or an invoice's XML data. The earlier signature stays mathematically intact. A recipient who checks the file with pyHanko, a widely used open-source signature checker, sees that signature reported as followed by a change it does not permit (`OTHER`), and a strict recipient may reject the file. Poppler's checker only says that the signature does not cover the whole file, which it also says after a harmless title change. What Adobe Acrobat says was not checked.

**What we learned.** The suspected cause, the extra associated-file entry (`/AF`) the library writes, is only part of the picture. pyHanko objects to any attachment added after a signature, whether or not that entry is written, and whoever writes it, including pyHanko's own tools and pypdf. qpdf cannot add one without rewriting the file and breaking the signature. Neither the PDF standard (ISO 32000-1) nor the European PAdES standard (ETSI EN 319 142-1) forbids adding an attachment after an approval signature. Each checker decides for itself which later changes to accept, and pyHanko accepts none for attachments.

**Option A: keep the behavior and document it.** Attachments stay allowed after an approval signature or document timestamp, as the specification says today (spec §7.2), with the `/AF` entry written as now. `README.md` and `ACCEPTANCE.md` gain a sentence saying that some checkers, pyHanko among them, report an earlier signature as modified after an attachment is added, and advising callers to add attachments before signing wherever they can: attach the invoice XML, then sign. Cost: a small documentation item. Recipients who use pyHanko still see the warning when a caller adds an attachment after signing.

**Option B: require the caller to opt in.** Treat an attachment added after a signature as flatten and rotate are treated today: refused with `PdfSignatureConflictException` unless the caller sets `AllowBreakingSignatures = true`. Callers then cannot do it by accident. Cost: callers who add attachments to signed files today must change their code, and it needs the owner to change spec §7.2 ("Fills, metadata, attachments, and new signatures stay allowed, as today") and `AGENTS.md` ("On a document with an approval signature, flatten and rotate require the caller's explicit opt-in"). It does not change what any checker reports. And unlike flatten and rotate, an attachment does not change what the signer saw on the page, so the warning would overstate the risk.

**Option C: stop writing `/AF` on signed documents, or let the caller choose.** Not recommended. The evidence shows pyHanko objects just the same without it, so recipients would see no difference. The cost falls on the callers who need `/AF`: PDF/A-3 files and e-invoices such as Factur-X and ZUGFeRD must list the embedded XML in `/AF`, so a signed e-invoice that receives its XML afterwards would no longer meet those formats, and the relationship choice planned under W9 would be silently dropped.

**Recommendation: A.** The behavior matches the standards and the specification. The objection belongs to one checker's policy and applies to every tool, and documenting it, together with "attach before signing", gives callers what they need to avoid it. Choose B only if callers should be stopped from making this change unknowingly. In either case the `/AF` behavior should stay as it is.

**Uncertainty.** Acrobat was not checked. If Acrobat also flags attachments added after an approval signature, that strengthens the case for B; if it accepts them, A is enough.
