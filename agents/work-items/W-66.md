# W-66. Tolerate the writer quirks the corpus shows

## Problem

Reading is strict. Spec R11 and §8 allow a closed, documented list of writer bugs that Acrobat accepts. Which ones matter is decided by the real-world corpus (W-13).

## Why now

Reset plan C2 item 6. It changes the parser, so it lands before the G8 campaign.

## Scope and exclusions

- For each quirk the corpus shows: a local-window handler, a real-world fixture, a test, and a `README.md` entry.
- Excluded: whole-file scans and cross-reference reconstruction. If the corpus shows common files need them, record the evidence and escalate to the owner.

## Acceptance criteria

- Every corpus file that needs a tolerated quirk opens.
- Every quirk is listed in `README.md`.
- No handler reads outside a bounded window.

Refined at activation (2026-10-20). The corpus shows two findings and no other section 8 candidate:

- D1, tolerated writer quirk: a Flate stream whose `/Length` also counts the CR, LF, or CR LF before `endstream` decodes. The Adler-32 is checked at the end of the stream data or, failing that, in front of that marker; the handler looks at the last six bytes of data the decoder already reads. Other trailing bytes and a checksum that matches neither place still throw `PdfParseException`, with a message that names where the checksum was read. The IRS 1040-ES embedded file decodes to pypdf's bytes; one IRS 5500 (Distiller 6.0.1) font program decodes. New `ACCEPTANCE.md` Attachments row; new `README.md` support-matrix row "Writer quirks".
- Q1, defect fix (not a quirk): a name-tree key that is a string but not a text string (ISO 32000-1 7.9.6) does not fail the attachment listing; the attachment is named by `/UF`, then `/F`, opens by that name, and keeps its key bytes on a later attachment edit. The FAA 8710-1 attachment is `FAA_Form_8710-1_.pdf.accreport.html` (qpdf's preferred name), with bytes matching pypdf and the file's `/Params /CheckSum`. An invalid `/UF` still throws. New `ACCEPTANCE.md` Attachments row; `README.md` Attachments row and the `PdfAttachment.Name` XML doc.
- The G2 corpus validates with `attachments: ok` for both files.

Not a write item: plan C4 does not apply. No `ACCEPTANCE.md` row is weakened.

## Evidence required

Corpus fixtures and independent-reader checks: pypdf 6.21.1 and qpdf 12.4.2 through `corpus_probe.py`, Python zlib, and the producer's `/Params /CheckSum`.

## Notes

- 2026-10-20: Created under W-63 from `agents/reference/charter-reset-plan.md` C2.
- 2026-10-20: W-13 left two G2 release blockers for this item, D1 (a false zlib checksum failure when the zlib data ends before `/Length`, IRS 1040-ES) and Q1 (a UTF-16LE name-tree key without a byte-order mark, FAA 8710-1). Details and reproductions: `agents/evidence/qualification/g2-corpus.md`.
- 2026-10-20: Activated and scoped. D1 is the end-of-line marker before `endstream` counted in `/Length` (ISO 32000-1 7.3.8.1 says it shall not be). The decoder cannot learn where .NET's `DeflateStream` stopped reading, so the handler checks two fixed places instead of locating the deflate end. A scan of the corpus found the same shape in 7 Flate streams of `irs-f5500-2005` (fonts, a `/ToUnicode` CMap, page content), none of which the library decodes. Q1 is a legal key: a name-tree key is a string (ISO 32000-1 7.9.6), so the strict text-string decode was the library's defect. Naming by the file specification was chosen over guessing UTF-16LE (pypdf's `accreport.html`) because it needs no encoding heuristic and matches qpdf's preferred name. The other section 8 candidates were checked against every corpus file and do not occur: no bytes after the final `%%EOF` beyond an end-of-line, every `startxref` lands on `xref` or an object, and every `/Length` outside object streams ends at `endstream`. Nothing calls for a whole-file scan, so nothing is escalated.
- 2026-10-20: Spec R11 is still marked Change. `AGENTS.md` has the implementing item mark it Exists, but `docs/spec/` changes only with the owner's approval, so the edit is proposed to the owner rather than made here: in `docs/spec/phase-1.md` section 5, R11 `Change` becomes `Exists`.
- 2026-10-20: The owner approved the R11 status edit; W-84 marks R11 Exists.

## Closeout

Done 2026-10-20 in one commit that activates the item, carries its work, and closes it (D-42). Verification ran on that tree.

- D1, tolerated quirk: `ZlibPayloadStream` keeps the last six bytes of the stream data and `ChecksumMatches` accepts the Adler-32 at the end of the data or in front of a final CR, LF, or CR LF. The failure message is now "The zlib Adler-32 checksum at the end of the stream data does not match the decoded bytes." Listed in the `README.md` support matrix (Writer quirks) with both producers.
- Q1, defect fix: `PdfTextCodec.TryDecode` reports a byte string that is not a text string without throwing, and `WalkNames` keeps the file specification's name (`/UF`, then `/F`) for such a key. `SortKey` still holds the key bytes, so an attachment edit writes them back. `PdfAttachment.Name` documents the rule.
- Corpus: `corpus_probe.py` records qpdf's `preferredname` as `fileName` for each attachment and lets pypdf find the bytes by it when its key lookup fails. The manifest probe facts for the four entries with attachments gain `fileName`, `faa-8710-1` gains pypdf's SHA-256, and both findings' entries record `attachments: ok`. `CorpusTests` expects the file name when qpdf's key carries a NUL. `g2-corpus.md` records the dispositions.
- Tests: `WriterQuirkTests` (19 cases): LF, CR, and CR LF counted in `/Length` decode; a space, a letter, LF LF, LF CR, CR CR, and CR LF LF are refused; a wrong checksum is refused with and without an end-of-line; an xref stream with a counted LF opens; the IRS 1040-ES attachment matches pypdf's SHA-256 (15,003 bytes); an IRS 5500 Distiller 6.0.1 font program decodes to Python zlib's 4,667 bytes; a non-text key takes `/UF`, falls back to `/F`, survives an attachment edit, and an invalid `/UF` still throws; the FAA attachment name and its `/Params /CheckSum` MD5. Against the unchanged source all 19 failed (the six refusals only on the new message), as did the `CorpusTests` read checks for `faa-8710-1` and `irs-f1040es-2026`.
