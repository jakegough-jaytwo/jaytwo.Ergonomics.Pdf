# W-108. Retain cursor windows within an operation and gate source I/O

## Problem

Signing the filled 500-page object-stream form reads 70,035,458 source bytes for a 493,069-byte file, and flattening the 1,000-page form reads 399,321,762 for 974,773 bytes (`agents/evidence/qualification/memory-budgets.md`). W-79 attributed this to re-decoding object streams. D-49's measurement shows about 98% comes from `PdfCursor.Seek`, which discards the 64 KiB window, so the next read refills 64 KiB even when the target is a few hundred bytes already in the discarded window. The multiple is constant from 250 to 4,000 pages, so cost grows linearly, but it is paid in full on SMB or NFS shares and cold disks, which are in scope.

## Why now

D-49 places the change before the 1.0 release checks (W-81). The cursor is beneath every fuzz target and G7 workload, so changing it after W-81 would repeat the release checks.

## Scope and exclusions

- `PdfCursor` keeps its most recently filled 64 KiB windows, least recently used first out, capped at 1 MiB, and serves a seek inside a retained window without I/O. The window count, 4 to 16, is chosen from the measurements and recorded here. A fill stays 64 KiB.
- `ObjectStreamLease` also releases the cursor's retained windows when the public operation returns, normally or by exception. `Open` does not use the lease, so it releases the windows it filled before it returns, including when it throws.
- Within an operation that appends to its own source, a window that ended at the earlier end of the stream is refilled, not taken as end of file.
- Test-visible counters: `ProbeStream` counts read calls; the engine counts decoded bytes, internal and exposed to the test assembly as `RetainedObjectStreamCount` is.
- `LargeWorkloadTests` gates source bytes read, read calls, and decoded bytes for each G7 window with absolute thresholds from the measurements plus headroom. It also gains focused scaling cases, not G7 workloads, for flatten and sign on the G7 form shape at 1,000 and 4,000 pages.
- `CursorWindowTests` covers window reuse, the 1 MiB ceiling on a fixture laid out so every lookup lands in a different 64 KiB region, release at the end of an operation and after a failed one, release between `Open` and the first operation, the end-of-stream case on a same-stream save, and unchanged parse-error offsets.
- `memory-budgets.md` replaces the W-79 explanation of the read multiples and records the new measurements; W-79 gets a dated note pointing to it.
- G8: all eight fuzz targets rerun from the changed code at the campaign's predeclared allocation (120 seconds each, seven workers), recorded under `agents/reports/` and in `status.md`.
- Excluded: any change to object-stream retention (W-109), signing or flatten access order, fill sizes, public API, `README.md`, and the D-20 ceilings and fixture budgets.

## Acceptance criteria

1. On every G7 workload that writes output, and on the new scaling cases, the output file is byte-identical to the output at the base revision, compared by hash in a scratch worktree at the base.
2. In the new focused scaling cases (the G7 form shape at 1,000 and 4,000 pages, not G7 workloads), source bytes read for flatten and sign fall by at least 90% from the base revision. No G7 window reads more bytes, makes more read calls, or decodes more bytes than at the base revision.
3. On the adversarial fixture, the retained windows never exceed 1 MiB and every result matches a cursor that keeps no windows.
4. No byte read in one public operation is served in another, including after an operation that throws, and across the boundary between `Open` and the first operation after it.
5. Parse failures on the regression and fuzz seeds report the same exception types and offsets as at the base revision.
6. Every G7 window stays within its owner-approved fixture budget and D-20 ceiling.
7. `ACCEPTANCE.md` Scale gains a row: on the G7 object-stream form windows, source bytes read, read calls, and decoded bytes stay within the thresholds recorded in `memory-budgets.md`, and a retained cursor window is never served across public operations.
8. The eight fuzz targets reach their allocation with every artifact triaged.

## Evidence required

Release builds. `make g7-workloads` on Windows `net10.0`, `net8.0`, `net6.0`, and `net48`, and in the Linux builder image. Full suite with every external tool present on Windows and `make docker-builder docker-test`. The fuzz rerun under D-23's cap. `qpdf --check` and the existing signature verifiers stay as the independent tools on the G7 outputs.

- 2026-10-22: Window count 8 (512 KiB). On `net10.0` in Release, 16 windows read exactly what 8 read in every measured window; 4 read 2,955,628 bytes against 2,693,484 for the 1,000-page flatten and 10,881,378 against 10,815,842 at 4,000 pages. Sign, extraction, edit, and fill were the same with 4, 8, and 16.
- 2026-10-22: Counter scope. `DecodedByteCount` counts bytes from the cross-reference streams and the streams the engine reads whole (object streams, XMP, and other structural streams). Streaming decodes, such as attachment content, are the caller's reads and are not counted. `PdfStreamDecoder` did not need to change. `PdfDocument.OpenWithCursorWindows` and `CursorPeakRetainedBytes` are internal test seams beside `RetainedObjectStreamCount`.
- 2026-10-22: The first output-hash comparison differed everywhere, at base as well, because qpdf writes a random `/ID`, saves stamp `/ModDate` with the current time, attachments take the current time, and a sign without an `/ID` generates one. The workloads now use `qpdf --deterministic-id`, an explicit `ModificationDate` in the metadata-edit windows, fixed attachment dates, and a fixed `/ID` in the dense fixture. The explicit date is one more public operation in each metadata-edit window, so their counts are higher than W-79's at base and change alike; the 500-page edit threshold was set from that measurement.
- 2026-10-22: The release tests first passed with `Release` disabled, because the next operation refilled a fresh window over the whole small file before reaching the field. The fixture now puts the field's second-revision value beyond a padded first revision, so only the earlier step's window covers it. With `Release` disabled, all three fail.
- 2026-10-22: Observation, no defect. Dense windows allocate 0.4 to 0.9 MiB more than at base, because each public operation fills new windows after the previous operation's are released and the cursor keeps one 64 KiB buffer between operations. It is garbage, not live memory; at most 512 KiB of windows is live. Keeping every buffer between operations would trade that churn for 512 KiB held by each open document; not done.

## Closeout

- `PdfCursor` keeps its eight most recently filled 64 KiB windows, least recently used first out, and serves a seek inside one without I/O. The operation lease releases them when each public operation returns, normally or by exception, and `Open` releases the windows it filled, including when it throws. The length is read on every fill, so a window that ended at an earlier end of the stream is refilled after an append.
- Criterion 1: every G7 output and signed range, and the scaling cases' outputs, matched base by SHA-256 on `net10.0`, `net8.0`, `net6.0`, and `net48`: 44 of 44.
- Criterion 2: flatten source bytes fell 99.3% at 1,000 and 4,000 pages (399,321,720 to 2,693,484; 1,600,653,666 to 10,815,842) and sign 97.8% (139,316,292 to 3,019,015; 555,753,529 to 12,066,873). No G7 window read more bytes, made more read calls, or decoded more bytes than at base; decoded bytes were unchanged everywhere.
- Criterion 3: `CursorWindowTests` on the spread fixture (every object in its own 64 KiB region) peaks at 512 KiB of retained windows, matches a cursor without windows in every walk result and in the saved output, and reads no more; a randomized cursor test matches with 0, 1, 8, and 16 windows.
- Criterion 4: the release tests change the source between steps and see the new value after `Open`, after an operation, and after an operation that throws; with `Release` disabled, all three fail.
- Criterion 5: a scratch walk over 2,996 inputs (107 fixture, seed, and regression files with truncations and byte flips) gave identical results, exception types, offsets, and messages at base and change, 2,976 of them parse exceptions. `CursorWindowTests` checks the same with and without windows on the fixtures and their truncations.
- Criterion 6: every window is within its owner-approved fixture budget and D-20 ceiling on Windows and Linux; the largest are Linux `net6.0` uncollected garbage (82.01 MiB, flatten) and otherwise 22.25 MiB.
- Criterion 7: `ACCEPTANCE.md` Scale has the tripwire row; acceptance-matrix row 90 records it; `memory-budgets.md` has the thresholds and measurements and replaces the W-79 explanation; W-79 has a dated note.
