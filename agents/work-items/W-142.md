# W-142. Workflow pipeline with deferred operations, one editor session, and metadata

## Problem

`jaytwo.Ergonomics.Pdf` contains no source. Stage R2 needs the pipeline that every workflow operation uses. Metadata is its first operation, so this item ships observable behavior and the later items only add operations.

## Scope and exclusions

Implement spec F1 to F4, F7, F11, F12, F14, and F15 (`docs/spec/phase-1.md` section 6.7, D-60). That means `PdfWorkflow.From` and `FromFile`, `PdfWorkflowOpenOptions`, `WithTitle` and `WithMetadata(PdfMetadataChanges)`, `Save`/`SaveAsync` to a stream and to a path with `PdfFileSaveOptions`, `AppendToSource`/`AppendToSourceAsync`, and `PdfWorkflowResult`. F13 here covers `Modified` and `OutputLength`; `FieldAppearances` stays empty until W-143. Update the project `Description`, which still describes the pre-reset single library. In the same commit (D-43), set the rows this item completes to Exists and update `README.md` and `ACCEPTANCE.md`.

Excluded: forms (W-143), attachments and rotation (W-144), form export (W-145), and signing (stage R4). Ergonomics calls only public `jaytwo.Pdf` APIs.

## Acceptance criteria

- F1: `From`, `FromFile`, and operation methods perform no reads on a counting `IPdfSource` or stream. Changing a `PdfMetadataChanges` instance after it is described does not change the output.
- F2: a borrowed input, destination, or source stays open after success, an engine failure, and cancellation. A file opened from a path is closed in each case; the test reopens it with exclusive access.
- F3: a second terminal call throws `InvalidOperationException` after success, after failure, and after cancellation. So does an operation method called after a terminal call has begun. Of two concurrent terminal calls, exactly one runs.
- F4 and F7: a metadata workflow appends one revision, keeps the input as an exact prefix, and inspects the same as the direct-engine edit: the same title, author, subject, keywords, creator, and producer, and one more revision. A property assigned `null` is removed; one not assigned is unchanged.
- F11: a stream save with no operations writes an exact copy, and `AppendToSource` with no operations writes nothing. A non-empty, non-seekable, or non-writable destination is rejected. A destination stream that is the input stream is rejected, which keeps same-source writing to `AppendToSource`. A path save refuses an existing file without `Overwrite` and replaces it with `Overwrite`. A path equal to the input path, after normalization (case-insensitive on Windows), is rejected before the input opens. `AppendToSource` is rejected for an `IPdfSource` input and for a stream input that is not writable.
- F12: an argument error or shape error is thrown before the input opens, with zero reads. An engine failure (for example, `PdfEncryptionRestrictedException` on a restricted file) propagates with its own type. After an engine failure, a stream destination keeps its starting length. A path destination keeps its previous bytes, or stays absent, and no temporary sibling remains.
- F14: each terminal call has a synchronous and an asynchronous form. A cancellation observed during an asynchronous path save leaves no temporary sibling and no published file. The XML docs state that inspection and edits read the source synchronously during an asynchronous run.
- F15: on a large fixture, a metadata workflow reads no more source bytes than the direct-engine edit.
- Alias safety (F11): the tests cover a path that differs from the input only by case (Windows) or by relative segments. For a hard link to the input, they show the publish either fails or replaces the link while the input's bytes stay unchanged.

## Evidence required

Focused `jaytwo.Ergonomics.Pdf.Tests` on net10.0, plus net48 for the file-publish and alias tests (Windows `ReplaceFile`), and `make quiet-build`.
