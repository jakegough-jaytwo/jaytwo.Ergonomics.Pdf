# W-184. Avoid repeated page-list materialization during editing

## Problem

Each numbered workflow rotation calls `PdfWorkflowBuilder.Page`, which obtains `editor.Pages`. That property calls `PdfEngine.ListPages` and creates every `PdfPageEditor`; `PdfPageTree.ListPages` first walks the entire page tree and creates every `PdfPage`. R numbered rotations on P pages therefore repeat the full traversal and wrapper construction R times, including repeated changes to one page. The call path demonstrates unnecessary work; its practical allocation and runtime costs have not yet been measured.

## Scope and exclusions

Measure the current path, then make the smallest behavior-preserving C# refactor behind the existing engine page-access API that avoids repeated full-list materialization during one editor session. Reusing stable semantic page handles is a candidate, subject to lifecycle and memory measurements. Establish existing held-handle behavior before choosing the implementation. Keep workflow replay in declaration order under F5 and F9; page inspection and PDF invariants remain engine-owned.

Preserve lazy inspection, disposal and source-consistency checks, inherited and normalized rotation, save/sign continuation, permissions, certification, signature opt-in, and exact-prefix incremental output. Keep any retained semantic state scoped to the editor and consistent with successful changes. D-49's per-operation source-byte lifetime remains unchanged. Exclude new public APIs, eager loading at document/editor creation, global caches, broader page-tree redesign, workflow operation merging, and additional runtime dependencies. If handle reuse would alter committed semantics, use a narrower optimization or raise the specific conflict before implementation.

## Acceptance criteria

- Repeated numbered rotation/lookups within one editor no longer reconstruct all public page objects and editor handles or walk the full page tree for every lookup. A permanent focused test uses existing engine work counters to detect repeated traversal on a fixed many-page fixture; record before/after allocations separately from wall-clock timing.
- Interleaved absolute, relative, and all-page rotations retain declaration-order results and direct-engine parity. Include repeated edits to the same page and an all-page rotation followed by another numbered rotation.
- Page access stays lazy for workflows that never use pages. Editor/document disposal and a later editor session retain their supported behavior; page handles used around saves do not introduce stale relative rotations.
- Existing inherited rotation, argument refusal, encrypted assembly permission, certification, and signed-document opt-in cases still pass. Refused operations leave pending state/output as required, and a compatible workflow still appends at most one ordinary revision.
- Record the retained-memory cost of any semantic page-list reuse on a many-page fixture. Memory remains tied to the structural working set, no whole-PDF buffering is introduced, and no raw source bytes survive their D-49 operation lease.

## Evidence required

Run focused `PageAccessTests`, `EditorTests`, `PageTests`, and `WorkflowRotationTests` on net10.0, plus the same behavior selection on net48 for the shared engine lifecycle. Build affected target frameworks with StyleCop/XML checks. Record a bounded before/after traversal and allocation comparison using the same fixture and operation sequence; use deterministic work counts for the permanent check, not elapsed-time thresholds. Ergonomics tests continue to use only public APIs. Run `make agents-check`, `graphify update .` after code changes, and staged `make task-check`. No full matrix, fuzz campaign, report, or Docker integration checkpoint is required for this focused item.

## Closeout

`PdfDocumentEditor.Pages` now lists the pages once per editor session and returns the same `PdfPageEditor` handles afterwards (`PdfEngine.CheckDisposed` keeps the disposed-document check on the cached path). Handles stay current because every rotation change goes through them; one editor per document at a time, and a later editor lists afresh and sees pending rotations. No public API change; lazy until first use.

- Before/after on a 50-page fixture, four lookups and rotations: page-node visits 204 before, 51 after (`PageAccessTests`, deterministic work counters; red before the change, green after). Retained cost: one `PdfPageEditor` per page for the editor's lifetime, no source bytes.
- `PageAccessTests`, `PageTests`, `EditorTests` pass on net10.0 and net48 (46 each); `WorkflowRotation` tests pass on net10.0 (6); `jaytwo.Pdf` Release build has no warnings. `graphify update .` run.
