# W-75. Attachment relationship, dates, checksum, compression, and page mode

## Problem

Attachments are always `Unspecified`, carry no dates or checksum, are stored uncompressed, and cannot open the attachments panel (spec R8, W9 to W13).

## Why now

Reset plan C2 item 16.

## Scope and exclusions

- Spec R8 and W9 to W13, including the PDF/A-3 relationship subset and the conformance non-claim in W9.
- `PdfAttachmentOptions` gains `Relationship`, `CreationDate`, `ModificationDate`, `Compress`, and `OpenAttachmentsPanel`. `PdfAttachment` gains `Relationship`, `CreationDate`, and `ModificationDate` (R8).
- `/CheckSum` and the compressed length come from one extra streaming pass over the content at `Add`, because the serializer writes `/Length` before the body. The write pass checks both again, so content that changes between `Add` and the save fails the save instead of publishing a wrong checksum.
- Spec status for R8 and W9 to W13 becomes Exists in the same commit (D-43).
- Excluded: page-level attachment annotations, PDF/A, Factur-X, or ZUGFeRD conformance, reading `/CheckSum` back through the public API (R8 does not list it), and attachment-level async.

## Acceptance criteria

1. W9: `Relationship` writes each of the eight `/AFRelationship` values, `Unspecified` by default. `PdfAttachment.Relationship` reads it; an absent or unknown value reads as `Unspecified`. pypdf 6.21.1 reads the written value. (`ACCEPTANCE.md` Attachments, new bullet.)
2. W10: `/Params` has `/CreationDate` and `/ModDate` (the caller's values, the time of `Add` when omitted) and `/CheckSum`, the MD5 of the uncompressed bytes. pypdf reads the dates and checksum and the checksum matches an MD5 the test computes. `PdfAttachment` reads the dates; a malformed date throws `PdfParseException` only when that property is read. (New bullet.)
3. W11: `Compress = true` writes `/Filter /FlateDecode`. The library, `qpdf --show-attachment` (12.4.2), and pypdf return the original bytes byte for byte, including content above the 32 MiB structural cap. Content is read at most 64 KiB at a time. Default is off. (New bullet.)
4. W12: `OpenAttachmentsPanel = true` sets catalog `/PageMode /UseAttachments`; pypdf reads it and `qpdf --check` passes. (New bullet.)
5. W13: `Remove` documents that the bytes stay in earlier revisions until Phase 2 compaction. (`README.md` Attachments row.)
6. Failure: content that changes length or bytes between `Add` and the save throws `InvalidOperationException` and leaves the source stream and an empty destination unchanged. (New bullet.)
7. C4 encryption: a compressed attachment with dates and checksum round-trips on RC4 and AES files under the user and the owner password; its strings are encrypted, `/Encrypt` and `/ID` are kept, and the original is a prefix. The fill-only refusal stays (row 5).
8. C4 rights: the new options keep `/UR3` when `/EF` grants the write. `OpenAttachmentsPanel` that changes `/PageMode` is a change no UR3 right grants, so it removes `/UR3` on an unsigned document and leaves `/Perms` on a signed one. DocMDP still blocks attachment edits at every `P` level. (Usage-rights bullet.)
9. A PDF/A-3 input with relationship, dates, compression, and the page mode stays at effective version 1.7 (Poppler `pdfinfo`), and qpdf lists its embedded files. (Version bullet.)

## Evidence required

Independent reader: pypdf 6.21.1 and qpdf 12.4.2 for relationship, dates, checksum, page mode, and compressed bytes; Poppler `pdfinfo` for the version. veraPDF is not used, so no PDF/A property is credited.

## Notes

- 2026-10-20: Created under W-63 from `agents/reference/charter-reset-plan.md` C2.
- 2026-10-21: Activated. Criteria refined as above.
- 2026-10-21: Design. `ExternalBody.Read` makes the W10 extra pass at `Add`, after the refusals and before anything is dirtied; it hashes the content and, with `Compress`, counts the zlib output, so the serializer knows `/Length` before the body. `PdfFlateEncoder` fills a 64 KiB buffer before each write, so both passes feed the deflater identical chunks. The save's pass hashes again and compares length and MD5, so changed content fails the save (the existing truncate-on-failure path leaves the destination unchanged) instead of publishing a wrong `/CheckSum` or `/Length`. A deflater given no input emitted no block, which qpdf 12.4.2 flagged ("input stream is complete but output may still be valid"); the encoder now writes the empty final block, and the empty-file test covers it.
- 2026-10-21: Measurement, G7 workload `LargeWorkloadTests.large_attachment_is_added_and_extracted_through_file_streams_within_budget` (256 MiB + 4097 bytes, file streams, Release, net10.0, Windows, one run each). Before (base `ab128f6`): add and save read 268,439,553 source bytes, allocated 0.15 MiB, peak heap growth 0.16 MiB, 0.22 s. After: 536,879,106 bytes (the W10 extra pass), 0.90 MiB allocated, 0.92 MiB peak, 1.18 s; largest read request 65,536 both times; budget 256 MiB. Reopen and extract is unchanged in kind (0.32 MiB, 0.28 s). The time is the second read and the two MD5 passes. Tradeoff kept: the save-time MD5 is what detects content changed after `Add`; dropping it would save one hash pass and could publish a wrong checksum.
- 2026-10-21: Not changed: the fuzz harness lists attachments but does not read the new date properties, which parse lazily. A later fuzz item can add them (`tools/fuzz/` is outside this item).
