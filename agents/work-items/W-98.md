# W-98. Classify a TSA header timeout on net48 under load

## Problem

1. **Summary.** `HttpTimestampAuthority` sometimes lets a header-phase timeout surface on net48 as a `TaskCanceledException` with no inner exception, instead of the documented `TimeoutException` inner exception.
2. **Impact.** `ACCEPTANCE.md` (Sealing) and the XML docs say a header- or body-phase timeout throws `TaskCanceledException` with a `TimeoutException` inner exception on every target. A caller that tells timeouts from cancellation by the inner exception would read this timeout as a cancellation. No file is written either way.
3. **Reproduction.** `SignatureTests.stalled_timestamp_response_headers_still_time_out` (`HttpClient.Timeout` 500 ms, a handler that never answers) failed once on net48 in a Release run of the full suite with all four targets at once (`dotnet test test/jaytwo.Ergonomics.Pdf.Tests -c Release`, GA SDK 10.0.402, 2026-10-21, W-14 working tree over `W-96`, no runtime change). `SignatureTests` alone on net48 then passed 8 of 8 runs. So it shows only under load.
4. **Expected.** `Assert.IsType<TimeoutException>(canceled.InnerException)` holds on every target (`ACCEPTANCE.md`, Sealing; `HttpTimestampAuthority` docs).
5. **Actual.** `Assert.IsType() Failure. Expected: System.TimeoutException. Actual: (null)` at `SignatureTests.cs` line 211, after 525 ms.
6. **Severity.** Medium: a predictable edge-case failure of a documented guarantee, intermittent and timing-dependent.

Likely cause, from `HttpTimestampAuthority.cs`: the library's own deadline (`CreateDeadline`) fires `min(50 ms, Timeout / 10)` before `HttpClient.Timeout`, and only an exception caught after that deadline has fired is rewrapped (`when (... timeout.IsCancellationRequested)`). When the thread pool is busy, `HttpClient`'s own timer can cancel first, and on net48 its `TaskCanceledException` carries no inner exception, so it passes through unwrapped. Not confirmed by a deterministic reproduction.

## Why now

Found by W-14's full-suite run. W-14 did not change runtime code, so this is out of its scope. Queued on 2026-10-23 ahead of W-80 at the owner's direction: it failed on net48 in 2 of 3 loaded full runs during W-120, and the Windows full runs that W-80 and W-81 need as evidence stay unreliable until it is fixed.

## Scope and exclusions

Make the classification independent of which timer fires first, for example by treating a cancellation that `HttpClient.Timeout` caused (the caller's token not canceled and the elapsed time at least the timeout) as a timeout, or by not relying on a fixed lead. Add a deterministic test that makes `HttpClient` cancel first. Excluded: changing the public exception contract.

## Acceptance criteria

The timeout test passes on every target, including under a forced ordering where `HttpClient`'s timer wins, and the full suite with all four targets at once does not show the failure.

## Evidence required

Internally tested on net10.0, net8.0, net6.0, and net48.

- 2026-10-23: Cause confirmed deterministically. An internal constructor takes the factory for the library's deadline source; `header_timeout_is_classified_when_http_client_cancels_before_the_deadline_fires` passes one that never fires, standing in for a deadline callback a loaded thread pool has not run, so `HttpClient.Timeout` (500 ms) cancels the headers first. Against the old classification, with only that seam added: net48 failed with `Assert.IsType() Failure. Expected: System.TimeoutException. Actual: (null)`, the recorded failure; net10.0, net8.0, net6.0, and the `netstandard2.0` lane passed `HttpClient`'s own exception through (`The request was canceled due to the config...`) instead of the library's.
- 2026-10-23: Fix: `ExchangeAsync` also classifies an exception as a timeout when its stopwatch shows the deadline (`HttpClient.Timeout` less `min(50 ms, Timeout / 10)`) has passed, not only when the deadline token is set, so the result no longer depends on which timer callback runs first. `HttpClient`'s timer is armed after the stopwatch starts, so it cannot fire before the clock reaches the deadline, given the lead covers the 15.6 ms tick of .NET Framework timers, which holds from a 160 ms timeout up. No public API, exception type, or message changed.
- 2026-10-23: `make quiet-test TEST_FILTER=FullyQualifiedName~SignatureTests`: 78 of 78 passed on net10.0, net8.0, net6.0, net48, and the lane. `SigningInteropTests` and `AsyncTests`: 82 of 82 on each.
- 2026-10-23: The original reproduction, two rounds: `dotnet test jaytwo.Ergonomics.Pdf.sln -c Release -p:CollectCoverage=false`, all five hosts at once (GA SDK 10.0.402). `stalled_timestamp_response_headers_still_time_out` and the new test passed in all ten host runs. Nine host runs passed 4,392 of 4,392. net6.0 in round 1 passed 4,391: `caller_cancellation_aborts_a_timestamp_body_that_ignores_the_token` took 3:11.7 against its 2-minute bound. That test cancels through the caller's token at 500 ms, which the first catch handles, and the clock check applies only after its 5-minute deadline, so this change does not reach it. Recorded as W-121.
- Limitation: a `CancelPendingRequests` call, or another failure, that lands after the deadline has passed by the clock but before either timer callback runs is reported as a timeout. The request had already run out its time, so this is the documented timeout, not unrelated cancellation reclassified early.

## Closeout

Done. A header timeout on net48 surfaced without its `TimeoutException` inner exception when `HttpClient`'s timer callback ran before the library's deadline callback, which a loaded thread pool allows. The library now also classifies by its own clock, so the documented `TaskCanceledException` with a `TimeoutException` inner exception holds whichever timer fires first. A deterministic test forces that order and failed on every host before the fix. No public API, `ACCEPTANCE.md`, or `README.md` change: both already state this behavior. Remaining: the limitation in Notes, and W-121.
