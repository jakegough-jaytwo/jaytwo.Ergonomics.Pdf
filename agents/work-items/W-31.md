# W-31. Cap the timestamp response size

## Problem

The W-29 review (`agents/reports/2026-10-18-tech-lead-B-29-review.md`, section 4) observed this from the code. It was not executed. `HttpTimestampAuthority.GetTimeStampToken` copies the whole HTTP response body into a `MemoryStream` with no size cap, so a hostile or broken timestamp server can make the library buffer a body of any size. This predates W-29.

## Why now

The charter says memory follows the working set of the operation. A token larger than the 8 MiB signature appendix cannot be embedded anyway. G8 stays unpassed.

## Scope and exclusions

Bound the response read in `HttpTimestampAuthority.cs`, with a regression test. The cap must be no larger than the 8 MiB signature appendix; the Technical Lead sets the exact value. No public API change and no new option. No change to TSA status, nonce, imprint, or digest-algorithm handling. Do not add TSA trust validation. Do not pass G8. Does not replace W-18.

## Acceptance criteria

A timestamp response body larger than the cap throws `PdfTimestampException` after reading at most the cap plus one buffer, and does not extend the file. A response within the cap still produces a token, per the `HttpTimestampAuthority` row in `ACCEPTANCE.md`. `QUALIFICATION.md` section 10. G8 is not passed.

## Evidence required

Internally tested. Not a gate pass.

## Notes

- 2026-10-19: Materialized from B-31 under W-60. Original entry: `agents/state/backlog.md` at `B-31`. Closed entry: `agents/state/backlog.md` at `B-31`. The role reports named here were removed under D-35; W-55 records their removal, and their pre-removal state is [squashed].
- 2026-10-18: The board set the cap at 2 MiB, under the 8 MiB appendix and above the 1 MiB embedding ceiling, with a read limit of 2,179,072 bytes. The first review returned the change: the library's token had replaced `HttpClient`'s own timeout exception, and the body read on .NET Framework could ignore the token. The rework restored `TaskCanceledException` with a `TimeoutException` inner exception for both phases, and disposes the response on timeout.

## Closeout

Accepted as the bounded fix, at the internally tested level. G8 is not passed. `HttpTimestampAuthority` sends with `ResponseHeadersRead`, reads the body in 81,920-byte chunks, and throws `PdfTimestampException` ("larger than") before the total passes 2,097,152 bytes. It refuses a declared `Content-Length` over the cap before opening the body. The body read stays under `HttpClient.Timeout`, and the caller's `HttpClient` is not mutated. `SignatureTests` passed 37/37 on `net8.0` and on `net6.0`. A 16 MiB body is refused after at most 2,179,072 bytes, a declared oversize after 0 bytes, and through `Sign` the stream bytes stay unchanged. A body of exactly 2,097,152 bytes returns its token, and one byte more is refused. Before the fix, 4 size tests failed on both frameworks, reading 16,777,216 bytes; before the rework, both timeout tests failed. The four library targets built in Release with 0 warnings and 0 errors. `README.md` and `ACCEPTANCE.md` each gained one sentence on the cap, and no criterion was weakened. Limitations: the .NET Framework abort by disposing the response was implemented but not tested (W-33 later added that test). Peak memory is the 2 MiB buffer plus its `ToArray` copy. A connection error after the timeout fires is reported as a timeout. The full suite was not run, and this is not the fuzz run.
