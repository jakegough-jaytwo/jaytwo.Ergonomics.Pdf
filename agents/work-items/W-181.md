# W-181. Refresh R4 signing interoperability and CMS campaign evidence

## Problem

Historical signing evidence predates the final project/editor/workflow model. W-104's deterministic CMS smoke is not a campaign, and W-18's completed campaign did not directly target the CMS reader.

## Scope and exclusions

Refresh direct-engine and workflow signing/timestamp evidence, then run the existing bounded fuzz infrastructure with direct CMS coverage and RFC 3161 coverage against the final code. Add only missing evidence tests for distinct risks. Preserve the historical W-18 record; write a new campaign record and current evidence inventory. No product change, broad security audit, new algorithm/profile, production-qualification claim, packaging work, or protected-document edit. Record findings as follow-up work items and complete any required fixes before accepting evidence; rerun affected checks after fixes.

## Acceptance criteria

- pyHanko and Poppler pdfsig establish the named signature integrity, revision coverage, explicit-test-anchor trust and modification-policy results for direct and ergonomic outputs. Cover the existing supported RSA/ECDSA, digest, format, encrypted-input, certification and failure guarantees without reducing the existing matrix.
- OpenSSL and pyHanko check signature timestamps and separate document timestamps. Include new/existing fields, permitted later revisions retaining earlier signature bytes, tamper controls and refusal cases. Incorporate W-103's DSS classifications with profile, cryptographic and trust results separate.
- Measure representative large workflow input and large attachment staging in Release with coverage off, recording environment, managed-memory/buffer observations and disk use. Confirm no whole-document managed buffering and exact source-prefix preservation; distinguish staging disk costs from memory bounds.
- Deterministic smoke/regression replay passes before the campaign. Run `make docker-fuzz-campaign FUZZ_WORKERS=1 "FUZZ_TARGETS=cms:3600 tsr:3600"` through the existing runner (two aggregate CPU-hours planned, within D-23's 24-hour ceiling), retaining the existing 10-second, 2048 MiB RSS and 64 KiB fragment input limits. The CMS target exercises ordinary and document-timestamp modes; record which paths/seeds are reached rather than inferring coverage from elapsed time.
- Record the tested revision, harness/tool versions, seed-corpus hashes, exact invocation, campaign duration and execution count, timeout/resource limits, and finding dispositions. Report incomplete runs explicitly. Also record tree state, framework/build and seed inventory. Every confirmed finding is minimized, reproduced and gets a permanent regression test and disposition; rerun from fixed code when needed. Controlled rejection is not signature verification, and a smoke/campaign run is not an independent security review.

## Evidence required

Use the applicable signing-matrix, change-verification and fuzz-qualification skills. Run focused categorized signing/interop/large-data tests on net10.0, the fixed-seed smoke, and the bounded campaign with its report. Record reusable evidence under `agents/evidence/` and the campaign under `agents/reports/`. Full framework and Docker integration are W-182's checkpoint. Run `make agents-check` and staged `make task-check`.
