# W-186. Centralize object-store checkpoint state

## Problem

`PdfObjectStore` owns the object backup, but `PdfFormFiller.Fill`, `PdfFlattener.Flatten`, and `PdfSigner.SignAsync` separately capture store-owned checkpoint values and supply five arguments to `Restore`. Fill and flatten pass current information/trailer values while signing passes saved values. Understanding restoration therefore requires knowing which store state each caller can change. The duplicated coordination is demonstrated; the review did not establish a current restoration defect.

## Scope and exclusions

Make the smallest behavior-preserving C# refactor that lets the existing store backup mechanism capture and restore the store-owned state currently supplied to `Restore`: size, information-object identity/generation, trailer ID, and dirty IDs, together with the existing per-object backups. Keep checkpoint creation, successful completion, and restoration concrete and internal. Leave appearance state with form appearances and signature state with the write gate; their operation-specific restoration remains explicit.

Preserve all-or-nothing fill and flatten, signing failure behavior, pre-existing pending edits, successful continuation, object allocation and cache restoration, source ownership, D-49 operation leases, and exact output bytes. Physical destination restoration remains separate and retains W-151's original-failure and restoration-diagnostic guarantees. Exclude a general transaction framework, nested transactions, new public APIs, broader rollback coverage or guarantees, source/destination redesign, and runtime dependencies. If centralizing the captured values exposes a behavior difference, establish and report it before changing committed semantics.

## Acceptance criteria

- Fill, flatten, and signing no longer capture or pass the store-owned values listed above; the existing store checkpoint mechanism owns their capture and restoration in one implementation.
- Failures after mutation begins restore the operation's changes while preserving edits already pending at checkpoint creation. New allocations and dirty/cache state retain the existing restoration behavior.
- Appearance and signature helper state restores as before. A failed operation can be followed by a successful supported operation and save/sign without stale helper state or leaked checkpoint state.
- Successful operations retain their edits, clear their checkpoint, and permit subsequent operations. Editor disposal/reopening retains the supported pending-edit semantics.
- Exception types and identity, signing cancellation, destination restoration diagnostics, permissions, certification, and source consistency remain unchanged. Representative fill, flatten, and signing output is byte-identical to the baseline under deterministic inputs.
- The result removes duplicated checkpoint coordination without adding a transaction hierarchy or changing state ownership outside this seam.

## Evidence required

Before editing, apply `csharp-refactoring` and load `pdf-core-change`, `pdf-acroform-change`, and `pdf-signing-change` for the affected state and operations. Use `pdf-change-verification` for verification. Run focused checkpoint, `FormDataTests`, `FlattenTests`, `SignatureTests`, `SigningRollbackTests`, and `EditorTests` on net10.0, plus the restoration/continuation selection on net48 for the shared failure lifecycle. Reuse existing fault injection and add only missing distinct cases, including pre-existing pending edits and failure after mutation begins for each caller. Run the relevant deterministic output-identity cases and build affected targets with StyleCop/XML checks. Record the commands and outcomes in Closeout. Run `make agents-check`, `graphify update .` after code changes, and staged `make task-check`. No full framework matrix, independent-tool sweep, fuzz campaign, qualification update, report, or Docker integration checkpoint is required for this focused refactor.
