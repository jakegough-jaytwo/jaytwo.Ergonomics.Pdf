# W-141. Propose the R2 workflow requirements and API shape

## Problem

Reset stage R2 (`reset-plan.md` section 8) builds `jaytwo.Ergonomics.Pdf` workflows, but `docs/spec/` has no workflow requirements: `phase-1.md` section 1 says only that the Phase 1 capabilities gain workflows in R2, and the `PdfWorkflow` shapes in `reset-plan.md` section 4.2 and `reset.md` are illustrative. Workflow behavior can ship only against owner-approved requirements, so W-142 to W-145 cannot be scoped until those exist.

## Scope and exclusions

Write `agents/reference/r2-workflow-proposal.md` for the owner. It contains the proposed requirement rows for `docs/spec/phase-1.md` (status New) and the choices a decision record will hold. For each choice, give the options and a recommendation. Settle:

1. **Entry and ownership.** `PdfWorkflow.From` overloads for `Stream`, file path, and `IPdfSource`; the password; borrowed versus owned input; and the rule that `From` and operation descriptions neither open nor read the source.
2. **Output.** Terminal operations for a stream and a file path; whether the workflow offers a same-stream append to its input; the file convenience's commit (temporary sibling then replace, `reset-plan.md` section 4.4); destination capability requirements; and what a run returns, such as fill dispositions (`NeedsViewer`).
3. **Operations.** Fill (single and bulk), flatten (all or named), metadata (information keys and XMP), attachment add (stream and file path) and remove, and page rotation. For each, name what it adds over the engine call: composition, a default, validation, ordering, or convenience (`reset-plan.md` section 13). Drop any operation that would only rename an engine call.
4. **Ordering and conflicts.** Whether execution order is canonical or follows the calls (for example, fills before flatten), and how each repeated or contradictory target is handled: a field filled after it is flattened, an attachment added and removed under one name, a page rotated twice, a metadata key set twice. Each is rejected before output or resolved by a stated rule.
5. **Validation and failure.** Map each check to the three failure classes in `reset-plan.md` section 4.4: before the source opens, after it opens but before the destination is written, and during output. State the exception model, so a task-level error keeps the engine's failure category visible (the engine exception type, or an inner exception) rather than replacing it.
6. **Signed documents.** How the caller opts in to `PdfDocumentEditor.AllowBreakingSignatures` for flatten and rotation.
7. **Sync and async.** Which terminal operations exist synchronously under spec W20, given that inspection still reads the source synchronously until W-138.
8. **Read shortcuts.** Candidates such as exporting form values from a path, each with the caller code it removes. Keep only those that remove real ceremony.
9. **Reuse.** Whether one workflow description can run against several inputs, as in filling one template many times.

Include a side-by-side of caller code, direct engine versus workflow, for each common task. This is the evidence for the R2 exit criterion that workflows are shorter and add real defaults or safeguards.

After the owner approves the wording, record the choices as a decision, add the approved rows to `docs/spec/phase-1.md`, and refine the acceptance criteria of W-142 to W-145 to match. Exclusions: implementation, signing in the workflow (stage R4), assembly workflows (stage R3), and any change to engine behavior. If an operation needs an engine change, record it as a separate item.

## Acceptance criteria

- The proposal answers each of the nine questions with options and a recommendation.
- After the owner chooses, the decision is `accepted`, `phase-1.md` carries the approved rows with status New, and W-142 to W-145 have concrete acceptance criteria.

## Evidence required

The proposal and the owner's recorded approval. No build or test run.
