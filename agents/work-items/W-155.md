# W-155. Decide encryption interoperability edge cases

## Problem

Several reported encryption edge cases lack specification-backed expected behavior or independent-producer fixtures: R6 Unicode passwords and a proposed raw-UTF-8 fallback, R5/R6 `/U` and `/O` lengths, R2 through R4 password encodings, R4 `/Length` defaults, explicit per-stream `/Crypt` filters, AES empty strings, and direct trailer `/Info` dictionaries.

## Scope and exclusions

Research each case against the applicable PDF standard and independently produced files, then classify it as conforming behavior, confirmed defect, deliberately unsupported valid variant, malformed input, or unjustified tolerance. Do not add password fallbacks, malformed-file tolerances, or implementation fixes in this item.

## Acceptance criteria

- Each listed edge case has a cited expected behavior and at least one suitable fixture or an explicit explanation of why an independent fixture cannot be produced.
- Results are checked across the supported runtime families where encoding or cryptography behavior may differ.
- Confirmed defects and deliberately unsupported valid variants receive separate implementation or documentation work items with narrow scope.
- Any choice that changes supported algorithms, tolerance policy, or an encryption guarantee is presented to the owner as a decision before implementation.

## Evidence required

A case-by-case matrix naming the standard basis, producer/tool and version, fixture shape, observed library behavior, runtime results, and disposition.

#### Case-by-case starting points

**1. R6 Unicode passwords and the proposed raw-UTF-8 fallback**
- Standard: 7.6.4.1 requires SASLPrep (RFC 4013, stringprep RFC 3454, Normalize and BiDi options), then UTF-8, then truncation to the first 127 bytes. 7.6.4.3.3 and 7.6.4.4 then use that UTF-8 password. R5 is "shall not be used" in PDF 2.0 (Table 21); it is Adobe's extension level 3 and does no SASLPrep.
- Code: `PdfSecurity.PrepareRevision6` (about line 732) maps non-ASCII spaces and mapped-to-nothing characters, applies NFKC, runs `ValidatePrepared` (prohibited characters and the RandALCat/LCat rule), then `TruncateUtf8` (line 764, trims back to a code-point boundary). Prohibited input throws `InvalidRevision6Password()` rather than falling back. `PrepareRevision5` is raw UTF-8 plus truncation, which matches R5.
- Existing tests: `revision6_accepts_the_nfkc_form_of_the_password`, `revision5_truncates_the_password_to_127_bytes`, `password_round_trips_strings_streams_and_the_prefix`.
- Questions to settle: (a) .NET `FormKC` follows the current Unicode version, while RFC 4013 pins Unicode 3.2; do characters assigned after 3.2 produce a different result or fail `ValidatePrepared`, and which wins? (b) Does truncating at a code-point boundary differ from truncating at exactly 127 bytes in other implementations, which would mean a different key for long non-ASCII passwords? The spec text says "first 127 bytes" with no boundary rule. (c) The fallback: a raw-UTF-8 retry after SASLPrep fails would accept files written by producers that skipped SASLPrep. That is a password-acceptance policy change, so it goes to the owner as a decision (criterion 4), not into this item. Record which producers need it. **Unverified**: qpdf is believed to try more than one password representation on R5/R6 open; read qpdf's encryption source or documentation before citing that.
- Fixtures to try: qpdf `--encrypt <user> <owner> 256` with a password containing a precomposed and a decomposed accent, a compatibility character (for example a ligature or full-width digit), a non-breaking space, and a soft hyphen; pypdf `encrypt(..., algorithm="AES-256")`; compare which libraries open each file with the NFC, NFKC, and raw forms.

**2. R5/R6 `/U` and `/O` lengths**
- Standard: Table 21 says 32 bytes for R4 and earlier and 48 bytes for R6 (hash 32, validation salt 8, key salt 8). `OE` and `UE` are 32 bytes and `Perms` is 16.
- Code: `ReadBytes(encrypt, key, minimum)` (line 1334) enforces only a minimum: 48 for `O` and `U` in R5/R6, 32 for `OE` and `UE`, 16 for `Perms`, 32 for legacy `O` and `U`. Longer values are accepted and the prefix is used. `ValidatePerms` (line 706) is stricter and requires `Perms.Length == 16`.
- Gap against the charter: accepting longer-than-spec values is a tolerance, and `AGENTS.md` says tolerated quirks are a closed list, each with a real-world fixture, test, and `README.md` entry (spec §8). I found no `O`/`U` length entry in `docs/spec/phase-1.md` by keyword search; confirm by reading §8 directly. If none exists the current behavior is an unlisted tolerance: either justify and list it with a fixture, or tighten it.
- **Unverified**: some R5/R6 writers are said to pad `O` and `U` to 127 bytes. If a real producer does this, that is the fixture to produce. If none can be produced, say so explicitly (criterion 1) and classify as unjustified tolerance.
- Also check legacy shorter-than-32 and exactly-32 behavior against Algorithms 4 to 7 (a short `/U` may be a truncated 16-byte check in R3 and R4 files, because only the first 16 bytes are compared there; see ISO 32000-1 7.6.3.4 Algorithm 5 and `UserMatches` at line 439).

**3. R2 to R4 password encodings**
- Standard: Algorithm 2 step a (ISO 32000-2 7.6.4.3.2, 32000-1 7.6.3.3): convert to PDFDocEncoding (Unicode input goes through a codepage first), then pad or truncate to 32 bytes with the fixed 32-byte padding string; an empty password becomes the padding string. 7.6.4.4.1 repeats that R4-and-earlier passwords are limited to PDFDocEncoding characters.
- Code: `CreateLegacy` (line 397) uses `PdfTextCodec.EncodePdfDoc`, which throws `PdfEncryptedException` with `PasswordRejected` for any character not in PDFDocEncoding (see `PdfTextCodec.cs:117`). `PadPassword` (line 589) truncates to 32 bytes.
- Question: PDFDocEncoding and Latin-1/WinAnsi differ in `0x18` to `0x1F`, `0x80` to `0xA0`, and the euro sign (`0xA0` in PDFDocEncoding, `0x80` in WinAnsi). A producer that maps the password through Latin-1 or WinAnsi would produce a different key for those characters. A password with a character outside PDFDocEncoding is reported as a rejected password, not as "cannot be represented"; decide whether that error reason is right (criterion: typed failure vs wrong password).
- Fixtures: qpdf 40/128-bit and AES-128 with passwords `caf\u00e9`, `\u20ac100`, a bullet, and a 40-character password (truncation); pypdf RC4/AES-128; check whether each producer's key matches PDFDocEncoding, Latin-1, or UTF-8. Existing coverage: `empty_revision4_user_password_opens`, `rc4_round_trips_strings_streams_and_the_prefix`, `qpdf-encrypted.pdf`. None covers non-ASCII legacy passwords.

**4. R4 `/Length` defaults**
- Standard: Table 20 `Length` is "Optional; only if V is 2 or 3", in bits, multiple of 8, 40 to 128, default 40. For V 4 the key length comes from the crypt filter dictionary; Table 25 `Length` is required in 32000-2 (optional in 32000-1) and, per errata #184, the standard security handler writes it in bytes (16 or 32), though files exist with bits (128 or 256). AESV2 requires 128 bits, AESV3 requires 256.
- Code: `CreateRevision4` (line 306) rejects a top-level `/Length` other than 128 with `Unsupported()` and ignores its absence. `ReadFilter` (line 1223) accepts a crypt-filter `/Length` of either the byte count or eight times the byte count and accepts its absence. `CreateRevision3` defaults the key to 40 bits when `/Length` is absent, and rejects `CF`, `StmF`, `StrF`, `EFF` presence with `Unsupported()`.
- Cases to settle: top-level `/Length 16` on V4; crypt-filter `/Length` missing (spec 2: required; 1: optional); crypt-filter `/Length` that disagrees with the method (RC4 `V2` with `/Length 128` in a filter, AESV2 with `/Length 16` vs `128`); V4 with `V2` method and key length other than 128; `/Length` of the wrong type (`ValidateOptionalTypes` already makes that malformed). Classify each as conforming, tolerated, or unsupported and list any tolerance in spec §8.
- Existing tests: `revision4_can_mix_aes_strings_with_rc4_streams`, `revision4_rc4_stream_decrypts_beside_an_aes_string`, `unsupported_handlers_are_refused`, and `HardeningTests.omitted_string_or_stream_crypt_filter_defaults_to_identity`.

**5. Explicit per-stream `/Crypt` filters (strongest defect lead)**
- Standard: 7.6.6 and Table 20 `StmF`: all streams use the default stream filter except cross-reference streams and streams with a `Crypt` entry in their `Filter` array. The `DecodeParms` entry carries `/Name`; a missing name means `Identity`. Table 25 `AuthEvent` `EFOpen` marks embedded-file crypt filters. A `Crypt` filter has to be first in the `Filter` array (7.4.10; confirm the wording).
- Code: `PdfSecurity.CipherFor(PdfObject.Dict)` (line 926) chooses the cipher only from the object number and `/Type`: encrypt dictionary none, `XRef` none, `Metadata` per `EncryptMetadata`, `EmbeddedFile` via `EFF`, everything else the default stream cipher. It does not read the stream's `/Filter` or `/DecodeParms`. The only `/Crypt` handling I found is in the assembly path, `PdfTypedObjectCopier.cs:118` to `129`, which feeds `OpenAssemblyStream` (line 247).
- Suspected defect, to confirm with a fixture: a stream such as `<< /Filter [/Crypt] /DecodeParms [<< /Name /Identity >>] >>` with no `/Type /Metadata` is stored in the clear, but the ordinary read path would still decrypt it with the default cipher and return garbage. The same applies to a named non-default filter. A file where `EncryptMetadata` is false but the metadata stream carries `/Crypt /Identity` instead of the `/Type /Metadata` rule is the common real-world shape, so check which of the two this library actually follows. Also check the write side: appended revisions that rewrite such a stream must keep its crypt choice.
- Fixture routes: qpdf `--encrypt ... --encrypt-metadata=n` and `--stream-data`/`--decode-level` options, then inspect with `qpdf --show-object` and `--json`; or build one by hand with `StandardEncryptor`. Compare with `mutool` and `pdftotext` for independent opening.
- Existing tests: `clear_metadata_and_identity_attachments_are_not_encrypted` (shape unknown, read it before assuming it covers explicit `/Crypt`), `object_stream_strings_are_plaintext_inside_the_encrypted_stream`.

**6. AES empty strings (and empty streams)**
- Standard: 7.6.3.1 and errata #542: padding is always present, so an empty AES string encrypts to a 16-byte IV plus one 16-byte block of `0x10`, 32 bytes total. Strings and streams both.
- Code: `DecryptBytes` (line 985) rejects any AES input shorter than 32 bytes or not a multiple of 16 with `PdfParseException(0, "Encrypted data is truncated.")`. `OpenAssemblyStream` reads 16 IV bytes and reports a truncated stream if fewer are present.
- Question: how should a zero-length string `()` or `<>` in an AES document, a 16-byte (IV only) value, or a stream with no bytes behave? Strictly these are malformed. Some writers are reported to emit empty strings unencrypted; **unverified**, check qpdf, pdf.js, and pdfium behavior before citing. Decide between malformed input and a listed tolerance; check that the error is a typed malformed-encryption or parse failure and does not throw `CryptographicException` raw. Also confirm the round trip: `Encrypt(...)` must write 32 bytes for an empty string.
- Fixtures: qpdf-encrypted AES-128 and AES-256 files with `/Title ()`, an empty form value, and an empty attachment; hand-built variants with a zero-length and a 16-byte value.

**7. Direct trailer `/Info` dictionaries**
- Standard: Table 15 says `Info` is "Optional; shall be an indirect reference" (ISO 32000-1 same). Encryption (7.6.3.2 step a) says a direct string uses the identifier of the indirect object containing it. A trailer dictionary is not an indirect object, so a direct `/Info` in a classic trailer has no defined object key. In a cross-reference-stream file the trailer dictionary is the stream object's dictionary, which is an indirect object but is itself never encrypted.
- Code: `PdfDocumentLoader.TakeTrailer` (lines 198 to 220) accepts `trailer.Get("Info") is PdfObject.Dict` as `_store.InlineInfo`, and `DecryptStrings(encryptedInline)` (line 192) decrypts it using `value.ObjectNumber` and `value.Generation` of that dictionary. Check what those are for a trailer dictionary; probably 0 and 0, which has no spec basis. `PdfInfoMetadata.cs` (lines 214 and 236) reads and rewrites inline info.
- Classification candidate: malformed input (spec violation) that the library tolerates. If a real producer writes it, it needs the spec §8 treatment (fixture, test, README line) and a defined decryption rule; if not, consider rejecting or ignoring it in encrypted documents. Also decide behavior on write: the editor drops the inline form when it rewrites metadata (`InlineInfo = null` at line 237), which is worth a regression check in an encrypted file.
- Fixtures: hand-built classic-trailer file with a direct `/Info` in plaintext and encrypted forms; search for a real producer before concluding none exists.
