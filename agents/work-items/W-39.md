# W-39. FieldMDP Include and Exclude follow ISO 32000 (audit SA-08)

## Problem

Audit finding SA-08 (Medium): the code and `README.md` treated `Include` as allowing the named fields and `Exclude` as blocking them. ISO 32000 FieldMDP is the reverse: `Include` locks the named fields, and `Exclude` locks every field except them. Acceptance covered only `All`.

## Why now

It is a defect in a documented certification guarantee. Correcting it changes documented certification behavior, so it needed the owner's confirmation, which D-24 gave.

## Scope and exclusions

The FieldMDP gate in `PdfEngine.cs`, the AcroForm tests, `README.md`, and `ACCEPTANCE.md`. `All` stays unchanged.

## Acceptance criteria

The behavior follows ISO 32000. `README.md` and `ACCEPTANCE.md` are corrected. A PDF-aware tool independently verifies both the `Include` and the `Exclude` outcomes.

## Evidence required

Independently validated.

## Closeout

Accepted under D-24 at the independently validated level. FieldMDP follows ISO 32000-1 12.8.2.4: `Include` locks the named fields, and `Exclude` locks every field except them. A named field covers its descendants, as pyHanko applies it. An unknown `/Action` locks every field. The README had the rule reversed since genesis, and the code followed it. Both are corrected, along with `ACCEPTANCE.md`. pyHanko 0.38.0 confirms that the library locks the same fields under five lock specifications, and that each fill it allows keeps the original signature intact with `docmdp_ok` and `FORM_FILLING`. QA added the FieldMDP and DocMDP-plus-FieldMDP theories, the pyHanko interop test, a `fieldmdp` mode in `certify_samples.py`, and a per-field lock check in `validate_signature.py`. Limitation (Low): `Include` with no `/Fields` locks nothing. Reports: `agents/reports/2026-10-19-qa-engineer-B-39.md` and `2026-10-19-tech-lead-B-39-review.md`. Completed 2026-10-19.
