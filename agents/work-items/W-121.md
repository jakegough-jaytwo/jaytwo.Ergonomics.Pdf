# W-121. Time the remaining HTTP timestamp tests on the library's task, not the xUnit resumption

## Problem

1. **Summary.** `SignatureTests.caller_cancellation_aborts_a_timestamp_body_that_ignores_the_token` bounds the time from the start of the call to the test's resumption after `await Assert.ThrowsAsync(...)` at 2 minutes. Under a loaded full run it overran that bound.
2. **Impact.** If the delay is the test host's, as W-120 found for the header-phase test, Windows full runs and the Docker gate go red intermittently with no library defect. If it is the library's, a caller who cancels a stalled body waits minutes. No file is written either way.
3. **Reproduction.** 2026-10-23, W-98 working tree: `dotnet test jaytwo.Ergonomics.Pdf.sln -c Release -p:CollectCoverage=false`, all five hosts at once, round 1 of 2: net6.0 failed it at 3:11.7 (`Assert.InRange() Failure`). The other nine host runs passed. W-77 recorded it at 2:05.8 on net10.0 under the same load (acceptance-matrix footnote e16).
4. **Expected.** The body abort follows promptly after the caller's 500 ms cancellation (`ACCEPTANCE.md`, Sealing: a body that ignores the token is aborted by disposing the response).
5. **Actual.** 3:11.7 against a 2-minute bound.
6. **Severity.** Medium until the cause is known.

Likely cause, not confirmed: the one W-120 measured. The test resumes on xUnit 2.4.1's `MaxConcurrencySyncContext`, which waits for one of its eight test threads, so the stopwatch includes that wait. The `stalled_timestamp_*` tests in `SignatureTests` take their elapsed time the same way: `stalled_timestamp_response_body_still_times_out` overran its 10 s bound in a W-77 Docker run (11.35 s), and `stalled_timestamp_response_headers_still_time_out` failed in W-120's loaded net48 runs without a captured message.

## Why now

Found by W-98's full run. It makes the Windows full runs that W-80 and W-81 need as evidence unreliable, as W-98 did. Not queued.

## Scope and exclusions

Confirm where the time goes, for example with the probes W-120 used. If it is the test host, take the elapsed time in an `ExecuteSynchronously` continuation of the library's task, as W-120 did, in this test and in the `stalled_timestamp_*` tests that time the same way. If it is the library, fix the library. Excluded: W-98's classification, and widening any bound without a measured cause.

## Acceptance criteria

The cause is recorded, and these tests pass in repeated loaded full runs on every host, with their bounds still failing a library that is late.

## Evidence required

Internally tested, with the cause recorded.

They used W-98's reproduction: three rounds of `dotnet test jaytwo.Ergonomics.Pdf.sln -c Release --no-build -p:CollectCoverage=false`, with all five hosts at once on 8 cores. Each probe recorded, from the start of the call, when the caller's token fired, when the body stream was disposed, when the library's task completed (an `ExecuteSynchronously` continuation), when the test method resumed, and the thread-pool counts.
  - Results: 6 failures in 15 host runs. `caller_cancellation_aborts_a_timestamp_body_that_ignores_the_token` overran its 2-minute bound 4 times (net6.0 2:16 and 2:40, net10.0 3:04, net48 2:16). `caller_cancellation_of_timestamp_headers_is_not_reported_as_a_timeout` overran its 10 s bound on net10.0 and net6.0 in round 1 (11.9 s each). That test already timed the library's task under W-120.
  - In all 15 runs of the 2-minute test, the stream was disposed and the library's task completed within 5 ms of the caller's token firing. The test method resumed up to 183 s after the start. In 12 of the 15 runs it was still waiting when the stream's own 30 s fallback fired. The library's part was never late. The time went to the test waiting for one of xUnit 2.4.1's eight `MaxConcurrencySyncContext` threads, as W-120 found.
  - A second delay is the thread pool's. The caller's 500 ms `CancellationTokenSource` timer fired as late as 7,046 ms on net6.0 and 3,362 ms on net10.0. The 500 ms `HttpClient` timeouts completed the library's task as late as 5,632 ms. Up to 12 work items were queued with 9 or 10 pool threads. Timer callbacks and the library's `ConfigureAwait(false)` continuations both wait in that queue, which other tests in the same process keep busy. That fits W-120's test overrunning by about 2 s, but it was not probed in that run. No library code blocks: it awaits and registers callbacks only.
  - So timing on the library's task removes the first delay but not the second. In-process isolation removes both.
- 2026-10-23: Fix, test only. Every bounded test now takes the elapsed time in an `ExecuteSynchronously` continuation of the library's task.

Before this, a library that never disposed the response still passed, because the stream fails on its own after 30 s. W-69 had widened this bound from 10 s to 2 minutes and blamed the abort continuation; these probes show that delay was the test's resumption.

## Closeout

Done. Two delays from the test host caused the overruns, and neither was the library's. The 2-minute test's elapsed time included waiting up to 183 s for an xUnit test thread to resume it, although the library finished within 5 ms of the cancellation. The library's own continuations and the caller's timer also waited in a thread pool that the other tests in the same process kept busy (up to about 7 s). The HTTP timeout and cancellation tests now run in a non-parallel xUnit collection and take the elapsed time on the library's task. The bounds are 10 s throughout, and an assertion now catches a missing body abort that the old 2-minute bound let through. Remaining: other timing ceilings in the suite, such as the `HardeningTests` scan ceiling in footnote e16, still run in parallel and are outside this item.
