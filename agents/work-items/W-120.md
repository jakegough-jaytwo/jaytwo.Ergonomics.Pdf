# W-120. Caller cancellation of timestamp headers is seen late on the netstandard2.0 build

## Problem

1. **Summary.** `SignatureTests.caller_cancellation_of_timestamp_headers_is_not_reported_as_a_timeout` asserts that a stalled header phase ends within 10 seconds of the caller's cancellation. On the library's `netstandard2.0` build, run as part of the full suite, it ends at about the 30-second `HttpClient.Timeout` and the handler's 30-second stall instead. The exception is still correct, an `OperationCanceledException` for the caller's token; only the elapsed time fails.
2. **Impact.** If the library causes it, a caller of the `netstandard2.0` build (every .NET Framework consumer) who cancels a timestamp request waits until the configured timeout, against the cancellation behavior `ACCEPTANCE.md` (Sealing) describes. If the test host causes it, the W-119 `netstandard2.0` lane is red in `make docker-builder docker-test` and Jenkins until the test is fixed. No file is written either way.
3. **Reproduction.** 2026-10-22, W-119 working tree, no runtime change:
   - `test/jaytwo.Ergonomics.Pdf.NetStandard.Tests` (the test sources on net8.0 against the `netstandard2.0` build), full suite, alone: failed 2 of 2 on Windows (36.7 s, 29.2 s) and 1 of 1 in Docker (33.3 s).
   - The same lane in a five-host Windows run: failed (12.7 s). net48 in that run: failed (50.6 s).
   - `SignatureTests` alone on that lane and on net48: passed 3 of 3 each.
   - The net10.0, net8.0, and net6.0 builds of the library: passed in every run, in Docker and on Windows.
   So it needs the `netstandard2.0` build and the rest of the suite in the same process.
4. **Expected.** The header wait ends promptly after the caller cancels, on every build (`ACCEPTANCE.md`, Sealing; `HttpTimestampAuthority` docs).
5. **Actual.** `Assert.InRange() Failure. Range: (00:00:00 - 00:00:10)` at `SignatureTests.cs` line 262.
6. **Severity.** Medium until the cause is known: a possible failure of a documented guarantee on every .NET Framework consumer, and a red checkpoint gate.

`HttpTimestampAuthority.ExchangeAsync` passes a token linked to the caller's straight to `HttpClient.SendAsync` and has no framework-specific code. The two library builds differ only in `PdfAppendixBuffer.Write(ReadOnlySpan<byte>)`, the number parse in `PdfParser`, the `IsExternalInit` polyfill, and the `netstandard2.0` dependency packages. A likely cause is thread-pool starvation in the test process, from work that blocks pool threads only on this build, which delays the cancellation continuation until the stall ends. Not confirmed. W-98, a net48 timestamp timeout classification failure under load, may share the cause.

## Why now

Found by W-119's new `netstandard2.0` lane, which is red until this is fixed. Queue it before the next integration checkpoint.

## Scope and exclusions

Find what delays the cancellation, for example by recording thread-pool counts and when the handler's `Task.Delay` is canceled, and by bisecting the suite for the tests that must run alongside. Fix the library if it blocks or misses the token; fix the test or the blocking test code if the delay is the host's. Excluded: the W-98 timeout classification, unless the cause is shared.

## Acceptance criteria

The full `netstandard2.0` lane and net48 pass this test in repeated runs, and a test or recorded measurement shows that the caller's cancellation ends the header wait promptly on the `netstandard2.0` build.

## Evidence required

Internally tested, with the cause recorded.

## Notes

- 2026-10-23: Activated. Cause found with temporary timing probes (since removed) in the test, over five full `netstandard2.0` lane runs on Windows (`dotnet test test/jaytwo.Ergonomics.Pdf.NetStandard.Tests -p:CollectCoverage=false`). Each probe recorded, from the caller's `Cancel()`: when the handler's `Task.Delay` was canceled, when the library's `GetTimeStampTokenAsync` task completed, when the test's `Record.ExceptionAsync` task completed, and the thread-pool counts.

  | Run | Lane result | Handler canceled | Library task done | Test's task done | Pool threads / queued at cancel |
  | --- | --- | --- | --- | --- | --- |
  | 1 | passed | 3 ms | not probed | 6,522 ms | 19 / 0 |
  | 2 | passed | 490 ms | 493 ms | 493 ms | 17 / 7 |
  | 3 | failed | 4 ms | 5 ms | 44,232 ms | 9 / 0 |
  | 4 | failed | 3 ms | 5 ms | 29,244 ms | 7 / 0 |
  | 5 | passed | 2 ms | 4 ms | 119 ms | 19 / 0 |

  The library ends the header wait within 5 ms of the caller's cancellation even in the failing runs, and the thread pool was not starved. The delay was the test host's: the test wrapped the call in `Record.ExceptionAsync(async () => await ...)`, whose lambda resumes on xUnit 2.4.1's `MaxConcurrencySyncContext`. That context runs continuations only on its eight test threads, so the lambda waited for other tests to free one. The stopwatch measured that wait. Not a library defect, and not shared with W-98, which is a timer race in the library's classification.
- 2026-10-23: Fix: the test now takes the elapsed time in an `ExecuteSynchronously` continuation of the library's own task. The assertions on the exception are unchanged. A temporary mutation that awaited 15 s in `ExchangeAsync` before rethrowing the caller's cancellation failed the test at 15.0 s against the 10 s bound (net10.0), so the bound still catches late cancellation in the library. Reverted.
- 2026-10-23: `make quiet-test TEST_FILTER=FullyQualifiedName~SignatureTests`: 77 of 77 passed on net10.0, net8.0, net6.0, net48, and the `netstandard2.0` lane.
- 2026-10-23: Three rounds of the full `netstandard2.0` lane and the full net48 suite run side by side (`--no-build -p:CollectCoverage=false`): this test passed in all six runs. The lane passed 4,391 of 4,391 each round. net48 passed 4,391 of 4,391 in round 1 and 4,390 of 4,391 in rounds 2 and 3; the one failure each time was `stalled_timestamp_response_headers_still_time_out` (2 s, 530 ms), W-98's test, outside this item. Recorded in W-98.

## Closeout

Done. The caller's cancellation ends the header wait within 5 ms on the `netstandard2.0` build; the 10 s overruns were the test waiting for an xUnit test thread after the library had already finished. The test now times the library's own task, so it measures the guarantee rather than the test host. No runtime, `ACCEPTANCE.md`, or `README.md` change: the documented behavior was already met. Remaining: `caller_cancellation_aborts_a_timestamp_body_that_ignores_the_token` and the `stalled_*` tests still time through the test method's resumption; they have wide or met bounds and have not failed for this reason, so they were left unchanged.

2026-10-23 addendum: the closeout's remark that the other timing tests "have not failed for this reason" was wrong. `caller_cancellation_aborts_a_timestamp_body_that_ignores_the_token` overran its 2-minute bound in W-77 (2:05.8) and in W-98's loaded Release run (3:11.7); the cause is not yet confirmed. Recorded as W-121.
