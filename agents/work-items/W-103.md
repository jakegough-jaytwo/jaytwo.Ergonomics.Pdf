# W-103. Validate PAdES output with EU DSS in the Docker tests

## Problem

W-71 shipped PAdES baseline B-B and B-T. No ETSI conformance checker has classified the output. pyHanko 0.38.0 and `pdfsig` show that the signature is intact, valid, and trusted, and that it is `ETSI.CAdES.detached`. Neither classifies the profile level. The profile evidence is an EN 319 142-1 6.3 checklist in `test/jaytwo.Ergonomics.Pdf.Tests/Fixtures/validate_signature.py`. This repository wrote it, so it encodes our own reading of the standard (W-71 Notes). It does accept pyHanko's own PAdES signature and reject its `adbe.pkcs7.detached` one.

EU DSS (Digital Signature Service) is the European Commission's open-source Java library for creating and validating AdES signatures, and it is the reference implementation EU trust services use. Its ETSI validation report names the detected signature format (`PAdES-BASELINE-B`, `PAdES-BASELINE-T`, and so on) and its indication.

## Why now

The owner said on 2026-10-21 that it may be worth having in the Docker tests, but that it is not urgent. It becomes more valuable with PAdES B-LT and B-LTA in 1.x, where DSS checks the revocation and long-term validation data that a hand-written checklist covers poorly. Schedule it before `QUALIFICATION.md` G4 is claimed for PAdES, or with the 1.x long-term validation work, whichever comes first.

## Scope and exclusions

- A test-only tool, like pyHanko and `pdfsig`. It is never a runtime dependency.
- Add a JDK and a pinned DSS release to the `base` stage of the `Dockerfile`, and document a Windows install in the tool-path notes.
- Add a small Java wrapper. DSS has no simple CLI, so the wrapper validates one PDF with an explicit test trust anchor (and a TSA root for B-T) and prints the detected signature format, the indication, and the subindication.
- Find it through `ExternalTool.Locate` with a `JAYTWO_*` variable. Do not hard-code paths or `.exe` names.
- Run it in the existing PAdES interop tests (`pyhanko_and_pdfsig_accept_pades_baseline_b_for_every_key_and_digest`, `pyhanko_and_pdfsig_accept_pades_baseline_t_with_an_openssl_timestamp`, and the PAdES rows of the encrypted-input test) beside pyHanko and `pdfsig`, or in a sibling test class if the JVM start-up cost is better paid once.
- Excluded: revocation checking and trust in real roots (out of charter); B-LT and B-LTA output (1.x); replacing the pyHanko checklist, which stays as a fast check.
- Alternative if CI wiring proves too costly: a one-off run through the EC's hosted DSS demo validator on a B-B and a B-T sample made with test keys, recorded in `agents/evidence/`. That evidence is point-in-time, not CI, and it sends the samples to an external service.

## Acceptance criteria

- DSS reports `PAdES-BASELINE-B` for library B-B output for RSA 2048, P-256, and P-384 with SHA-256, SHA-384, and SHA-512, with indication `TOTAL_PASSED` (or the documented subindication that a self-issued test root produces, recorded as such) under the test trust anchor.
- DSS reports `PAdES-BASELINE-T` for B-T output with the OpenSSL test authority's token.
- DSS reports `PAdES-BASELINE-B` for B-B on qpdf-encrypted input signed under the owner and the user password, or the item records that DSS cannot open encrypted PDFs.
- `make docker-builder docker-test` installs the tool and runs these checks on Linux. A missing tool fails the tests, as `AGENTS.md` requires for required tools.
- Any disagreement between DSS and the `validate_signature.py` checklist is recorded as a defect against the library or the checklist, not suppressed.

Plan C4 does not apply: this item adds no write.

## Evidence required

Independently validated by EU DSS: record its version, the JDK version, and the reported format and indication for each case in `agents/evidence/acceptance-matrix.md` row 59 and `agents/evidence/qualification/g4-pdfsig.md` (or a new G4 record for DSS).
