# W-103. Classify R4 PAdES output with pinned EU DSS

## Problem

W-71 shipped PAdES B-B and B-T, but the existing pyHanko/pdfsig evidence and repository-authored attribute checklist do not provide independent baseline-profile classification. The final engine and ergonomic paths need that evidence under D-64. The engine already selects ETSI.CAdES.detached and the PAdES attribute set when requested; its legacy default is not a demonstrated profile defect.

## Scope and exclusions

- Integrate pinned test-only EU DSS and a compatible pinned JDK through the Docker base stage and Windows test-tool installer after W-179 adopts the exact authorization wording. Use the common locator and its approved overrides, never hard-coded executable paths. No runtime dependency.
- Build a small wrapper that retains original validator reports and emits signature identity, detected profile/level, cryptographic/digest results, timestamp results, and indication/subindication separately. Verify the pinned release's actual API/report fields and standard/policy edition against primary documentation; do not rely on the external review's citation placeholders or assumed field spellings.
- Validate direct-engine and W-180 workflow output using explicit local test CA/TSA anchors, validation time and policy. Disable unintended public-network retrieval. Keep the existing fast checklist and pyHanko/pdfsig checks.
- Exclude real-root trust services, runtime validation, B-LT/B-LTA, new profiles/algorithms, and changing expected classification to conceal an output defect. A hosted validator is supplementary only and cannot replace the adopted reproducible pinned-tool requirement; no external submission is authorized by this item.

## Acceptance criteria

- DSS independently classifies B-B for RSA 2048, ECDSA P-256 and P-384, each with SHA-256/384/512, and B-T with an OpenSSL-authority signature timestamp. Exercise both direct-engine and workflow-produced output, reusing fixtures rather than manufacturing redundant combinations.
- Assert classification separately from CMS/PDF cryptographic results and policy indication. Seek TOTAL_PASSED under the explicit test configuration; retain any self-issued-root subindication verbatim as a separate result. An INDETERMINATE indication is not relabeled a validation pass merely because the root is synthetic.
- B-B on qpdf-encrypted owner/user inputs is classified and verified where supported. Record a DSS limitation with exact tool version and diagnostics when unsupported; it is not a pass and does not waive the existing encrypted pyHanko/pdfsig evidence.
- Negative controls distinguish a valid legacy basic signature from PAdES, B-B from B-T, a modified signed byte, corrupt signature, and a mismatched timestamp. Classifier/verifier disagreements become defects with disposition, never suppressed expectations.
- Linux Docker tests and Windows focused interop tests locate and execute the pinned tool; a missing required tool fails. Run the tool-install integration gate from a separate worktree.

## Evidence required

Run focused PAdES interop tests on net10.0 on Windows and Linux, plus `make docker-builder docker-test` for this tool-install integration checkpoint from a separate worktree. Save reports and update the acceptance evidence inventory and a DSS G4 record under agents/evidence/. Record fixture hashes, producing commit, DSS/JDK/OS versions, policy identifier/hash and standard edition, signature identity, algorithms, expected/actual classification, crypto and timestamp results, trust inputs/time, indication/subindication, execution status and report checksums. Distinguish pass, fail, not-run and unsupported. This produces R4 evidence, not a release-gate or production-qualification claim. Run `make agents-check` and staged `make task-check`.
