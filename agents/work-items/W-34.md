# W-34. Header-phase timestamp timeout lacks TimeoutException on .NET Framework

## Problem

On `net48`, `SignatureTests.stalled_timestamp_response_headers_still_time_out` fails: the `TaskCanceledException` has no `TimeoutException` inner exception. `HttpTimestampAuthority` left the header phase to `HttpClient`'s own timeout exception, and only .NET 5 and later add the inner exception. W-31 claimed the same exception shape for both phases. The timeout itself works.

## Why now

The regression test already existed and failed on `net48`, so the full suite was red on .NET Framework.

## Scope and exclusions

Make the header-phase timeout produce `TaskCanceledException` with a `TimeoutException` inner exception on every framework. Change only `HttpTimestampAuthority`. No public API change.

## Acceptance criteria

`stalled_timestamp_response_headers_still_time_out` passes on `net48`, `net6.0`, and `net8.0`, and the other stall tests still pass.

## Evidence required

Internally tested.

## Closeout

Accepted at the internally tested level. `HttpTimestampAuthority` owns one deadline for the header and body phases. It passes the owned deadline token to `HttpClient.SendAsync`, resolves the .NET Framework timer race deterministically, and normalizes only owned-deadline failures. On `net48`, `net6.0`, and `net8.0`, a timeout in either phase is `TaskCanceledException` with a `TimeoutException` inner exception, and unrelated cancellation is not reclassified. `stalled_timestamp_response_headers_still_time_out` now passes on `net48`.
