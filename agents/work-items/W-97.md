# W-97. Encrypt the signature dictionary strings other than /Contents in an encrypted file

## Problem

1. **Summary.** In a password-encrypted file, `Sign` writes the signature dictionary's text strings, `/M`, `/Reason`, `/Location`, `/ContactInfo`, and `/Name` (`PdfEngine.CreateSignatureDictionary`), in plaintext, as `AGENTS.md` ("Leave signature dictionaries plaintext") and `docs/spec/phase-1.md` §7 ("Signature dictionaries stay plaintext") require. Other readers decrypt those strings with the document key, as they do every string in the file, and get garbage. Only `/Contents` is read as plaintext by them.
2. **Impact.** The signature itself verifies. But a reader that shows the signing time, reason, location, contact, or signer name from the dictionary shows garbage or nothing for every signature the library adds to an encrypted file. `pdfsig` crashes on such a file when the CMS signing time is missing or at the Unix epoch, because it then falls back to `/M`.
3. **Reproduction.** Sign `test/jaytwo.Ergonomics.Pdf.Tests/Fixtures/qpdf-encrypted.pdf` (AES-256, revision 6, user password `user-secret`) through `PdfDocument.Open(stream, "user-secret")` and `Sign` with `SigningTime` set, then read the signature dictionary with pypdf 6.21.1 (`PdfReader`, `decrypt("user-secret")`), or run `pdfsig -upw user-secret` (Poppler 26.08.0).
4. **Expected.** ISO 32000-1 7.6.1 applies encryption to all strings and streams in the file. Its exceptions are the trailer `/ID`, strings in the encryption dictionary, and strings inside encrypted streams; it names no exception for a signature dictionary. In practice `/Contents` is exempt, because it is written into a gap reserved before signing: Poppler (merge request 718, "Don't decrypt the Contents field of Sig dictionaries") and pyHanko exempt only `/Contents`. pyHanko 0.38.0, signing the same fixture incrementally, writes `/M` and `/Reason` as AES ciphertext and `/Contents` in plaintext, and `pdfsig` 26.08.0 accepts its output.
5. **Actual.** pypdf 6.21.1 reads `/M` of the library's output as an empty string ("Ignoring padding error: Invalid padding bytes.") and `/Contents` as garbage. `pdfsig` 26.08.0 exempts `/Contents` and verifies the signature (`Signature is Valid.`), and takes the signing time from the CMS. With a CMS signing time at the Unix epoch it falls back to `/M`, decrypts it, and exits with an access violation (Windows 0xC0000005, MSYS2 build) before printing a report, in 12 of 12 samples. With a current signing time it does not read `/M`, 6 of 6 pass. The same crash occurs on an unencrypted file whose `/M` is replaced by bytes that are not a date, so the crash is a `pdfsig` robustness defect; the garbage `/M` it reads is the library's.
6. **Severity.** High: a supported operation (signing an encrypted file) writes strings other readers cannot read, and one independent verifier crashes on the output. It is not a false signature guarantee: the signature value and byte range verify in pyHanko and `pdfsig`.

Not checked: Adobe Acrobat or Reader.

## Why now

Found by W-14 while adding `pdfsig` as the second verifier. The current behavior is required by `AGENTS.md` and the spec, so changing it is the owner's decision. Not queued.

## Scope and exclusions

Options for the owner:

- **A. Encrypt every signature dictionary string except `/Contents`.** The signature dictionary is then written like every other new object, with `/Contents` left as the reserved hex string. Needs the owner to change `AGENTS.md` ("Leave signature dictionaries plaintext") and spec §7 ("Signature dictionaries stay plaintext") to "Leave the signature `/Contents` plaintext". The `/ByteRange` covers the encrypted strings, so their length must be known before the digest, which it is: the cipher and the string are known when the dictionary is written. `EncryptionTests.signature_dictionary_stays_plaintext` and `ACCEPTANCE.md` and `README.md` change with it.
- **B. Keep the behavior and document it.** `README.md` and `ACCEPTANCE.md` state that on an encrypted file the signing time, reason, location, contact, and signer name in the signature dictionary are not readable by other tools, and that the CMS signing time is the reliable one.

Recommendation: A. It matches ISO 32000-1, pyHanko, and Poppler, and costs one encryption call per string. The plaintext rule appears to have been meant for `/Contents`.

Excluded: the `pdfsig` crash itself, which is Poppler's to fix; a report upstream is optional.

## Acceptance criteria

- Under A: after `Sign` on an encrypted file, pypdf reads `/M`, `/Reason`, `/Location`, `/ContactInfo`, and `/Name` as the values passed, `/Contents` stays plaintext hex, pyHanko and `pdfsig` verify the signature, and `pdfsig` accepts it with a CMS signing time at the Unix epoch. The W-14 test signs the encrypted case at the epoch again.
- Under B: the documentation states the limitation, and no criterion is weakened.

## Evidence required

pypdf 6.21.1 reads of the dictionary strings; pyHanko 0.38.0 and `pdfsig` verification of encrypted signed output.

## Closeout

Done 2026-10-21 under option A (D-46). In an encrypted file the signature `/Contents` is the only plaintext string: `Sign` encrypts `/M`, `/Reason`, `/Location`, `/ContactInfo`, and `/Name` with the document's string cipher under the signature object's number and generation, and the reader decrypts every string of an existing signature dictionary except `/Contents`. A dictionary the library writes again, such as a direct `/UR3` in a changed catalog, is encrypted again with its `/Contents` untouched. The document-timestamp dictionary writes no text strings, and its `/Contents` stays the plaintext reserved hex (`EncryptionTests.document_timestamp_contents_stays_plaintext`, revisions 3 and 6). `PdfSecurity.IsSignatureContents` is the one test, used by `PdfSecurity.Apply` and `PdfSerializer.WriteValue`. `ACCEPTANCE.md` (encryption on write) and `README.md` (encryption bullet and support-matrix row) describe it; no criterion was weakened.
