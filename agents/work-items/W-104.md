# W-104. Fuzz the CMS signature reader directly

## Problem

W-72 added `CmsSignatureReader`, which parses untrusted CMS from every signature `/Contents` that `PdfDocument.Signatures` reads. That includes BER indefinite lengths, which it tolerates as a writer quirk. The only fuzz coverage is the `open` target's read walk, which mutates whole PDFs. A mutation rarely lands inside a `/Contents` hex string and still leaves the file parseable, so the reader's lengths, nesting, attribute, certificate-matching, and time paths get little coverage. The `der` target exercises `DerCodec`, a different, strict-DER reader that inspection does not use.

The current seeds also miss the most important real-world input. `SeedWriter.SignatureContents` matches only `/Contents <` with a space and reads only the top-level test fixtures. So the GPO bill's Acrobat BER CMS (`/Contents<3080...` in `Fixtures/corpus/`) and the two pyHanko corpus signatures are not seeds.

W-72 ran a throwaway mutation check: 300,000 byte mutations of three real CMS values, 49,751 parsed, 250,249 `PdfParseException`, no other exception. That run was not committed or repeatable, and it is not G8 evidence.

## Why now

D-64 retains this direct parser target for R4. W-18's campaign completed on 2026-10-22 without it; that historical record is not reopened. W-181 owns a fresh bounded campaign after this target and the workflow implementation are stable.

## Scope and exclusions

- A `cms` target in `tools/fuzz/FuzzTargets.cs` that calls `CmsSignatureReader.Read` on the input, once as a CMS signature and once as a document timestamp, and catches only `PdfException`. Input length is at most 64 KiB, as for the other fragment targets.
- Seeds in `SeedWriter`:
  - the `/Contents` of every signed test fixture and signed corpus file, with or without a space before `<`;
  - the GPO BER CMS;
  - a library-made CMS in both formats;
  - a CMS with an RFC 3161 signature-time-stamp token, and a document-timestamp token;
  - a CMS whose signer is named by subject key identifier;
  - the same CMS re-encoded with indefinite lengths.

  The token seeds come from `tools/fuzz/external-seeds.sh` where OpenSSL is needed.
- Add `cms:60` to the default `FUZZ_TARGETS` in the `Makefile`. The smoke run picks the target up from the target list.
- W-179 adopts the exact owner-approved `cms` row in `.agents/skills/pdf-fuzz-qualification/references/targets.md` before this item implements it. Keep the existing `open` signature-field walk. Target description:

  | `cms` | `CmsSignatureReader.Read` on the input as a CMS signature and as an `ETSI.RFC3161` token | BER and DER lengths and indefinite-length nesting, ContentInfo and SignedData structure, certificate set, SignerInfo, signed and unsigned attributes, signing-time and genTime parsing, issuer-serial and subject-key-identifier matching | `PdfException` | `/Contents` of the signed fixtures and corpus files, library CMS in both formats, OpenSSL time-stamp tokens, indefinite-length re-encodings |

- A confirmed finding becomes a deterministic test in `test/jaytwo.Pdf.Tests` and a minimized seed in `tools/fuzz/regressions/cms/`.
- Excluded: the fresh campaign and its record, which belong to W-181; changes to the reader's accepted inputs to make a mutation parse; changes to the `der` target.

## Acceptance criteria

- `make fuzz-smoke` runs `cms` over every seed and 2000 deterministic mutations with no uncontrolled failure, locally and in `make docker-builder docker-test`.
- The seed list for `cms` includes the GPO BER CMS, both pyHanko corpus signatures, and at least one CMS with a signature-time-stamp token and one document-timestamp token. A test or an assertion in the harness fails if the GPO seed is missing.
- `references/targets.md` lists `cms` with the wording the owner approved, and the harness and the table agree.
- Each confirmed finding, if any, has a regression test and a disposition, as `pdf-fuzz-qualification` requires. A finding in the reader is fixed in `src/jaytwo.Pdf/Signatures/CmsSignatureReader.cs` without widening what it accepts.

Plan C4 does not apply: this item adds no write.
