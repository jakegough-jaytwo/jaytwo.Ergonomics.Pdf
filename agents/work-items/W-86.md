# W-86. Order attachment name-tree keys the way readers expect

## Problem

W-67 observed it on a real corpus file. The IRS 2026 Form 1040-ES (`irs-f1040es-2026`) keys its one embedded file `Press Quality(1).joboptions` as a UTF-16BE string (`<feff0050...>`). Adding an attachment named `usage-rights.txt` and saving incrementally makes `qpdf --check` (12.4.2) exit 3 with "Name/Number tree node: keys are not sorted in validate". `WriteAttachments` sorts the flattened `/EmbeddedFiles` keys by their raw bytes, so the PDFDocEncoded `usage-rights.txt` (0x75) goes before the UTF-16BE key (0xFE). qpdf compares keys as text, so it expects `Press...` first.

Reproduction: open `corpus/irs-f1040es-2026.pdf`, call `Attachments.Add("usage-rights.txt", content)`, call `SaveIncremental(destination)`, then run `qpdf --check` on the destination.

The behavior predates W-67, which does not change how keys are ordered. A name that sorts first both ways, such as `Attachment.txt`, checks clean. That is the name `UsageRightsTests` uses.

## Why now

Attachment edits on real files should pass the G2 `qpdf --check` bar. W-75 changes attachment writing (spec R8 and W9 to W13). The ordering rule should be settled before that work or as part of it.

## Scope and exclusions

- Find out which key order ISO 32000-1 7.9.6 requires when one tree mixes PDFDocEncoded and UTF-16BE keys, and how Acrobat, qpdf, pypdf, and pdf.js look keys up.
- Write new keys so that the tree is ordered under that rule. One option is to encode a new key the way the tree's existing keys are encoded.
- Excluded: rewriting keys that the library does not add, beyond what the ordering requires.

## Acceptance criteria

Refine these when the item becomes active. At minimum, after the reproduction above, `qpdf --check` passes with no warnings and every reader still finds both attachments by name.

Refined at activation (2026-10-20):

- The rule is ISO 32000-1 7.9.6, unchanged in substance in ISO 32000-2 7.9.6 by the ISO-approved PDF Association issue 214 correction: `/Names` keys are in ascending order compared byte by byte, a shorter key before a longer one with the same leading bytes, and the keys use one self-consistent encoding. The written order stays the library's byte order (`CompareBytes`); the defect is the mixed encoding.
- Keys the tree already holds keep their bytes, including a key that is not a text string (W-66), and a replaced attachment keeps the key the tree held. Any other key (a new attachment, or a file listed only in `/AF` that the rewrite adds to the tree) is UTF-16BE with a byte-order mark when the tree holds no keys or only UTF-16BE keys, and otherwise PDFDocEncoded when every character has a code and the bytes do not begin like a byte-order mark, else UTF-16BE.
- The reproduction above passes `qpdf --check` with no warnings; `qpdf --show-attachment` returns both files; pypdf reads both, with the original file's bytes unchanged and the added bytes as written; the library lists and opens both; the original is a prefix.
- The Reader-extended corpus attachment test in `UsageRightsTests` adds `usage-rights.txt` instead of `Attachment.txt`, so the six forms are checked with a name that exposed the defect.
- Unit regression tests: a UTF-16BE tree takes a UTF-16BE key; a new tree is UTF-16BE; a PDFDocEncoded tree takes a PDFDocEncoded key and a replacement keeps its key; an `/AF`-only file takes the tree encoding; the documented limitation below.
- Documented limitation, not fixed: a name that PDFDocEncoding cannot hold, added to a tree with PDFDocEncoded keys, is UTF-16BE and sorts after them by bytes. Making that tree consistent would re-encode keys the library did not add.
- New `ACCEPTANCE.md` Attachments row; `README.md` Attachments support-matrix row.

## Evidence required

The 1040-ES corpus file, qpdf 12.4.2, and pypdf.

## Notes

- 2026-10-20: Created under W-67 from its corpus attachment test. Queue placement is the owner's decision.
- 2026-10-20: The owner queued it first, ahead of W-68.
- 2026-10-20: Activated and scoped. Findings. ISO 32000-1 7.9.6 (Adobe's PDF32000_2008 copy, read with Poppler `pdftotext`): keys "shall be sorted lexically in ascending order by key. Shorter keys shall appear before longer ones beginning with the same byte sequence. Any encoding of the keys may be used as long as it is self-consistent; keys shall be compared for equality on a simple byte-by-byte basis." ISO 32000-2 7.9.6 has the same text; the PDF Association errata (pdf-issues.pdfa.org, issue 214, ISO-approved) deletes "lexical(ly)" and changes nothing else. In the issue 214 thread, Adobe's representative describes Acrobat's comparison as a raw-byte compare over the shorter length (memcmp), and the TWG names the producer bug: the per-string "PDFDocEncoding if possible, otherwise UTF-16BE" choice must not be used for name-tree keys, because it mixes encodings. Independent readers: qpdf 12.4.2 (`libqpdf/NNTree.cc`) compares keys by `getUTF8Value()`, the decoded text, for `--check` validation, for binary-search lookup, and for insert, and repairs an unsorted tree in memory with a warning. pypdf 6.21.1 (`generic/_files.py`) reads `/EmbeddedFiles` in order without searching, and inserts by bisecting the decoded text as UTF-8. pdf.js (v5.4.296 `name_number_tree.js`, `catalog.js`) lists attachments with `getAll()` and binary-searches raw byte strings in `get()`. In a single-encoding UTF-16BE tree, byte order and qpdf's text order agree except between a character above U+FFFF and one in U+E000 to U+FFFF; in a single-encoding PDFDocEncoded tree, they agree except at codes 0x18 to 0x1F and 0x80 to 0xA0, which map above U+00FF. Reproduced before the fix: the 1040-ES with `usage-rights.txt` gives `qpdf --check` exit 3 ("keys are not sorted in validate"), and `--list-attachments` and both `--show-attachment` lookups exit 3 with the same warning but succeed after qpdf's repair; pypdf reads both files. The library also mixed encodings on its own trees: `PdfTextCodec.Encode` writes printable ASCII as a literal and anything else as UTF-16BE, so `z.txt` and then `Bericht Ä.txt` gave `[(z.txt) <FEFF...>]`; a hand-built file with exactly those keys makes `qpdf --check` exit 3 ("keys are not sorted"), and the same file keyed `[<FEFF...Bericht Ä.txt> <FEFF...z.txt>]`, as the fix writes it, exits 0. The regression test `new_name_tree_is_keyed_in_utf16be` failed on the old code.
- 2026-10-20 (after closeout): The owner accepted the documented limitation and declined re-encoding existing keys. Writers checked by source reading: PDFBox 3.0 and qpdf order by decoded text and PDFBox chooses each key's encoding separately; iText orders by decoded text for new keys and raw bytes for keys it read; none re-encodes a tree to one encoding. Corpus producers with attachments (LibreOffice 26.8, Antenna House 6.6, Adobe PDF Library 15.0) all key in two-byte encodings, even for ASCII names.

## Closeout

Done 2026-10-20 in one commit that activates the item, carries its work, and closes it (D-42). Verification ran on that tree.

- Implementation: `PdfEngine.WriteAttachments` gives every key the tree does not already hold the tree's encoding before it sorts by bytes: UTF-16BE (`PdfTextCodec.EncodeUtf16Be`) when the tree holds no keys or only UTF-16BE keys, otherwise `PdfTextCodec.EncodePdfDocOrUtf16Be`. `AttachmentSlot.KeyInTree` marks keys read from the name tree, and `AddAttachment` reuses a replaced attachment's key. The byte comparison (`CompareBytes`) is unchanged, because ISO 32000-1 7.9.6 already requires it. The file specification's `/F` and `/UF` are written as before.
- Behavior change: a new name tree is now keyed in UTF-16BE (before, printable ASCII names were literal strings); a replaced attachment keeps its old key bytes (before, the key was re-encoded from the name); a non-ASCII name with PDFDocEncoding codes in a PDFDocEncoded tree is PDFDocEncoded (before, UTF-16BE); a file listed only in `/AF` takes the tree encoding when the rewrite adds it to the tree (before, its `/UF` or `/F` bytes). Attachment listing order follows the new key bytes.
- Tests: `AttachmentTests` adds seven tests: UTF-16BE tree, new tree, PDFDocEncoded tree with a replacement, `/AF`-only file, the documented limitation, and the 1040-ES corpus file through qpdf `--check`, `qpdf --show-attachment` of both files, and pypdf (both names, the added bytes' SHA-256, the original's SHA-256 from the manifest). The Reader-extended attachment test in `UsageRightsTests` now adds `usage-rights.txt`. Without the fix (source changes stashed, net10.0), five of the seven failed, including the corpus test with qpdf's "keys are not sorted in validate"; the limitation test passes both ways, as it should. The `UsageRightsTests` change was not run against the old code.
- Verification: `dotnet test test/jaytwo.Ergonomics.Pdf.Tests` (GA SDK 10.0.402) with qpdf 12.4.2, Poppler 26.09.0, SoftHSM 2, OpenSSL 3.2.4, and Python 3.13 (pypdf 6.21.1, pyHanko 0.38.0): 977/977 on each of net10.0, net8.0, net6.0, and net48, all four run at once; the SoftHSM interop failure seen under W-67 did not recur. `dotnet build -c Release --no-incremental` of the library and the test project: 0 warnings, 0 errors. `make fuzz-smoke` passed, 0 failures in 8 targets. `make docker-builder docker-test` (Ubuntu image, qpdf 12.3.2, pypdf 6.21.1): 977/977 on each of net10.0, net8.0, and net6.0, and the fuzz smoke passed. `make agents-check` and `make task-check` passed.
- Limitations: a name that PDFDocEncoding cannot hold, added to a tree with PDFDocEncoded keys (or to a tree that already mixes encodings), is UTF-16BE and sorts after the PDFDocEncoded keys by bytes, so qpdf can still warn when the name sorts before them as text. qpdf compares keys as Unicode text, so even in a single-encoding tree it disagrees with ISO byte order in two edge ranges: PDFDocEncoding codes 0x18 to 0x1F and 0x80 to 0xA0 against Latin-1 letters, and UTF-16BE characters above U+FFFF against U+E000 to U+FFFF; the library follows the standard there. A tree keyed in UTF-8 (PDF 2.0) is treated like a PDFDocEncoded one. Adobe Acrobat and pdf.js were not run on the output; their comparison is taken from the issue 214 thread and the pdf.js source.
