# W-170. Tighten revision footers and the signature byte-range status

## Problem

The 2026-10-24 review of W-150 found four correctness gaps.

1. The revision footer check accepts white space before `startxref` but not comments. ISO 32000-1 7.2.3 treats a comment as white space, so a conforming file can be refused.
2. The footer's `startxref` value is parsed and then discarded, so the check does not show the footer belongs to the section being read.
3. `ByteRangeStatus.WellFormed` checks only that the gap starts with `<` and ends with `>`. That does not establish that the gap is this signature dictionary's serialized `/Contents` value.
4. An empty first or second range, `Length0` 0 or `Length1` 0, can still pass.

The review also prefers `HasSignatureValueDictionary` to `HasSignatureDictionary`, and asks the documentation to list what inspection does not verify.

## Scope and exclusions

- **Footer:** skip white space and complete comments before `startxref`, and require the offset to name the section being read. For a linearized pair, the main section's footer names the first-page section, and the first-page section's own value is not checked. `/XRefStm` sections are not revisions and need no footer.
- **Byte range:**
  - Report an empty range as its own status.
  - Report `WellFormed` only when the gap spans exactly the lexical source range of the signature dictionary's `/Contents` hex string, found by re-reading that uncompressed dictionary from the file.
  - Report a gap that is not that token, including a signature dictionary inside an object stream, as `GapNotContents`.
- **API:** rename `HasSignatureDictionary` to `HasSignatureValueDictionary`. List the non-verified properties in the XML docs and `README.md`.

Excluded:
- checking that the signature dictionary lies inside the signed ranges (a documented limitation);
- signature validation;
- spec text, which needs the owner's approval of wording.

## Acceptance criteria

Each of these has a test with a deterministic outcome:
- a comment before `startxref`;
- a footer whose offset names another section;
- the linearized corpus files;
- `Length0` 0;
- `Length1` 0, including `Offset1` equal to the file length;
- a gap that is a different hex string inside the same dictionary;
- a well-formed library signature.

Also:
- The pyHanko and pdfsig agreement tests still pass, and every signature pyHanko reads is `WellFormed`.
- Inspecting a signed sparse file past 1 GiB still reads less than 2 MiB.

## Evidence required

`make quiet-test TEST_FRAMEWORK=net10.0 TEST_FILTER=FullyQualifiedName~SignatureInspection|FullyQualifiedName~RevisionTests`, plus the fast lane, because the API rename touches many tests.

## Notes

- Raised by the owner's review of W-150 on 2026-10-24.
- The review endorses W-150's footer outcome (throw), the fixture correction, keeping the claimed revision independent of the status, and the general API direction.
- Spec wording proposed by the review, awaiting the owner's approval of the text:
  - R9: "Signature inspection shall report whether a signature field's `/V` resolves to a dictionary, the structural status of any `/ByteRange`, its claimed ending offset, and the revision whose ending offset matches that claim, if any. None of these properties establishes cryptographic signature validity or trust."
  - R10: "Revision inspection shall report the structurally established boundaries of each revision and whether any signature `/ByteRange` endpoint coincides with each boundary. Offset coincidence is independent of signature validity and shall not be described as cryptographic coverage."
