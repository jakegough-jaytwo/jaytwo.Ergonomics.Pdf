# W-227. Write a carried direct trailer Info as an indirect object, not a direct trailer dictionary

## Problem

ISO 32000-1 Table 15 makes the trailer `/Info` an indirect reference. W-226 preserved a direct Info by copying the dictionary into the new trailer, with strings encrypted as object 0 for encrypted files. Reproduced on W-226 output: qpdf's trailer shows `/Info << ... >>` (not a reference), and for the AES-128 file qpdf shows the Title as undecrypted hex, so no independent reader recovers it.

## Scope and exclusions

Move the direct Info into a new indirect object in the appended revision (normal object identity and encryption); original bytes stay a prefix. Out: other trailer entries, the loader's object-0 decryption of a direct source Info (an input convention, unchanged), full rewrite.

## Acceptance criteria

- Saved trailer `/Info` is an indirect reference whose object holds the values; qpdf reads them, decrypting the AES-128 case.
- Library reopens both; original bytes a prefix; indirect-Info and no-edit controls unchanged.
- The qpdf tests fail on W-226's output.

## Evidence required

`InfoPreservationTests` against W-226 and new code; full net10.0 suite; build; `make agents-check`, `make task-check`.

## Closeout

2026-11-01: reproduced on W-226 output (two qpdf cases failed: direct `/Info <<...>>` in the trailer, undecrypted title for AES-128). Fix: `PdfIncrementalWriter.WriteAppendix` allocates an indirect object from the direct Info (as `EditInfo` does) before writing, and W-226's direct trailer writer (`PdfSerializer.WriteTrailerValue` and the trailer branch) is removed. Because it sits in `WriteAppendix`, the signing save shares the path; no signing test with a direct Info was written.
