# W-214. Truncate AES-256 password bytes at exactly 127 bytes

## Problem

W-155 confirmed a Medium interoperability defect: `TruncateUtf8` backs up to a character boundary. qpdf R5 and R6 files with 126 ASCII bytes followed by é reject the correct user password. ISO 32000-2 7.6.4.1 p92 requires the first 127 bytes. See `agents/reference/W-155/findings.md`, manifest and `qpdf-256-{r5,default}-split127.pdf`; `regressions.py` has two permanent red checks. Reproduced across all five supported Windows runtime families and Linux modern hosts.

## Scope and exclusions

Correct byte truncation for R5 and R6. Migrate the independent fixtures into ordinary regression tests. Do not add password retries, change SASLprep or encoding, add algorithms, or change the supported contract. Proposed and unqueued pending owner scheduling.

## Acceptance criteria

- Correct user and owner boundary passwords open R5/R6 input and decrypt known metadata and stream payloads; incorrect passwords remain typed rejections.
- Exactly 127 bytes are used even if the last byte is a partial UTF-8 sequence; ordinary short passwords retain their behavior.
- A permanent normal-suite regression derives expected behavior from the independent producer and standard, not a self-generated encryptor.

## Evidence required

Focused EncryptionTests for the boundary, normal password and rejection; affected supported runtime families because shared byte preparation is framework-sensitive. qpdf confirms fixture credentials/payload. No full suite, Docker checkpoint or qualification update unless separately requested.

## Closeout

Not started. W-155 records the red evidence; no runtime fix is claimed.
