# W-174. Isolate the temp directory of each parallel unit-test run

## Problem

1. **Summary.** `make unit-test` runs the test projects in parallel. Coverlet keeps its hit-tracking file in the temp directory, named from the instrumented module. `jaytwo.Pdf.Tests` and `jaytwo.Ergonomics.Pdf.Tests` instrument the same `jaytwo.Pdf.dll` per framework, so on one framework they probably share a hits file.
2. **Impact.** Jenkins build 13 on `wip` failed: all tests passed, but coverlet threw `Unable to read beyond the end of the stream` computing coverage for `jaytwo.Ergonomics.Pdf.Tests` on net10.0, which failed the target and skipped `reportgenerator`.
3. **Reproduction.** Intermittent; Jenkins build 13. The shared hits file is the likely cause and was not confirmed against coverlet's source.
4. **Expected.** Parallel runs do not interfere, and a passing suite passes the target.
5. **Actual.** `make: *** [Makefile:162: unit-test] Error 1` with no failed test.
6. **Severity.** Medium: flaky CI gate; no product behavior is wrong.

## Scope and exclusions

Each parallel run in `unit-test` gets its own `TMPDIR` under `out/testResults/tmp/<name>`. The shared coverage output path is a separate problem, researched in W-175.

## Acceptance criteria

- `make unit-test` gives each parallel run a distinct temp directory.
- The test result and log globs are unaffected.

## Evidence required

Running `make unit-test` repeatedly to prove a negative is out of proportion for an intermittent race. The Makefile change is checked by inspection, and the next Jenkins builds are the evidence.

## Closeout

The `unit-test` loop creates `${BUILD_TEST_RESULTS_DIR}/tmp/$name` and runs each parallel `dotnet test` with `TMPDIR` set to it. Not run locally: the target needs the Linux image, and the failure is intermittent. The cause is probable, not confirmed. If build 14 or later shows the same error, the cause is wrong and this item needs reopening as a new defect. Completed 2026-10-25.
