# W-132. Open documents from an IPdfSource random-access snapshot

## Problem

Reset stage R1 step 4 (`reset-plan.md` sections 4.3 and 7). Input is a seekable `Stream` and only save and sign are asynchronous. Spec requirement R13 (New) and W20 (Change) require an `IPdfSource` with async open and reads.

## Scope and exclusions

- Introduce `IPdfSource` and its seekable-`Stream` adapter with the section 4.3 semantics: one stable snapshot, absolute `long` offsets, partial reads, zero-byte end of source, serialized engine reads, explicit ownership at every open entry point, and failure on a detected source change.
- Async open and read paths with cancellation; cancellation publishes no partially parsed state. Keep synchronous conveniences where they do not hide blocking remote I/O.
- Bounded read coalescing and caching above the source; state how D-49's cursor windows carry into them.
- Ship R13 and W20 under D-43: set their status to Exists and update `ACCEPTANCE.md` and `README.md`.

No storage adapters (stage R5) and no object-stream cache (W-109, reassessed after this item).

## Acceptance criteria

- Opening from a stream works through the adapter; tests cover partial reads, cancellation, ownership, and a source change during use.
- Existing large-file read budgets (D-20) and I/O tripwires (D-49) still pass.

## Evidence required

Focused source tests, the large-file and tripwire tests, and `make quiet-test LANE=fast`.

## Closeout

Shipped R13 and W20 (D-43: both set to Exists, with `ACCEPTANCE.md` and `README.md`).

- API: public `IPdfSource` (`Length`, `Read(long, Span<byte>)`, `ReadAsync(long, Memory<byte>, CancellationToken)`, `IDisposable`) and `PdfSourceChangedException`. `PdfDocument.Open` and the new `OpenAsync` take a stream (`leaveOpen` defaults to false, as before) or an `IPdfSource` (`leaveOpen` required). The internal `PdfStreamSource` is the stream adapter. Its snapshot is the stream's length; a read after the length changes throws `PdfSourceChangedException`, except while the document appends to its own stream, whose new length then joins the snapshot. A document opened from an `IPdfSource` saves and signs only into a destination.
- D-55: the cursor, `PdfLexer`, `PdfParser`, and `PdfXrefReader` are one async-shaped implementation. The synchronous members run it with `useAsync` false through `PdfSync`, which requires inline completion. A byte inside the current window costs no state machine, and only a fill awaits the source. The engine's open path (header, `startxref`, xref chain, `/Encrypt`, xref streams) and its `Load`/`Resolve` core are async-capable, so an indirect `/Length` met during an asynchronous open is awaited too, including from an object stream. For that case the asynchronous `ReadDecoded` loads the indirect `/Filter` and `/DecodeParms` values before the synchronous decoder resolves them.
- D-49 carry-over: the cursor's retained 64 KiB windows (8 by default, at most 16, so 1 MiB) are the bounded cache and the read coalescing above the source. They are still released when each public operation returns. A partial read makes a shorter window. Range reads (`ReadRange`) still read in chunks of at most 64 KiB and loop until whole. A zero-byte read before the end is truncation.
- Ownership: an owned source is disposed with the document, and also when the open fails or is canceled. A failed or canceled open disposes the engine it built, so nothing partially parsed is published.
- Build: `jaytwo.Pdf` now always compiles optimized. Unoptimized Debug builds emit async state machines as heap classes, which put three W-115 allocation tests over budget, while Release passed them unchanged. Debug symbols are kept.
- Limitation: after opening, the document's properties, the synchronous methods, and the appendix of an asynchronous save read through `IPdfSource.Read`, so a source must read synchronously as well. Asynchronous inspection is not part of this item (D-55).
