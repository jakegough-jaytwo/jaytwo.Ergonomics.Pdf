# W-88. Check signing a certified Reader-extended file

## Problem

On a file that is both certified at DocMDP `P` 2 or `P` 3 and Reader-extended, a `Sign` that removes `/UR3` changes the catalog `/Perms` in the signed revision. `P` 2 and `P` 3 allow form fill and signing, and a validator that compares revisions may judge a `/Perms` change as outside them and report the certification as broken. After W-87, this still happens whenever the UR3 transform does not grant the sign. No corpus file is both certified and Reader-extended, so the behavior is untested.

## Why now

The owner asked on 2026-10-20, reviewing W-67, for a follow-up to test the case rather than change behavior without evidence.

## Scope and exclusions

- Build a fixture that is certified at `P` 2 and carries a `/UR3` signature, or find a real one, and sign it in the cases where `/UR3` is removed.
- Check the output with pyHanko's difference analysis of certified documents, and record whether it accepts the revision.
- If it reports the certification as broken, propose the fix to the owner: refuse `Sign` on such files, or leave `/UR3` in place for them. Do not choose between them in this item.
- Excluded: validating the UR3 signature, and changing behavior before the owner decides.

## Acceptance criteria

The fixture and pyHanko's verdict for each removal case are recorded in Notes, and either no change is needed or a proposal is in front of the owner.

## Evidence required

pyHanko's validation of the signed output.

## Proposal for the owner

**What happens today.** On a certified (`P` 2 or `P` 3) Reader-extended file, the library performs the writes certification allows: fills, signatures, and document timestamps. When the usage-rights transform does not grant the write, the library also deletes `/UR3` from the catalog `/Perms` in the same revision, as `AGENTS.md` and spec §7.3 require. pyHanko treats any change to `/Perms` after a certification as outside every DocMDP level and reports the certification as broken (`ILLEGAL_MODIFICATIONS`). The new signature itself is fine. The write affected most is a document timestamp, because no transform grants it. Next is a signature into a new field. A fill or a signature into an existing field is affected only when the transform is absent, malformed, or lacks the right; every Adobe-extended corpus form grants `/Form FillIn` and `/Signature Modify`.

**Option A: refuse.** When the document is certified and the write would remove `/UR3`, throw a controlled exception before writing, leaving the document clean, as other refusals do. The library never produces a file whose certification pyHanko reports broken. The cost is that these files cannot be timestamped or signed into a new field at all, and the caller has no workaround in Phase 1, because no API removes `/UR3`. This changes `AGENTS.md` ("`P` 2 and `P` 3 allow form fill and signing") for these files.

**Option B: leave `/UR3` in place.** When the document is certified, a write that certification allows leaves `/Perms` untouched, even when the transform does not grant it. pyHanko accepts the result: `/Perms` is then unchanged, exactly as in the 16 accepted keep cases above. The cost is that the usage-rights signature no longer matches the document. Adobe Reader is expected to show its notice that extended features are no longer available, instead of dropping them silently, which is what spec §7.3 avoids today. Adobe Reader is not available here to confirm this. This changes the `AGENTS.md` sentence "otherwise removed in the same revision" and spec §7.3 for certified files.

**Recommendation: B.** The certification is a signature guarantee that recipients and validators check. Usage rights only unlock Reader features, and those features are lost either way; the only difference is whether Reader says so. B keeps every operation that certification allows, while A blocks timestamps on these files completely. Whichever option is chosen, it should cover fills as well as signatures, since the mechanism is the same. The owner may also want it to apply to documents that carry only approval signatures, because pyHanko judges `/UR3` removal against those too.

**Uncertainty.** Neither option has been checked against Adobe Acrobat. If Acrobat accepts the removal of `/Perms /UR3` under DocMDP, today's behavior is already right for Acrobat, and only pyHanko objects.
