# W-167. Measure baseline work for document operations on benign fixtures

## Problem

W-149 needs evidence of how much work one public operation does. The engine counts only final decoded bytes (`DecodedByteCount`) and retained object streams; it does not count intermediate filter stages, object-stream re-decodes, evictions, object loads, or tree traversal, so the existing G7 tripwires cannot show amplification.

## Scope and exclusions

Add internal, test-visible work counters to `jaytwo.Pdf` that observe without changing behavior: filter-stage decodes and bytes, object-stream parses, object-stream and cached-object evictions, object loads, reference resolutions, and page and field tree node visits. Source I/O and memory are measured in the tests with the existing `ProbeStream` and `WorkloadMeter`. Run the existing large-workload fixture shapes and the G2 corpus through representative public operations and record the counts, the amplification paths found in the code, and the current cancellation limitations in `agents/reference/w-149-work-budgets.md`, keeping measured evidence separate from analysis.

Excluded: adversarial fixtures (W-168), any cumulative limit, any change to the D-49 release policy or other production behavior, and the W-149 strategy decision.

## Acceptance criteria

- The counters are internal, per document, and change no public API or observable behavior.
- A focused test shows each counter counts what it names on a small builder fixture.
- The report gives commands and observed counts for the benign workloads, labels analysis as analysis, and lists the cancellation checkpoints each async public operation has.

## Evidence required

`make quiet-test TEST_FRAMEWORK=net10.0 TEST_FILTER=FullyQualifiedName~WorkCounterTests`, plus the baseline run whose command and output the report records.

## Closeout

2026-10-24. Added the internal `PdfWorkCounters`, one per document and readable through `PdfDocument.WorkCounters`. `PdfStreamDecoder.Decode` takes an optional counters argument; the object store, the loader, and the two tree walks increment the counters. No public API or behavior changed. `WorkCounterTests` checks each counter exactly on a four-object-stream builder fixture, including the second walk's re-decode. `WorkBaselineTests` (External + LargeData, and Corpus) reports the baseline. The measured rows, the analysis of paths A to F, the cancellation inventory, and the preliminary implications for W-149 are in `agents/reference/w-149-work-budgets.md`.

Main measured findings:

- D-49 re-decodes each object stream 3.6 to 7.0 times per operation on the G7 shape, and up to 15.9 times on real forms (`faa-8710-1`: 7.6 MB decoded from a 409 KB file in 0.46 s).
- No benign structural stream uses a filter chain.
- The largest peak heap growth is 55.4 MiB (4,000-page flatten).

Verification:

- `make quiet-build`: PASS.
- `make quiet-test TEST_FRAMEWORK=net10.0 TEST_FILTER=<WorkCounterTests|ObjectStreamCacheTests|IndirectFilterTests|XrefStream|LzwTests>`: 53/53 passed.
- The baseline command in section 2 of the report, Release net10.0: 3/3 passed.

Limitations:

- Cancellation latency is not measured, because no benign operation runs longer than 1.52 s.
- Streamed attachment decoding is not counted.
- Paths A to D are analysis only until W-168. W-149's criteria are not met.
