# W-173. Read MuPDF stext characters regardless of attribute order

## Problem

1. **Summary.** `RenderTool.ReadMuPdfWords` matched `<char c="..." quad="...">` with `c` first. MuPDF 1.27, which the Ubuntu 26.04 Docker image installs, writes `c` last, so the parser found no words.
2. **Impact.** Jenkins build 12 on `wip` failed: `AppearanceRenderTests.renderers_fit_auto_sized_text_and_paint_widget_colors` and `renderers_check_visibility_encoding_alignment_clipping_rotation_and_crop` failed on net10.0, the only target that runs `Interop` tests. Local MuPDF 1.28.5 writes `c` first, so the tests passed locally.
3. **Reproduction.** `mutool draw -q -F stext -o - <pdf>` in an `ubuntu:26.04` container with `mupdf-tools` 1.27.0.
4. **Expected.** The helper reads the words from either attribute order.
5. **Actual.** `Assert.Single` over an empty word list, and `Assert.Equal(3, 0)` for the `Align` words.
6. **Severity.** Medium: the CI gate fails; no product behavior is wrong.

## Scope and exclusions

`RenderTool.ReadMuPdfWords` reads `c` and `quad` by attribute name. No library change and no change to any assertion.

## Acceptance criteria

- `AppearanceRenderTests` pass with MuPDF 1.27 and 1.28.

## Evidence required

`AppearanceRenderTests` on net10.0 locally (MuPDF 1.28.5), and the next Jenkins build for 1.27.

## Closeout

`ReadMuPdfWords` now reads `c` and `quad` by name from each `<char>` tag. Confirmed the 1.27 order (`c` last) in an `ubuntu:26.04` container. `dotnet test test/jaytwo.Pdf.Tests -f net10.0 --filter FullyQualifiedName~AppearanceRenderTests` passed 16 of 16 with MuPDF 1.28.5. The 1.27 run is the next Jenkins build. Completed 2026-10-25.
