# W-89. Say in the README which writes use the ASCII literal rule

## Problem

`README.md` said, under "Text is PDF text", that writes use a literal string for ASCII and UTF-16BE hex otherwise. Since W-86, attachment name-tree keys follow a one-encoding rule instead, and a new tree's keys are UTF-16BE even for ASCII names. The support matrix Attachments row states the rule correctly; the general sentence contradicted it.

## Why now

The owner asked on 2026-10-20 to tighten the sentence after the W-86 review.

## Scope and exclusions

- `README.md`: the general sentence names the writes it covers and points name-tree keys to the Attachments row.
- Excluded: any behavior, test, or `ACCEPTANCE.md` change. `ACCEPTANCE.md` states the metadata and name-tree rules separately and does not contradict either.

## Acceptance criteria

- The sentence matches the writers that call `PdfTextCodec.Encode` (information entries and dates, field `/V` and `/T`, file specification `/F`, `/UF`, and `/Desc`, signature `/M`) and no longer covers `/EmbeddedFiles` keys. No `ACCEPTANCE.md` row changes.

## Evidence required

Reading the `PdfTextCodec.Encode` call sites in `PdfEngine.cs`; `make agents-check` and `make task-check`.

## Notes

- 2026-10-20: Created, activated, and completed in one commit at the owner's request (D-41, D-42). The call sites were read from `src/jaytwo.Ergonomics.Pdf/Internal/PdfEngine.cs`; name-tree keys use `EncodeUtf16Be` or `EncodePdfDocOrUtf16Be` instead (W-86).

## Closeout

Done 2026-10-20. `README.md` "Text is PDF text" now limits the ASCII literal rule to the text strings that use it and points attachment name-tree keys to the Attachments row. No runtime, test, or acceptance change. `make agents-check` and `make task-check` passed.
