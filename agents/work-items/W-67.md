# W-67. Apply the usage-rights policy to every write

## Problem

Reader-extended forms carry a `/UR3` signature. Some edits break it, and Reader then shows an error. Spec §7.3 keeps `/UR3` only when it provably permits the write.

## Why now

Reset plan C2 item 7. The common policy lands before the first new write, so each later write item adds only its own cases.

## Scope and exclusions

- Resolve `/Perms /UR3`, its `/Reference`, `/TransformMethod`, and `/TransformParams`.
- Apply the policy to the writes that exist today: fill, metadata, attachments, and sign.
- Every non-permitting case removes `/UR3` in the same revision and proceeds (plan C4).
- Excluded: validating the usage-rights signature.

## Acceptance criteria

- Permitted, absent, unresolvable, malformed, unknown, and insufficient `/UR3` cases are tested for each existing write.

Refine these criteria, and the `ACCEPTANCE.md` rows they add or change, when the item becomes active. A write item also meets every check in plan C4.

Refined at activation (2026-10-20):

- The writes that exist today are the four fill setters (text, check box, radio, choice), the metadata writes (Info text, dates, `Trapped`, XMP), attachment add, replace (add with an existing name), and remove, and `Sign` (including a document timestamp, which goes through `Sign`).
- Spec 7.3 grants: a fill keeps `/UR3` when the UR3 transform lists `FillIn` in `/Form`; add, replace, and remove keep it when `/EF` lists `Create`, `Modify`, and `Delete` respectively. No right keeps it for a metadata write or `Sign`.
- Every other case removes `/UR3` from `/Perms` in the same revision and the write proceeds: absent transform (no or empty `/Reference`); unresolvable (`/UR3`, `/Reference`, a `/Reference` entry, `/TransformParams`, `/V`, or a listed right that does not resolve, including a generation mismatch); malformed (wrong object type for `/UR3`, `/Reference`, an entry, `/TransformParams`, a rights array, or a right); unknown (`/TransformMethod` other than `UR3`, `/V` other than the name `2.2`, a second transform in `/Reference`); insufficient (the rights do not list the write).
- A file with no `/UR3` gets no `/Perms` change. Each part may be indirect; an omitted `/V` is `2.2` (ISO 32000-1 Table 255).
- The policy runs after every check that can refuse the write, so a write refused by the permission bits or validation keeps `/UR3` and does not dirty the document, and a failed `Sign` restores it.
- A parse failure while resolving those objects stays a `PdfParseException` (plan C4); a reference that does not resolve is a removal, not a failure.
- Plan C4 checks for this item: the original bytes are a prefix; one revision; encrypted input under the user password (fill granted and kept, metadata refused and `/UR3` kept) and the owner password (metadata allowed, `/UR3` removed), with qpdf and pypdf reading the output with the password; the certification and FieldMDP gates run before the policy and are unchanged: DocMDP `P` 2 refuses a metadata or attachment write and keeps `/UR3`, and a signature removes `/UR3` and keeps `/DocMDP`. The approval-signed CMS-40B keeps its earlier signature intact and valid.
- New `ACCEPTANCE.md` AcroForm row; new `README.md` support-matrix row "Usage rights".

## Evidence required

Real Reader-extended forms from the corpus: IRS W-9 and 1040-ES, VA 21-4138, Grants.gov SF-424, CMS-40B, and CMS-40B with a pyHanko approval signature. qpdf 12.4.2 `--check`, and pypdf 6.21.1 and pyHanko 0.38.0 through `corpus_probe.py`.

## Notes

- 2026-10-20: Created under W-63 from `agents/reference/charter-reset-plan.md` C2.
- 2026-10-20: Activated and scoped. W-63 is done. pypdf reads the six Reader-extended corpus files: each has one `/Reference` entry with `/TransformMethod /UR3` and `/V /2.2`. All grant `/Form FillIn`. The IRS, VA, and Grants.gov forms grant `/EF Create Delete Modify Import`, and CMS-40B grants no `/EF` rights. CMS-40B keeps `/Perms` and `/UR3` direct in the catalog; the others make both indirect. The policy is applied when each write is made, not at save, so it needs no extra state and the existing backup and restore in `Sign` covers it. Spec 7.3 names three `/EF` rights for attachment edits; this item reads them as add = `Create`, replace = `Modify`, remove = `Delete`. Spec 7.3 lists no right for `Sign`, so signing removes `/UR3` even when `/Signature Modify` is granted. Both readings are recorded for the owner, and neither contradicts the spec.
- 2026-10-20: Observation outside this item's scope: adding an attachment to the IRS 1040-ES, whose name-tree key is UTF-16BE, under a name that sorts after it as text makes qpdf `--check` warn that the keys are not sorted. The library orders keys by bytes. This predates W-67. It is recorded as proposed W-86, and the corpus attachment test uses a name that sorts first both ways.

## Closeout

Done 2026-10-20 in one commit that activates the item, carries its work, and closes it (D-42). Verification ran on that tree.

- Implementation: `PdfEngine.ApplyUsageRights(category, right)` runs in each fill setter, metadata write, attachment add, replace, and remove, and in `Sign`, after every refusal check. It keeps `/UR3` only when each `/Reference` entry is a UR3 transform with `/V` 2.2 (or omitted) whose `category` array lists `right`. Otherwise it removes `/UR3` from the `/Perms` object, or from a copy of a direct `/Perms` in the catalog. `SetRadio` now checks for a missing export value before any edit. `AddAttachment` reads the name tree before allocating, which it needs to tell add from replace. The internal `PdfDocument.HasUsageRights` lets tests read the result.
- Tests: `UsageRightsTests`: 13 writes times 30 policy cases (390), covering permitted, absent, unresolvable, malformed, unknown, and insufficient transforms, with prefix, one-revision, and untouched-`/Perms` checks; a fill plus metadata write in one save for each case (30); refused writes and a failed `Sign` keep `/UR3` and leave the save byte-identical; DocMDP `P` 2; AES-128 and AES-256 under the user and owner passwords, read back by qpdf `--check` and pypdf; and on the six Reader-extended corpus forms, attachment add (kept except CMS-40B), signing (removed, the new signature intact and valid in pyHanko, earlier signatures intact and valid), and 1040-ES replace and remove (kept), each checked with qpdf `--check` and the corpus probe. `CorpusTests` now asserts that pypdf finds no `/UR3` after the metadata revision and the same `/UR3` state after the fill, for every corpus entry. With the policy disabled, 370 of the 436 `UsageRightsTests` cases failed. With grants ignored, 43 cases failed across `UsageRightsTests` and `CorpusTests`.
- Verification: `dotnet test test/jaytwo.Ergonomics.Pdf.Tests` (GA SDK 10.0.402) with qpdf 12.4.2, Poppler 26.09.0, SoftHSM 2, OpenSSL 3.2.4, and Python 3.13 (pypdf 6.21.1, pyHanko 0.38.0): 970/970 on net8.0, net6.0, and net48. On net10.0, 969/970: `SigningInteropTests.pkcs11_signature_matches_pkcs1_and_pyhanko_trusts_the_chain` failed while all four targets ran at once against the one SoftHSM token, and the five `SigningInteropTests` passed in two reruns of net10.0 alone. After the DocMDP test was added, `UsageRightsTests` and `CorpusTests` ran 560/560 on each of the four targets. `dotnet build src/jaytwo.Ergonomics.Pdf -c Release --no-incremental`: 0 warnings, 0 errors. Fuzz smoke passed, 0 failures in 8 targets. `make agents-check` and `make task-check` passed. `make docker-builder docker-test` was not run; this commit is not an integration checkpoint.
- Limitations: the usage-rights signature is not validated, and Adobe Reader was not available to confirm its behavior on the output; the evidence is the transform parameters as pypdf and the library read them. A parse failure in a `/UR3` object fails the write with `PdfParseException`. The PDF 1.5 `/Perms /UR` entry is not read or removed. Signing removes `/UR3` even when `/Signature Modify` is granted, because spec 7.3 lists no right for signing. On a document that is both certified (`P` 2 or 3) and Reader-extended, that removal changes `/Perms` in the signed revision; no corpus file has that combination. The fuzz seeds do not yet include a `/UR3` structure, so the G8 campaign (W-18) should add one. Name-tree key order on mixed-encoding trees is W-86.
