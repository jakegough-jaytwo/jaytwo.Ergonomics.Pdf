# W-42. Reduce object-stream body allocation churn

## Problem

Parsing object-stream bodies allocates roughly 100 bytes per decoded byte. A 32 KiB file decoding to 31 MiB was measured at 3.23 GiB allocated in about six seconds. It completes under a 1 GiB heap cap, so the issue is churn rather than retention.

## Why now

This is a known Medium performance risk related to the B-17 O1 observation.

## Scope and exclusions

Reuse one parser and its token pushback storage while parsing the members of one decoded object stream, and parse integer tokens without allocating temporary text. Add a focused allocation regression that parses a valid, high-member-count object stream directly and states the maximum allocation factor relative to decoded size.

Do not change the decoded-size cap, the object-stream read-work bound, accepted object-stream syntax, object retention, or cross-reference behavior. Do not add a cache or a runtime dependency.

## Acceptance criteria

- Parsing 65,536 integer members from one decoded object stream allocates less than 16 bytes per decoded byte on net10.0.
- Existing object-stream parsing, overlap refusal, and cache-release tests continue to pass.

## Evidence required

- Before-and-after allocation measurements from the focused regression workload on net10.0.
- The focused object-stream and hardening tests.
- The repository verification required by `pdf-change-verification`, including the Docker integration gate before commit.

## Closeout

- `PdfParser.ParseObjectStream` reuses one parser per decoded object stream and clears its token pushback at each member, and integer tokens are parsed digit by digit without temporary text. Real numbers keep the existing text path. The decoded-size cap, the read-work bound, accepted syntax, and object retention are unchanged.
- Allocation on the 65,536-member regression workload (`object_stream_body_allocation_is_proportional_to_decoded_size`, net10.0, Debug, `GC.GetAllocatedBytesForCurrentThread`, decoder and xref excluded): 54.9 bytes per decoded byte before the change, 35.4 with parser reuse alone, and 7.9 with the integer fast path, against the 16-byte ceiling. The test failed red at 54.9 on the unchanged parser.
- Added `integer_token_fast_path_preserves_the_full_long_range` and `integer_token_fast_path_still_refuses_values_outside_the_long_range` for the sign, `long.MinValue`, `long.MaxValue`, and one-past-range edges.
- Verification: warning-free all-target `make quiet-build`; the net10.0 `HardeningTests` class (72 passed) and `ObjectStreamCacheTests`; the new and object-stream `HardeningTests` on net48 (10/10); Docker totals 4268/4268 on `net6.0`, `net8.0`, and `net10.0`, and fixed-seed fuzz smoke passed. The first Docker run failed only an unrelated dictionary timing budget on `net8.0` and `net10.0`, which passed in isolation in 391 ms and 331 ms against its 10-second limit; the rerun was green.
- Limitation: the factor is measured for integer members only. Object streams of dictionaries, strings, names, and real numbers were not measured by this item; their allocation is left to the G7 workloads (W-79).
