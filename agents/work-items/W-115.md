# W-115. Cut object parsing allocations

## Problem

One walk of the 500-page form decodes about 1.8 MB and allocates about 44 MiB, so parsing allocates roughly 24 bytes per decoded byte. Every form path pays it. Extraction allocates 68 MiB against iText's 12 MiB, and sign 105 MiB against 20 MiB (`agents/evidence/itext-comparison.md`).

## Why now

After W-114, this is the remaining cost on every form path.

## Scope and exclusions

- Profile allocations on form extraction and the field walk, and record the largest allocation sites in Notes.
- Reduce the largest sites, for example by interning names, using a compact representation for small dictionaries, and avoiding boxing and copies of decoded buffers. Measure each change.
- Excluded: object-stream retention (W-109), public API, and any change to what is parsed or accepted.

## Acceptance criteria

- Outputs are byte-identical on the G7 workloads, the interop tests, and the corpus round trips. Every parser hardening and fuzz regression test passes, and parse errors keep their offsets.
- Allocation per decoded byte on form extraction is at most half of today's, measured in `make compare-itext` and recorded.
- G8: every fuzz target reruns from the changed code at the campaign's predeclared allocation, as in W-108, recorded in `status.md`.

## Evidence required

Internally tested, plus the G8 rerun.

## Notes

- 2026-10-22: Base for every comparison is `12c17fa` (W-114 done) in a scratch worktree. The profilers were scratch programs outside the repository: one measured `GC.GetAllocatedBytesForCurrentThread` over warm passes on the G7 500-page form (qpdf `--object-streams=generate --deterministic-id`, 256,799 bytes) and the 1,000-page flatten form; the other captured EventPipe `GCAllocationTick` events with stacks (TraceEvent, scratch only).
- Largest allocation sites on form extraction at base, share of sampled bytes over ten warm passes:
  - `PdfParser.ReadName`, 28.4%: two `List<byte>` per name, an array copy, and a UTF-8 string.
  - `PdfCursor` over a byte array, 18.3%: each object-stream parse allocated a 64 KiB window and copied the decoded stream into it.
  - `PdfObject.Dict` list growth, about 9%: 4, 8, then 16 slots for a typical widget dictionary.
  - `PdfParser.ReadKeyword`, about 9%: a `StringBuilder`, its buffer, and a string for every `R`, `obj`, and `endobj`.
  - `DeepClone` of object-stream members in `PdfEngine.LoadFromObjectStream`, 8.3%.
  - `PdfStreamDecoder.ReadAll`, 5.1%, and the zlib input buffer, 0.6%.
  - `PdfEngine.Resolve`, 4.3%: a `HashSet<int>` on every call, including direct values.
- Changes, each measured on extraction (allocated per warm pass, `net10.0` Release, Windows):

  | Step | Extraction, MiB | Per decoded byte |
  |---|---:|---:|
  | Base `12c17fa` | 68.23 | 42.84 |
  | Buffer cursor reads the decoded array, no window copy | 60.67 | 38.09 |
  | Names and keywords through one token buffer per parser, with a fixed table of common names (`PdfCommonTokens`) | 30.07 | 18.88 |
  | `Resolve` makes its set at a chain's second reference | 28.45 | 17.87 |
  | Dictionaries and arrays built once at final size from per-depth lists; presized `DeepClone`; object-stream list presized and repeat set made only when numbers stop ascending | 24.15 | 15.16 |
  | Literal and hex strings and reals through the token buffer | 22.81 | 14.32 |
  | zlib input buffer sized to what a seekable source has left, at most 8 KiB | 22.05 | 13.84 |

  Decoded bytes are unchanged (1,669,931). Metadata edit fell from 21.62 to 8.62 MiB, bulk fill from 62.42 to 24.83, and the 1,000-page flatten from 201.57 to 78.09.
- The common-name table holds about 300 ASCII names and keywords chosen from name counts over the G7 form and ten uncompressed corpus forms (keys and values outside content streams) and from the structures the library reads. It is fixed when the type loads, so input cannot grow it. A name not in it allocates only its string.
- Tried and reverted: `ReadAll` reading straight into a doubling array. Asking a decoder for fewer bytes than 8 KiB changed which error a corrupt Flate stream reports under a small cap (the differential below found it on a mutated seed). Keeping every request at 8 KiB needed a spare 8 KiB at the final read, which allocated more than the `MemoryStream` version, so `ReadAll` is unchanged.
- Caught before commit: deriving the object-stream repeat set from the parsed members' `ObjectNumber` is wrong, because `true`, `false`, and `null` are shared instances whose `ObjectNumber` each member overwrites. The set is built by re-reading the header pairs, which have already passed. `an_object_stream_repeat_is_refused_whether_or_not_numbers_ascend` covers it with those members.
- Observation, not changed (excluded: what is parsed or accepted): parsing writes `ObjectNumber` and `Generation` onto the shared `Bool.True`, `Bool.False`, and `NullObj.Instance`, both in `ParseIndirect` and in `ParseObjectStream`. Two such members of one object stream then share one number, and documents on different threads share the instances. It is not reproduced here as a user-visible failure; it is recorded for a separate item.
- Not done: the `DeepClone` of each object-stream member on load, about 8% of what remains. Removing it needs an audit of every path that mutates a loaded object; the measured target was met without it.
- Equivalence: a scratch differential ran the same inputs through base and change and compared, line by line, each step's result hash, exception type, message, and `PdfParseException.Offset`. Inputs were the harness seed corpus for `open`, `edit`, `object`, `objstm`, and `decode`, the committed regression inputs, every fixture PDF under `test/jaytwo.Ergonomics.Pdf.Tests/Fixtures` (as `open` and `edit`), and 99 handcrafted edge inputs (name escapes and long names, invalid UTF-8, odd reals, unknown keywords, repeated keys below and above 16 entries, nested containers, large strings, object streams with descending, repeated, and singleton members, decode caps at and around 8 KiB), each with eight truncations and eight byte flips. All 3,521 outcomes matched; 1,345 of them are parse exceptions, 476 are successful incremental saves with identical output hashes, and none is an uncaught exception. Base was deterministic across two runs.
- `ParserAllocationTests` run against base (with the two `PdfCommonTokens` tests removed): every behavior test passed; the widget object-stream bound (32.5 bytes per decoded byte at base, 8.2 after) and the buffer-cursor allocation (65,680 bytes at base) failed, as intended.
- G7 on Windows, 2026-10-22: `make g7-workloads` and the scaling cases (`object_stream_form_flatten_and_sign_read_in_proportion_to_the_form`, `net10.0`) ran at base and change, Release, coverage off, each test in its own process. All 24 workload runs and both scaling cases passed at each revision with the D-49 tripwires unchanged. All 32 output and signed-range hashes, and all 60 source-byte, read-call, and decoded-byte figures, are identical between base and change on `net10.0`, `net8.0`, `net6.0`, and `net48`. No window allocated more than at base on any framework; 500-page extraction fell from 68.54 to 22.36 MiB on `net10.0` (73.08 to 24.66 on `net48`), and the 1,000-page flatten from 197.93 to 74.33. Peak heap growth is sampled and depends on when collections land, so single runs moved both ways; the largest peak across frameworks fell for every form window (extraction 6.60 to 6.16 MiB, edit 6.43 to 5.34, fill 11.03 to 9.52, sign 8.39 to 6.49, flatten 21.39 to 15.83) and every dense window. ## Closeout

- Parse allocation on the 500-page form extraction fell from 42.95 to 13.95 bytes per decoded byte in `make compare-itext` (68.40 to 22.21 MiB; iText 12.33), 32.5% of base against the limit of half. The largest sites, recorded in Notes, were name tokens, the buffer cursor's window copy, dictionary growth, keyword tokens, and `Resolve`'s per-call set; each change was measured. Metadata edit, bulk fill, sign, and flatten fell to 34% to 39% of their base allocation.
- Criterion 1: every G7 output and signed-range hash (32) and every source-byte, read-call, and decoded-byte figure (60) matched base `12c17fa` on `net10.0`, `net8.0`, `net6.0`, and `net48`, with the scaling cases. A differential over 3,521 inputs (fuzz seeds, regressions, every fixture including the corpus, 99 edge inputs, and their truncations and byte flips) matched base in every result, exception type, message, and parse offset. The hardening, object-stream, cursor-window, corpus, and interop tests pass unchanged in both full runs.
- Criterion 2: recorded in `agents/evidence/itext-comparison.md` and `memory-budgets.md`.
- Criterion 3: all eight fuzz targets reran from `aacd4ee` (code equal to `daa81c0`) at 120 seconds with 7 workers, zero artifacts, about 1.93 CPU-hours (`agents/reports/2026-10-22-W-115-fuzz.md`); `status.md` records it.
- Verification: Windows `make quiet-test` 4,391/4,391 on each of `net10.0`, `net8.0`, `net6.0`, and `net48` with every external tool; warning-free Debug and Release builds of every target. Windows `make g7-workloads` 24/24 and the scaling cases at base and change. `make compare-itext` 28/28. Linux `make quiet-docker-test` 4,391/4,391 on each of `net10.0`, `net8.0`, and `net6.0` with the fuzz smoke run passing (second run; the first failed on timing, see Notes). `make agents-check` and the staged `make task-check` passed; `graphify update .` completed.
- New tests: `ParserAllocationTests` (52 cases) pins name, keyword, real, string, and container results, object-stream repeats with shared singleton members, reference chains and cycles, and two allocation bounds that fail at base.
