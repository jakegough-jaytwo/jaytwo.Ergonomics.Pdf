# W-229. Accept a non-seekable output stream for the Combine workflow terminals

## Problem

WORKFLOW-STREAM-01 and WORKFLOW-TERM-01 (adopted): a Combine output stream must be writable, empty and at position zero but need not seek; only save, append, sign and timestamp need seeking. `PdfCombineWorkflow.RunAsync` required `CanSeek`, so it rejected a writable non-seekable stream. It also read `Length` and `Position`, which a non-seekable stream cannot report. W-228's `IneligibleStreams` data and its acceptance row treated that rejection as correct.

## Scope and exclusions

Combine `Save(Stream)` and `SaveAsync(Stream)` share one check. The engine entry (`PdfDocumentEditor.Concatenate`, also used by `ExtractPages`) documents that its destination need not seek, and its failure cleanup already tolerates `NotSupportedException`. The Ergonomics library has no extract or image-to-PDF workflow terminal, so nothing else shares this validation; the engine-level extract was not tested here. Out: the adopted contract, the other eligibility and single-execution rules, W-228's post-claim checks (unchanged).

## Acceptance criteria

- A genuinely non-seekable writable stream (no length or position) is accepted by Combine `Save` and `SaveAsync`, receives a readable PDF, and the description is then consumed.
- A stream that can seek must still be empty at position zero; null and read-only streams, invalid paths and the input as destination are still rejected without consuming the description.
- The builder terminals still require seeking.

## Evidence required

`WorkflowBeginTests` on old and new code; full Ergonomics net10.0 suite; build; `make agents-check`, `make task-check`.

## Closeout

2026-11-01: reproduced on the old code: Combine `Save` to a forward-only stream threw `ArgumentException` ("empty writable seekable stream"). Fix: the stream check requires a writable stream, and checks `Length` and `Position` only when the stream can seek. Acceptance and behavior wording corrected.
