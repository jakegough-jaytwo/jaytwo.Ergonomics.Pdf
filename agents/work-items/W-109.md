# W-109. Reuse decoded object streams within an operation under a hard cap

## Problem

The engine keeps at most one clean decoded object stream. Operations walk fields and pages in cycles across every object stream, so on the W-79 form shape each stream is decoded 4.7 to 7.5 times per operation (D-49). An LRU of a few streams does not help that pattern; only holding every stream the operation touches does.

## Why now

Not before 1.0. D-49 approves it for 1.x polish, after W-108 removes the larger source over-read.

## Scope and exclusions

- Keep every clean decoded object stream the current public operation touches, up to a hard cap (16 or 32 MiB, chosen from measurements), and fall back to today's one-stream behavior above it. Release at the end of the operation, as W-108 does for cursor windows.
- Replace the `RetainedObjectStreamCount <= 1` assertions with the cap.
- Measure on real-world object-stream forms (Acrobat, iText, Word export), not only the synthetic G7 shape, and record whether the cyclic access pattern holds there.
- Excluded: a document-lifetime cache, disk spill, and changes to signing or flatten access order unless the cache proves insufficient.

## Acceptance criteria

To be written when the item is scoped for 1.x. They will include byte-identical outputs, decoded-bytes thresholds in the D-49 tripwires, and peak memory within the D-20 ceilings with the cap reached.

## Evidence required

As W-108, plus the real-world form measurements.
