# W-93. Document pyHanko's verdict on an attachment added after a signature

## Problem

W-92 found that pyHanko 0.38.0 reports any embedded-file addition after an approval signature or document timestamp as modification level `OTHER`, whichever tool writes it, because its difference-analysis policy allows no change to the catalog `/Names` (or `/AF`) after signing. The earlier signature stays intact and valid. `README.md` and `ACCEPTANCE.md` do not say so, so a caller who adds an attachment to a signed file cannot know that some recipients will see the earlier signature reported as followed by a change it does not permit.

## Why now

On 2026-10-20 the owner chose option A of W-92's proposal: keep the behavior (attachments stay allowed after an approval signature or document timestamp, spec §7.2, with `/AF` written as now) and document the verdict.

## Scope and exclusions

- `README.md`: one short statement in the Attachments row of the support matrix, where a caller deciding about attachments on signed files looks.
- `ACCEPTANCE.md`: one criterion in the Attachments section, enforced by a permanent test.
- `UsageRightsTests`: a test that pyHanko signs a built form (approval) while it runs, the library time-stamps the same form with the OpenSSL test authority (document timestamp), the library adds an attachment to each, and pyHanko reports the earlier signature intact and valid with modification level `OTHER`. A metadata write on the same signed bases is the control pyHanko accepts. The class already uses Python with pyHanko and pypdf, qpdf, and OpenSSL 3 (`AGENTS.md` names it for OpenSSL), so no tool is added.
- `W-92`: a dated Notes line recording the owner's choice and pointing here.
- Excluded: any runtime behavior change, and edits to `docs/spec/`, `AGENTS.md`, `QUALIFICATION.md`, or `.agents/skills/`.

## Acceptance criteria

- `ACCEPTANCE.md` Attachments gains the criterion: after an approval signature or document timestamp, an attachment add leaves the earlier signature intact and valid, pyHanko 0.38.0 reports modification level `OTHER`, and a metadata write is not `OTHER`. No criterion is weakened.
- `README.md` Attachments row says the same in the README's terms and advises adding attachments before signing.
- The new test passes on net10.0, net8.0, net6.0, and net48, and the Release build has 0 warnings.

## Evidence required

Independent tool: pyHanko 0.38.0 difference analysis through `corpus_probe.py`, with `qpdf --check` (12.4.2) on each output. Trust is not claimed: each certificate is its own trust anchor.
