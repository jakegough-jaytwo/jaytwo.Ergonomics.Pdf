# W-68. Form value model, bulk fill, and export

## Problem

Fills use four type-specific setters, there is no bulk fill, and there is no export of form data (spec W1, W2, R6).

## Why now

Reset plan C2 item 8. It reshapes the public API early, while breaking changes are free, so later tests are written once.

## Scope and exclusions

- A single typed fill API, all-or-nothing bulk fill, and `Export()` returning one entry per terminal field.
- Excluded: FDF and XFDF, new appearance behavior, and flatten.

## Acceptance criteria

- A bulk fill with one invalid value changes nothing.
- Export round-trips through fill.
- Existing fill behavior is unchanged under the new API.

Refine these criteria, and the `ACCEPTANCE.md` rows they add or change, when the item becomes active. A write item also meets every check in plan C4.

Refined at activation (2026-10-20):

- API (spec 6.6, question 7 answered as the illustration shows): a `PdfFieldValue` value type with implicit conversions from `string`, `bool`, and `string[]`, whose default is "no value". `PdfAcroForm.Fill(fullName, value)` fills one field and returns its `PdfAppearanceDisposition`. `PdfAcroForm.Fill(values)` takes name and value pairs (a `Dictionary<string, PdfFieldValue>` works) and returns the disposition per name. `PdfAcroForm.Export()` returns a read-only dictionary of full name to `PdfFieldValue`. `SetText`, `SetCheckBox`, `SetRadio`, and `SetChoice` are removed. The disposition `NeedAppearances` is renamed `NeedsViewer` (W1).
- Value kinds: a text field takes text; a check box takes a Boolean; a radio takes its on-state name, or no value, which turns every widget off; a choice field takes one value, a list (more than one only when multi-select), or no value or an empty list, which clears `/V` and `/I`. Any other kind throws `PdfFieldValueException`. Password, signature, and push-button fields cannot be filled (W5).
- Bulk fill (W2): every entry is validated before anything changes: unknown name, wrong kind, read-only, password, signature, push button, `/MaxLen`, an unlisted option, several values on a single-select field, check-box widgets with different on-states, a radio state that no widget has, FieldMDP, DocMDP, and the permission bits; a null or repeated name throws `ArgumentException`. One failure throws and a later save writes nothing. The fills then apply in order, as single fills would, in one revision; a failure while applying restores the document.
- Export (R6): one entry per terminal field, not per widget. Text is a string, empty when unset; a check box is a Boolean; a radio is its selected on-state or no value; a single-select choice is a string or no value; a multi-select choice is a list. Signature fields, push buttons, and password fields are not exported; read-only fields are.
- Round trip: filling a form with another copy's export, less its read-only fields, gives an equal export, and pypdf reads the same values.
- Existing fill behavior is unchanged: the existing fill tests pass through `Fill` with unchanged assertions, except that the wrong-setter cases become wrong-kind cases.
- Plan C4: the original bytes stay a prefix in one revision; AES-256 input under the user password (fill granted) and the owner password, read back by qpdf and pypdf; a user password without the fill bit refuses the whole bulk fill; DocMDP `P` 1 refuses and `P` 2 allows a bulk fill; a FieldMDP-locked entry refuses the whole bulk fill; `/UR3` is kept for a bulk fill that `FillIn` grants and kept by a refused one.
- Memory: a bulk fill reads the field tree once, so 500 fields on a 1,000-page file do not read the unread content holes.
- `ACCEPTANCE.md`: the AcroForm fill row changes from setters to value kinds, and new rows cover bulk fill and export. `README.md`: Supported today, the appearances tenet, the AcroForm support-matrix row, and Usage. Spec R6, W1, and W2 become Exists (D-43).

## Evidence required

Independent-reader checks on corpus forms: on every corpus form with fields, pypdf's values agree with `Export`, and a bulk fill of every fillable field passes `qpdf --check` and pypdf reads the filled values, with earlier signatures intact (pyHanko through the corpus probe).

- 2026-10-20: Defect found by this item's corpus check, fixed here because it blocks the round-trip criterion on a real producer. Summary: a fill wrote `/V` to a widget kid instead of the field when the kid carried `/FT`. Impact: filling a LibreOffice radio group or multi-widget field left the field's value unchanged while its widgets showed the new state; Acrobat and pypdf report the old value. Reproduction: corpus `libreoffice-form`, field `Service` (parent 11 0 has `/T`, `/FT /Btn`, `/V /FTL`; its widget kids 10, 12, and 13 also carry `/FT /Btn`); fill `Service` with `LTL` and save. Expected: the field dictionary's `/V` becomes `/LTL` (ISO 32000-1 12.7.3.1: the value is a field entry, and a kid without `/T` is a widget). Actual: `/V /LTL` was written into widget 10, the library then read it back from the widget, and pypdf 6.21.1 read `FTL`. Severity: High (the operation's output fails independent verification). Cause: `WalkField` took the node that holds `/FT` as the value owner. Fix: the value owner is the nearest field dictionary, a top-level `/Fields` entry or a node with `/T`, and `/V` is read only from field dictionaries. Regression test: `AcroFormTests.widget_kids_with_field_entries_do_not_own_the_value`. With the old rule it and the corpus check for `libreoffice-form` and `libreoffice-form-pypdf-inherited` fail.

## Closeout

- Public API (`jaytwo.Ergonomics.Pdf.AcroForm`): `PdfFieldValue` (readonly struct: `Kind`, `Text`, `Boolean`, `Values`, `None`, `FromText`, `FromBoolean`, `FromList`, implicit conversions from `string`, `bool`, and `string[]`, value equality) and `PdfFieldValueKind` (`None`, `Text`, `Boolean`, `List`); `PdfAcroForm.Fill(string, PdfFieldValue)`, `Fill(IEnumerable<KeyValuePair<string, PdfFieldValue>>)` returning `IReadOnlyDictionary<string, PdfAppearanceDisposition>`, and `Export()` returning `IReadOnlyDictionary<string, PdfFieldValue>`. Removed: `SetText`, `SetCheckBox`, `SetRadio`, `SetChoice`. Renamed: `PdfAppearanceDisposition.NeedAppearances` to `NeedsViewer`.
- Implementation: `PdfEngine.Fill` reads the field tree once, checks DocMDP, FieldMDP for every name, the permission bits, and then plans each entry (`PlanFill`) with the old setters' checks in their old order. Only then does it apply the usage-rights rule once and each plan (`ApplyText`, `ApplyCheckBox`, `ApplyRadio`, `ApplyChoice`, the old setter bodies), under the backup that `Sign` uses, so a failure while applying restores every edit. `CertificationLevel` and `FieldChangeBlocked` take the collected slots, so a bulk fill does not walk the tree per entry. The value-owner fix is in `WalkField` (Notes).
- Tests: `FormDataTests` (31 cases): 16 single-refusal cases in a bulk fill, null and repeated names, export of built forms against pypdf, round trip both ways with qpdf and pypdf, bulk equals single fills byte for byte, AES-256 under the user and owner passwords and the missing fill bit, DocMDP `P` 1 to 3, a FieldMDP lock on one entry, an apply failure, 500 fields on 1,000 sparse pages, and value equality. `CorpusTests.form_export_agrees_with_pypdf_and_a_bulk_fill_is_accepted_by_independent_tools` runs on every corpus entry: 16 forms with widgets compared with pypdf, 13 of them bulk-filled (the other three have only signature fields), each checked by `qpdf --check`, the corpus probe (prefix, one revision, pyHanko signatures intact and valid), `/UR3`, and pypdf. `UsageRightsTests` adds a bulk fill to the write matrix and a refused bulk fill. `AcroFormTests.widget_kids_with_field_entries_do_not_own_the_value` is the defect's regression test.
