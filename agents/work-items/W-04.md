# W-04. Send a nonce, and check that a timestamp token matches its request

## Problem

The library accepted any token from a status-0 or status-1 response. It did not compare the token's message imprint or digest algorithm with the request. The request carried no nonce, so a replayed token could not be detected. The W-05 signing audit confirmed this from the code.

## Why now

Gate G5. It was the first code change after kickoff.

## Scope and exclusions

- Add a random nonce to each request, under D-14. Keep `certReq` omitted.
- Reject a token whose imprint, digest algorithm, or nonce does not match the request. Throw `PdfTimestampException`.
- Run the check where the request is built, in `CmsDetachedSignatureProvider` and `DocTimeStampSignatureProvider`, not only in `HttpTimestampAuthority`, so any `ITimestampAuthority` implementation is covered.
- TSA trust stays out of scope under D-10.
- Public API: add a nonce-bearing overload of `Rfc3161TimeStampRequest.Create`. Do not change the bytes of the existing `Create(ReadOnlySpan<byte>)`; that would be a breaking change and an owner decision. `ITimestampAuthority` does not change. No engine file.
- `tsa_server.py` changes only if the local TSA does not echo the nonce.

## Acceptance criteria

- New `ACCEPTANCE.md` rows: a mismatched imprint, a mismatched digest algorithm, and a missing or mismatched nonce each throw and do not extend the file.
- The request-encoding row and the `README.md` timestamp paragraph describe the nonce.
- The existing local-TSA test still passes, with pyHanko reporting the token intact, valid, and trusted.

## Evidence required

Internally tested, plus the existing independent TSA round trip.
