# W-69. Async signer, timestamp, and save

## Problem

The signer and timestamp interfaces and the save methods are synchronous, which suits neither cloud key services nor network output (spec W20). W-49 found that timestamp-authority exceptions are not sanitized; that is folded in here.

## Why now

Reset plan C2 item 10. It rewrites the interfaces the signing items build on.

## Scope and exclusions

- `IPdfExternalSigner.SignHashAsync`, `ITimestampAuthority.GetTimeStampTokenAsync`, and `IPdfSignatureProvider.CreateContentsAsync` replace the synchronous members. Each returns `ValueTask<byte[]>` and takes a `CancellationToken`. The certificate properties stay synchronous; they are read once, before the signer is called. The signing contract (raw SHA-256 digest, RSA PKCS#1 v1.5) does not change; W-70 changes it.
- `PdfDocument.SaveIncrementalAsync` and `SignAsync` beside the synchronous methods, on one code path: the synchronous methods run the same steps with synchronous I/O and wait for the provider.
- The async methods copy the prefix with asynchronous reads and writes, and write the signature appendix asynchronously. The `SaveIncremental` appendix is serialized synchronously to the destination, because the serializer writes straight to the stream; buffering it would be the staging the charter excludes.
- The destination is truncated to its starting length when a write fails after it has started, so cancellation during the prefix copy, and any other failure mid-write, leaves the destination unchanged.
- `Microsoft.Bcl.AsyncInterfaces` on `netstandard2.0` (D-39).
- Sanitize `ITimestampAuthority` exceptions (former W-49): a host authority's exception becomes a generic `PdfTimestampException` with no inner exception. `HttpTimestampAuthority` is library code, so its documented exceptions pass through. Cancellation of the caller's token surfaces as a fresh `OperationCanceledException` from the signer and from the authority.
- Excluded: async reads, `IAsyncDisposable` (`Dispose` does not save, so there is nothing to await), and an async serializer.

## Acceptance criteria

- Sync and async results are byte-identical: an incremental save, a CMS signature, and a fill plus signature on an RC4-encrypted file, with a fixed signing time and a file that has an `/ID` (new `ACCEPTANCE.md` row).
- Cancellation before the call, inside the signer, inside the timestamp authority, and during the prefix copy throws `OperationCanceledException`, leaves the destination and the source unchanged, and leaves the document able to save again (new row).
- Timestamp-authority exceptions carry no provider details: message, data, and inner exception are gone, in both providers (new row; the signer row changes to name `SignHashAsync`).
- `HttpTimestampAuthority` honors the caller's token without reclassifying it as a timeout (the timeout row changes).
- Both verifiers (W-14) accept async-signed output: pyHanko 0.38.0 intact, valid, and trusted; `pdfsig` valid and trusted over the `/ByteRange`.
- C4: an encrypted input under the user and the owner password signs through `SignAsync`; a refused write through the async methods leaves the destination unchanged; the prefix is kept.
- Spec W20 becomes Exists, and `README.md` lists async signing and saving as shipped.

## Evidence required

pyHanko and `pdfsig` on async-signed output.

## Notes

- 2026-10-20: Created under W-63 from `agents/reference/charter-reset-plan.md` C2.
- 2026-10-21: Activated. Criteria refined as above. W20 makes the interfaces asynchronous, so the synchronous members are replaced rather than kept beside them; the spec's illustrative `SignAsync(output, options, provider, cancellationToken)` shape is followed.
- 2026-10-21: Truncation on a failed write also covers a defect the old code had: a `PdfTooLargeForClassicXrefException` or I/O failure after the copy had started left a partial destination, against README "A file past a cap throws before the destination grows". The same-stream truncation returns the opened stream to its length, which `ValidateDestination` checked on entry.
- 2026-10-21: In the first full four-target run, `caller_cancellation_aborts_a_timestamp_body_that_ignores_the_token` failed only its 10-second elapsed bound (11 to 34 s) on every target; it finishes in about 0.5 s alone. Under four parallel framework runs the thread pool delays the abort continuation. The bound is now 2 minutes against a 5-minute `HttpClient.Timeout`, which still separates the caller's cancellation from the deadline.

## Closeout

Done 2026-10-21.

- `IPdfExternalSigner.SignHashAsync`, `ITimestampAuthority.GetTimeStampTokenAsync`, and `IPdfSignatureProvider.CreateContentsAsync` return `ValueTask<byte[]>` and take a `CancellationToken`. `PdfDocument.SaveIncrementalAsync` and `SignAsync` share one engine path with the synchronous methods (a `useAsync` flag), so the bytes match. `HttpTimestampAuthority` is natively async and links the caller's token to its deadline. `TimestampAuthorityCall` sanitizes host authorities. `Microsoft.Bcl.AsyncInterfaces` 8.0.0 on `netstandard2.0` (D-39).
- Spec W20 is Exists (D-43). `ACCEPTANCE.md`: the signer rows name `SignHashAsync`, the HTTP row adds caller cancellation, and four new Sealing bullets plus one Foreign files bullet. `README.md`: an async tenet, truncation on failed writes, the timestamp sanitization, the dependency statements. Evidence inventory rows 51 to 54.
- Verification: the full suite on Windows `net10.0`, `net8.0`, `net6.0`, and `net48`, 3579 tests each, 3578 passed, plus the timing fix rerun (103 of 103 in `SignatureTests`, `AsyncTests`, and `SigningInteropTests` on all four). `make docker-builder docker-test` passed 3579 of 3579 on Linux `net10.0`, `net8.0`, and `net6.0`. Release build with StyleCop clean; the fuzz tool builds. With the truncation disabled and the sanitization replaced by a rethrow, 14 of the 26 `AsyncTests` cases failed. Independent: pyHanko 0.38.0 and `pdfsig` 26.08.0 (Windows) and 26.01.0 (Linux) accept `SignAsync` output (row 54).
- Limitations: the `SaveIncrementalAsync` appendix is serialized synchronously to the destination; the prefix copy and the `SignAsync` appendix are asynchronous. The synchronous `Sign` blocks on the provider, so a host that needs its synchronization context calls `SignAsync`. Cancellation is not observed while the `SaveIncrementalAsync` appendix is written. Truncation after a failure is best effort: a destination whose `SetLength` throws keeps the partial bytes, and the original failure is the one reported. The certificate properties stay synchronous. No `IAsyncDisposable`.
