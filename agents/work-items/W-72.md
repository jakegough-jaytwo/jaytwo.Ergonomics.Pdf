# W-72. Inspect existing signatures

## Problem

There is no way to list existing signatures, their signers, times, coverage, or certification level (spec R9).

## Why now

Reset plan C2 item 13. It parses untrusted CMS, so it lands before the G8 campaign.

## Scope and exclusions

- The fields R9 lists, for every signature field, without reading the signed byte range.
- "Which revision it signs" is reported as the end offset of the signed range, the offset at which that revision ends. R10 (W-73) owns how revisions are counted, including linearized files, so this item does not number them.
- CMS `/Contents` (`adbe.pkcs7.detached`, `adbe.pkcs7.sha1`, `ETSI.CAdES.detached`, `ETSI.RFC3161`) is parsed. Other sub-filters (`adbe.x509.rsa_sha1`) report the dictionary entries only.
- Excluded: trust, revocation, and cryptographic validation; the opt-in integrity check of spec section 12 question 4; the `/UR3` usage-rights signature, which is not a signature field.

## Acceptance criteria

Refined at activation on 2026-10-21. `ACCEPTANCE.md` Sealing gains four bullets (inspection; inspection failures; inspection interoperability; the BER writer quirk). The `README.md` writer-quirks list gains entry 2 (BER `/Contents`).

- `PdfDocument.Signatures` lists each terminal signature field once, not once per widget, in field-tree order: full name, whether `/V` resolves to a dictionary, `/SubFilter`, signer certificate (DER), every certificate in the CMS certificate set, digest and signature algorithm identifiers, `/M` and the CMS signing-time attribute, `/Reason`, `/Location`, `/ContactInfo`, `/Name`, `/ByteRange`, the signed revision's end offset, whether a later revision exists, the embedded signature-time-stamp token's `genTime` (the token's own for `ETSI.RFC3161`), and DocMDP `P` when the signature certifies. An unsigned field reports its name and nulls.
- The listing agrees with pyHanko 0.38.0 (with asn1crypto) and `pdfsig` on every signed corpus file (`gpo-bills-118hr815enr`, `cms-40b-pyhanko-approved`, `opm-of306-pyhanko-certified`), on the pyHanko fixtures, and on this library's own RSA 2048, P-256, and P-384 output in both formats, a B-T signature with an OpenSSL timestamp, a document timestamp, a signature followed by a metadata revision, and a signature on a qpdf AES-256 file opened with the user password. pdfsig checks field names, signed state, signer common name, sub-filter, hash algorithm, signed ranges, and whole-file coverage; pyHanko checks everything else.
- Listing the signatures of a sparse signed file larger than 1 GiB reads less than 2 MiB and never the unread middle.
- A CMS that does not parse, has other than one SignerInfo, or has bytes other than zero padding after it throws `PdfParseException`. Field reads stay available.
- BER indefinite lengths in `/Contents` are a tolerated writer quirk (spec section 8): ISO 32000-1 12.8.3.3.1 requires DER, and Acrobat's signature on the GPO bill uses indefinite lengths. Real-world fixture, test, and `README.md` entry.

## Evidence required

Agreement with two verifiers.

## Notes

- 2026-10-20: Created under W-63 from `agents/reference/charter-reset-plan.md` C2.
- 2026-10-21: Activated. Findings: the corpus has three signed signature fields; every other corpus `/ByteRange` belongs to a `/UR3` signature. The GPO bill's CMS is BER (`30 80`) on its outer containers, with DER certificates, and certifies with DocMDP `P` 1. pyHanko counts the IRS W-9's linearized first section as its own revision (three revisions), which R10 counts as one, so this item reports offsets and leaves numbering to W-73.
- 2026-10-21: API: `PdfDocument.Signatures` returns `PdfSignatureInfo` (one per terminal signature field). `CmsSignatureReader` is a separate reader from `DerCodec`, which stays strict DER for timestamp-response input checks. A malformed signature throws `PdfParseException` from `Signatures` instead of returning partial data, matching the strict-reading rule; field reads stay available.
- 2026-10-21: pdfsig 26.08.0 does not parse an `ETSI.RFC3161` document timestamp: it prints `Signature Type: unknown`, an empty common name, and an unknown hash. For a document timestamp it confirms only the field name, the signed ranges, and whole-file coverage; pyHanko confirms the rest.
- 2026-10-21: The `open` fuzz target's read walk now enumerates `Signatures`, which `references/targets.md` already describes ("signature fields"). Proposal for the owner, not made: a dedicated `cms` fuzz target over `CmsSignatureReader.Read`, seeded with the corpus CMS values, because PDF-level mutations rarely reach deep into `/Contents`. Adding it changes `.agents/skills/pdf-fuzz-qualification/references/targets.md`, which needs owner approval. A throwaway run of 300,000 mutations of the GPO, OPM OF-306, and pyHanko CMS values (seed 72, not committed) gave 49,751 parsed and 250,249 `PdfParseException`, and no other exception.

Done 2026-10-21. `PdfDocument.Signatures` ships spec R9; spec R9 is set to Exists in this commit (D-43), with `ACCEPTANCE.md` Sealing (four bullets), `README.md` (supported list, Signing row, writer quirk 2, usage), and acceptance-matrix rows 61 to 64.

- Evidence: Independently validated by pyHanko 0.38.0 with asn1crypto (every reported property) and `pdfsig` 26.08.0 on Windows and 26.01.0 on Linux (field names, signed state, signer common name, sub-filter, hash, signed ranges, whole-file coverage) on all corpus files that open, the pyHanko fixtures, and the library's RSA, P-256, and P-384 output in both formats, B-T plus a document timestamp, a later metadata revision, and an AES-256 user-password file. Internally tested: the sparse file past 1 GiB read under 2 MiB and never the hole; every listed malformed input throws `PdfParseException` with field reads intact.
- Verification: `make quiet-test` (Windows, every external tool set) 3721/3721 on `net10.0`, `net8.0`, `net6.0`, and `net48`. `make quiet-docker-test` 3721/3721 on `net10.0`, `net8.0`, and `net6.0`, fuzz smoke passed. `make fuzz-smoke` passed locally.
- Limitations: nothing is validated (out of charter). Revisions are reported as offsets, not numbered (W-73). `HasLaterRevisions` follows cross-reference sections, so bytes appended after the signed range without a new section are not a later revision, while `pdfsig` would report the document as not wholly signed. Non-CMS sub-filters (`adbe.x509.rsa_sha1`) report the dictionary only. BER is tolerated only as indefinite lengths. When several signature-time-stamp tokens are present, only the first is reported. pdfsig gives no evidence on document timestamps beyond name, ranges, and coverage.
- For the owner: the proposed `cms` fuzz target in the Notes.
