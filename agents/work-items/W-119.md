# W-119. Install the Windows test tools with one script and test the netstandard2.0 build on Linux

## Problem

A full test run on Windows needs qpdf, Poppler (with a `pdfsig` built against NSS), NSS `certutil`, SoftHSM 2, OpenSSL 3, and Python with pinned pyHanko and pypdf. No single installer provides them. On the owner's machine they came from five places by hand: a qpdf zip, a Poppler zip without `pdfsig`, a full MSYS2 install for `pdfsig`, a SoftHSM zip, and Git's OpenSSL. They take about 1.2 GB and are configured through ten `JAYTWO_*` variables kept in agent memory, not in the repository. A fresh clone cannot run the suite natively, and W-80 is about to add MuPDF.

Python is also found two ways. Two call sites use `ExternalTool.Locate("JAYTWO_PYTHON", ...)`; about eighteen start the bare name `python`, so they ignore `JAYTWO_PYTHON` and, on Windows without Python on `PATH`, start the Microsoft Store alias.

Separately, no Linux test runs the `netstandard2.0` build. The net10.0, net8.0, and net6.0 test hosts each load the library build for their own framework, so only the Windows `net48` tests exercise `netstandard2.0` (D-13 note). Jenkins never does.

## Why now

The owner asked for it on 2026-10-22, ahead of W-80, which adds MuPDF as one more tool.

## Scope and exclusions

- `tools/test-tools/install.ps1`: installs pinned, hash-checked copies of the test tools into the git-ignored `.tools/` folder without administrator rights, and writes `.tools/test.runsettings` with every `JAYTWO_*` path. It is idempotent.
  - MSYS2 `ucrt64` packages for Poppler (`pdftotext`, `pdftoppm`, `pdfinfo`, `pdfsig`), NSS `certutil`, qpdf, and OpenSSL, from a pinned MSYS2 base archive.
  - The SoftHSM2-for-Windows 2.5.0 portable zip.
  - A pinned `uv` that creates a Python virtual environment from `tools/test-tools/requirements.txt`.
  - It checks for the .NET runtimes the tests need and reports what is missing. It does not install .NET.
- `tools/test-tools/requirements.txt` holds the Python pins, and the `Dockerfile` installs from it, so Windows and Linux share one list.
- `Directory.Build.props` points `RunSettingsFilePath` at `.tools/test.runsettings` when the file exists and no run settings are set, so `dotnet test` and IDE test runners find the tools with no environment set up.
- `.tools/` is ignored by git and excluded from the Docker build context.
- Every Python start goes through `ExternalTool.Locate("JAYTWO_PYTHON", ...)`.
- `test/jaytwo.Ergonomics.Pdf.NetStandard.Tests` compiles the existing test sources and fixtures on `net8.0` against the library's `netstandard2.0` build, and runs in `make unit-test`, so Jenkins and Docker run it.
- Excluded: MuPDF (W-80 adds it to the script); a Linux or macOS native installer (the `Dockerfile` is the Linux recipe); narrowing the `net48` suite; Jenkins configuration; installing .NET.

## Acceptance criteria

- On a Windows machine with only .NET and the script's output, `dotnet test` on the solution passes on every target, with no `JAYTWO_*` variable set and no test tool on `PATH`.
- Running the script a second time downloads nothing and leaves `.tools/` working.
- A download whose SHA-256 does not match its pin stops the script before it is unpacked.
- `make docker-builder docker-test` passes and runs the `netstandard2.0` tests on `net8.0`.
- No test starts a bare `python`.
- `README.md` (Build) and `AGENTS.md` describe the script and the extra lane; spec §9 lists the lane.

## Evidence required

Internally tested: a full Windows run that uses only `.tools/`, and a Docker run.
