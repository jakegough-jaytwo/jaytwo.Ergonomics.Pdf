# W-35. Request the TSA certificate and parse tokens as strict DER

## Problem

Requests omitted `certReq` under D-14, so tokens carried no TSA certificate. pyHanko accepted the W-15 OpenSSL token only when the test added the TSA certificate to the parsed token out of band (open decision D-O6). Separately, audit finding SA-10 (Medium): `ReadTlv` and the timestamp parser did not require full consumption at the top level or in nested structures, and nonce matching returned before checking trailing values, so a token with trailing or malformed DER could match.

## Why now

The owner closed D-O6 under D-21, and the audit disposition placed SA-10 in this item rather than a separate one.

## Scope and exclusions

Under D-21: each request sets `certReq` TRUE explicitly. The library checks that the response includes the TSA signing certificate its ESS signing-certificate attribute identifies. A regression test has pyHanko validate the token with only the trust anchor configured. The signature placeholder sizing fits the larger token. Under SA-10: the token parser requires strict DER and full consumption. Certificate inclusion, cryptographic validity, and trust stay distinct: inclusion does not establish trust, and the library validates no chain. No public option to omit the certificate.

## Acceptance criteria

- Requests set `certReq` TRUE, and the no-nonce request vector changes accordingly.
- Both providers reject a token that lacks the certificate its single ESS signing-certificate attribute identifies, without extending the file.
- The token parser rejects trailing and malformed DER.
- pyHanko validates the OpenSSL token with only the root, and the out-of-band workaround is removed.

## Evidence required

Independently validated for the OpenSSL document timestamp. Internally tested for the negative ESS and DER matrix.

## Closeout

Accepted under D-21. Independently validated for the OpenSSL document timestamp, and internally tested for the negative ESS and DER matrix. Requests set `certReq` TRUE, and the no-nonce vector is now 59 bytes. Both providers reject a token that lacks the certificate its single ESS signing-certificate attribute identifies, and the file is not extended. The token parser requires strict DER and full consumption, which closes SA-10. pyHanko 0.38.0 validates the OpenSSL 3.2.4 token with only the trust root, and the out-of-band workaround is gone. Inclusion is not trust, and the library validates no chain. `README.md` and the timestamp rows of `ACCEPTANCE.md` describe the behavior. Reports: `agents/reports/2026-10-18-signing-engineer-B-35.md`, `2026-10-18-qa-engineer-B-35.md`, and `2026-10-18-tech-lead-B-34-B-35-review.md`. Completed 2026-10-18.
