# Acceptance criteria

These are the checks the test suite builds from. A change that breaks one of them is a regression.

## Opening

- A stream that cannot seek is rejected with `ArgumentException` before any read.
- `Open` and `OpenAsync` take a readable seekable stream or an `IPdfSource` (spec R13, W-132). With `leaveOpen: false`, disposing the document, or a failed or canceled open, disposes the stream or source; with `leaveOpen: true` neither does. A null source throws `ArgumentNullException`.
- `OpenAsync` awaits `IPdfSource.ReadAsync` for every read and never calls `Read`, including for an RC4 file's `/Encrypt` and for an older cross-reference stream whose `/Length` is a member of an object stream the newer section lists; its reads never overlap. A classic file, that chain, the RC4 file, and a file with 300 KiB of stream data open to the same pages, revisions, and fields synchronously and asynchronously, from a stream and from a source.
- A source that returns one byte, or seven, per read opens synchronously and asynchronously, and a fill saves the same bytes as from a whole stream. A source that returns zero bytes before its claimed length fails the open with `PdfParseException`.
- A canceled token, before the first read or between reads, makes `OpenAsync` throw `OperationCanceledException` and return no document; a borrowed source then opens normally.
- A stream whose length changes under the document fails the next read, edit, and same-stream save with `PdfSourceChangedException`, and nothing is written. The document's own same-stream saves join its snapshot, so its later reads and saves see them. A document opened from an `IPdfSource` has no stream to append to: `SaveIncremental()` with no destination throws `InvalidOperationException`, and a save to an empty destination works.
- `Open` reads the header from the first 1024 bytes and the last `startxref` from the tail. An earlier `startxref` is ignored. A missing `startxref`, a `startxref` past EOF, a cyclic `/Prev`, and an object number that does not match its xref entry throw `PdfParseException`.
- A standard-security revision 2 (40-bit RC4), revision 3 (RC4, 40 to 128 bits), revision 4 (AES-128 or RC4), revision 5 (AES-256), or revision 6 (AES-256) file opens with its user or owner password. Strings and streams come back decrypted, including a string stored inside an encrypted object stream. A cross-reference stream stays plaintext, so an encrypted xref stream is rejected with `PdfParseException`, and `/Encrypt` is resolved from that map as an uncompressed object without scanning the file. Revision 4 follows each crypt filter, so strings and streams can use different ciphers. A revision 5 password is UTF-8 truncated to 127 bytes. A revision 6 password is prepared before that truncation, so a decomposed password matches its composed form. A file whose user password is empty opens when no password is passed, and the permission bits still apply. The wrong password, a missing password on a file that requires one, and a non-standard handler throw `PdfEncryptedException`.
- Tolerated writer quirk (D-57): an encryption dictionary `/P` from 2,147,483,648 through 4,294,967,295 reads as the signed 32-bit value with the same bits. pypdf 6.21.1 writes `/P 4294966244` on revisions 2 to 6; each of those files opens with its user or owner password and reports the permissions qpdf reports as `P = -1052`. Under the user password a fill and a signature succeed and a metadata edit is refused, the original encryption dictionary is kept, and qpdf, pypdf, pdfsig, and pyHanko (except on revision 5, which pyHanko 0.38.0 cannot open) accept the output. Both ends of the unsigned range open on every revision as their signed spelling does. `/P` of 4,294,967,296, of -2,147,483,649, as a real number, or as a string throws `PdfEncryptedException`.
- A revision 4, 5, or 6 file that omits `/StrF` or `/StmF` treats those strings or streams as `Identity`: they are read in the clear, written in the clear, and the saved file reopens.
- An incremental save or signature of an encrypted file keeps the original bytes as a prefix and repeats `/Encrypt` and `/ID`. New strings and streams are encrypted. A new signature dictionary's strings (`/M`, `/Reason`, `/Location`, `/ContactInfo`, `/Name`) are encrypted with the document's cipher under the signature object's number, and only its `/Contents` stays plaintext, inside the gap the `/ByteRange` leaves; this holds for revisions 2 to 6 under the user and the owner password. A signature dictionary already in the file is read the same way: its strings are decrypted, so a FieldMDP lock's field names apply, its `/Contents` is read as it is, and a write that copies it encrypts the strings again and leaves `/Contents` plaintext. pypdf reads the new strings as passed, and pyHanko and `pdfsig` verify the signature, including with a CMS signing time at the Unix epoch, where `pdfsig` reads `/M` (W-97). Reopening with the same password reads the update.
- An update matches the cross-reference format of the section at `startxref` (D-56, W-117). After a cross-reference stream, `SaveIncremental`, `Sign`, and a document timestamp each append a Flate-compressed cross-reference stream: `/Type /XRef`, the trailer entries, and rows for the objects it writes and for itself, under the next free object number. Its `/Prev` names the source's section, a second update chains to the first, each row points at its object, and `Revisions` gains one revision per update. On an AES-256 file the stream is plaintext, keeps `/Encrypt` and `/ID`, and reopens under the user and the owner password. A classic source, and a hybrid source whose table at `startxref` names an `/XRefStm`, still get a classic table. On qpdf's object-stream rewrite of a form, unencrypted and AES-256, `qpdf --check` accepts a fill, a signature over it, and a later fill. pypdf reads the filled value, `pdfsig` verifies the signature, and pyHanko finds it intact, with modification level `FORM_FILLING` after the later fill.
- A user password that only allows form fill can fill a field. Metadata, attachments, and signing throw `PdfEncryptionRestrictedException`. The owner password can modify the document. `/EncryptMetadata false` leaves XMP in the clear. `/EFF /Identity` leaves embedded-file streams in the clear.
- `Permissions` reports the user-access bits for the user password and the owner password. An unencrypted file allows every operation. Revision 2 reports print, modify, copy, and annotate, and high-quality print, form fill, assembly, and accessibility follow those four; the reserved higher bits are ignored. Revision 3 and later report high-quality print only when print is also allowed, form fill when annotate or the fill-in bit is set, assembly from the assemble bit alone, and accessibility when copy or the accessibility bit is set. A revision 2 user password with the fill-in bit set and annotate clear cannot fill a field.
- Headers `%PDF-1.0` through `%PDF-1.7` open. An incremental save keeps that header. A page content stream is not decoded, including when its filter is `LZWDecode`.
- The effective version is the later of the header and a catalog `/Version` name (ISO 32000-1 7.5.2). A write that emits a key ISO 32000-1 defines at a later version sets catalog `/Version` in the same revision: adding an attachment needs 1.7 (`/UF`), removing one or writing XMP 1.4, `Title`, `Subject`, `Keywords`, and `ModDate` 1.1, `Trapped` 1.3, a fill 1.2, and a signature or document timestamp 1.3. `/Version` is itself a PDF 1.4 key, so a raise declares at least 1.4. An effective 1.7 or later, including 2.0, is not changed, and no write declares more than 1.7. `/AF`, `/AFRelationship`, `/ETSI.CAdES.detached`, `/ETSI.RFC3161`, and `/DocTimeStamp` raise nothing. A refused fill, a write the permission bits refuse, and a failed signature leave no raise. Poppler `pdfinfo` reports the raised version, including on a 128-bit RC4 file under the user and the owner password, which keeps `/Encrypt` and `/ID`; it reports the LibreOffice PDF/A-3b corpus file at 1.7 after an attachment add, also one with relationship `Alternative`, dates, compression, and `/PageMode /UseAttachments` (PDF 1.6), and qpdf still lists its embedded files. No PDF/A conformance is claimed.
- Classic xref entries of 20 bytes ending in CRLF, 20 bytes ending in SP LF, 20 bytes ending in SP CR, and 19 bytes ending in LF all open.
- Xref streams using Flate and PNG predictor 12 open, including an object stored in an object stream. A classic xref with `/XRefStm` overrides the stream for objects it lists, including a hybrid section reached through `/Prev` (ISO 32000-1 7.5.8.4: the table, then its `/XRefStm` stream, then `/Prev`).
- A reference to an undefined object, to a free entry, or with a generation other than its xref entry's resolves as null (ISO 32000-1 7.3.10). Generation 0 names an object-stream member. Such a field reference adds no field, a widget `/P` does not set its page, a dangling `/Info` reads as absent, and an edit writes a new dictionary instead of changing the object with that number. A dangling `/AcroForm`, `/DR`, `/Names`, or array is replaced when the library writes one. A stream `/Length` that resolves as null throws `PdfParseException`. An `/Encrypt` reference whose generation does not match throws `PdfParseException`.
- A trailer `/Size` of 2,000,000,000 does not allocate a dense xref. A preamble before `%PDF-` is preserved, and offsets include it.
- `PdfDocument`, `PdfMetadata`, `PdfAttachmentCollection`, `PdfAcroForm`, and `PdfPage` expose no setter and no save, sign, fill, flatten, attachment, or XMP write. `PdfDocument.Edit()` returns the `PdfDocumentEditor` that makes those changes (spec R14, W-131). A document has one open editor at a time; another `Edit()` throws `InvalidOperationException`. Disposing the document or an editor does not write pending changes. Changes left by a disposed editor stay pending, the document's reads show them, and the next editor's save writes them. A disposed editor, and an editor of a disposed document, throw `ObjectDisposedException`. Each editor starts with `AllowBreakingSignatures` false. `leaveOpen: false` disposes the stream.

## Scale

- A 3 GiB sparse file can be opened, its info read, saved on the same stream, and signed, without a read that starts in the unread middle. Bytes read stay under 2 MiB. The metadata appendix is under 8 KiB. The signature `/ByteRange` uses the real long offsets. The signer is not required to read the file.
- A cross-stream save of a file larger than 1 MiB requests reads of at most 1 MiB and reads the source less than twice plus 1 MiB. The source bytes do not change. A non-empty destination throws and is left untouched.
- A 1,000-page file reports page 1000 for a field on the last page, including an inherited media box and `/Rotate 90`. `Pages` reports the same count, rotation, and media box, and an omitted crop box equals that media box. Content streams that live in an unread hole are not read.
- A file whose length is past 9,999,999,999 throws `PdfTooLargeForClassicXrefException` on save and writes nothing.
- G7 workloads on real files (`LargeWorkloadTests`). Each measured window's peak managed-heap growth stays within the D-20 ceilings: 256 MiB for inspect, edit, and sign, and 512 MiB for form extraction and flatten. The fixture budgets, measured in isolated Release processes, are in `agents/evidence/qualification/memory-budgets.md`.
- On a dense 1 GiB file with a metadata revision and a signature, `Signatures` reports the signature, its reason, certificate, and signed revision 3 ending at the file's end, and `Revisions` lists three revisions at the exact end offsets with only the last covered. Each opens the file and reads less than 16 MiB of it, so no signed range is read.
- A 1 GiB CSV attachment added with `Compress = true` is read twice in requests of at most 64 KiB, and the save grows the file by less than half the payload. Extracting it through file streams returns bytes with the payload's SHA-256, the carrier's original bytes stay a prefix, and `qpdf --check` passes.
- On a 500-page qpdf object-stream form, one `Fill` of 500 text fields generates every appearance, and its save keeps the prefix. A signature over that revision covers it, the 500 values read back, the CMS verifies, and `qpdf --check` passes.
- On a 1,000-page qpdf object-stream form with 2,000 fields, `Flatten` and its save keep the prefix and leave no field, and `qpdf --check` passes.
- Twenty open, field and page read, and dispose cycles on the 500-page object-stream form, and twenty field reads on one open document, leave the managed heap retained after a full collection within 1 MiB of the heap after the first cycle.
- A qpdf AES-256 copy of the dense 1 GiB file, with a cross-reference stream and object streams, opens under the user and the owner password and reports its pages, title, and fields while reading less than 16 MiB, so `/Encrypt` is found without a discovery scan.
- Source I/O tripwires (D-49). On the G7 object-stream form windows, source bytes read, read calls, and decoded bytes stay within the thresholds recorded in `agents/evidence/qualification/memory-budgets.md`. The other G7 windows, and flatten and sign on the same form shape at 1,000 and 4,000 pages, are gated the same way. Within one public operation the source cursor serves a seek inside one of its eight most recently filled 64 KiB windows without reading, and a retained window is never served across public operations: not from `Open` to the first operation, and not after an operation that throws.

## Limits

Each limit fails before any destination grows, and a file inside every limit opens as before.

- A literal string past 32 MiB throws `PdfObjectTooLargeException` from its plain, nested-parenthesis, escape, octal, and carriage-return branches, and so does a hex string, including one with an odd final digit. A string of exactly the cap parses.
- A name, number, or keyword longer than 65,536 bytes throws `PdfObjectTooLargeException`, and refusing a 1 MiB token allocates under 2 MiB.
- An array or dictionary with more than 1,048,576 entries throws `PdfObjectTooLargeException`. Repeated dictionary keys count toward the cap, and the last value of a repeated key wins. A dictionary of 150,000 distinct keys opens in under 10 seconds.
- An xref stream `/Index` subsection that overflows the object-number range, overlaps or precedes the subsection before it, lists more entries than the stream decodes to, or ends past `/Size` throws `PdfParseException`. When `/Size` and the decoded entries cover it, a subsection that lists an object number at or above 8,388,608 throws `PdfObjectTooLargeException`. Both refusals happen before any entry is built, and the over-cap refusal allocates under 96 MiB.
- The cross-reference sections of one file list at most one distinct object per 8 bytes of file length, never fewer than 65,536 and never more than 2,097,152. Past that, `Open` throws `PdfObjectTooLargeException`. An 8,319-byte xref stream that lists 8,388,608 objects is refused, and so is the same stream chained three times by `/Prev`. Each allocates about 25 MB, and each finishes under a 256 MiB heap limit. A stream or classic section is merged straight into the one map. Re-listing the same objects in another `/Prev` section adds under 48 bytes per entry, and each new object adds under 128 bytes.
- A classic xref subsection whose start or count is negative, or whose last object number is past 2,147,483,647, throws `PdfParseException` before its rows are read.
- An object stream whose `/N` pairs cannot fit in its `/First` bytes throws `PdfParseException`. Its header is read pair by pair, so header bytes after the `/N` pairs add under 4 MiB of allocation. Parsing 65,536 integer members allocates less than 16 bytes per decoded byte on net10.0. Objects that overlap so that parsing reads more than four times the decoded stream plus 64 KiB throw `PdfObjectTooLargeException`. A header that repeats an object number, and an xref entry whose index names a member with a different object number, throw `PdfParseException` (W-18).
- A page tree nested more than 256 levels below its root throws `PdfParseException` from `Pages` and `PageCount`, and a 200-level tree still opens.
- A signature appendix of exactly 8,388,608 bytes, counted as serialized from the leading line feed through `%%EOF`, is written. One byte more throws `PdfSignException` with "The signature appendix would exceed 8 MiB. Call SaveIncremental before Sign." That holds when the bulk of the appendix is a reused empty signature field whose dictionary holds a long literal string, and when it is an attachment added in the same revision. The source stream and an empty cross-stream destination stay unchanged, the document can still be signed into another field, and the appendix buffer never holds more than 8 MiB. The serializer encodes strings and the reserved `/Contents` gap through a fixed buffer, so serializing a 9 MiB string allocates under 256 KiB as a literal, an escaped literal, a hex string, and an RC4, AES-128, or AES-256 encrypted string, and the largest `/Contents` gap does too.
- A `/Filter` that is not a name or an array of names, a `/DecodeParms` entry that is not a dictionary or null, and a `/DecodeParms` that does not have one entry per filter throw `PdfParseException` when the stream's bytes are required. `/DecodeParms [null null]` with two filters still decodes.
- A stream's `/Filter`, `/DecodeParms`, their array entries, and its `/Predictor`, `/Colors`, `/BitsPerComponent`, `/Columns`, and `/EarlyChange` values may be indirect. They resolve through the document, and the stream decodes, whether it is an attachment read as a stream or an object stream decoded whole. The checks above apply to the resolved values. A reference to an undefined or free object is null, so an undefined `/Filter` is no filter. A chain of 256 references resolves and a chain of 257 throws `PdfParseException`, as does a reference cycle, including an object stream whose `/Filter` is stored inside itself. A cross-reference stream's `/Filter`, `/DecodeParms`, and decoder parameters must be direct (ISO 32000-1 7.5.8.2), so a reference there throws `PdfParseException` from `Open`. A file that qpdf rewrites with object streams, keeping the indirect filters, reads the same attachment bytes as `qpdf --show-attachment`.
- Corrupt Flate data (an invalid zlib header, invalid deflate data, a truncated stream, or a checksum mismatch) throws `PdfParseException` when the stream's bytes are required, whether the stream is decoded whole, as an object stream is, or read as a stream, as an attachment is.
- A stream `/Length` that runs past the end of the file, including one past 2 GiB in a `MemoryStream`, throws `PdfParseException`.

## Pages

- Setting the editor's `Pages[n].Rotation` (spec W6, W-78) writes a direct `/Rotate` on that page, overriding an inherited value. Positive and negative multiples of 90 are normalized to 0, 90, 180, or 270; another value throws `ArgumentOutOfRangeException` and leaves the document clean. Reopening reports the new rotation while the media box, crop box, and field rectangle stay in the same PDF user-space coordinates, and the field reports the new page rotation. The original bytes are a prefix and the update is one revision. pypdf reads the direct value and unchanged coordinates, and Poppler renders the rotated page with the expected orientation.
- DocMDP `P` 1, 2, and 3 block rotation even with `AllowBreakingSignatures`. An approval signature or document timestamp requires that opt-in; FieldMDP does not block rotation. Rotation removes `/UR3` on an unsigned document and leaves `/Perms` unchanged on a signed one. AES-256 and 128-bit RC4 files rotate under the owner password and a user password with modify permission, keep `/Encrypt` and `/ID`, and are read by qpdf and pypdf; a user password without modify permission refuses and leaves a later save byte-identical.

## Metadata

- Title, author, subject, keywords, creator, and producer round-trip. Non-ASCII values are written as UTF-16BE. PDFDoc bytes `0x80` and `0xA0` decode to U+2022 and U+20AC. A custom info key survives an edit and can be read back. The information dictionary can be read and written by key. Creator and producer change only when set. `Trapped` is the name `True`, `False`, or `Unknown`.
- `D:YYYYMMDDHHmmSSZ` and `D:YYYYMMDDHHmmSS±HH'mm'` parse, including when written back through the information-dictionary key. Setting `ModificationDate` keeps a later edit from replacing it. Other info edits refresh `ModDate` in UTC.
- With no XMP, an info edit creates a packet and updates the matching `dc` / `pdf` / `xmp` field. Well-formed XMP is updated in place, including `xmp:ModifyDate`. Malformed XMP does not fail `Open`; `OpenXmp` throws `PdfXmpException`; an info edit leaves the metadata stream bytes unchanged. XML that parses but has no `rdf:RDF` is malformed XMP for an info edit: the edit succeeds and the packet stays byte for byte. `SetXmp` stores the given bytes.

## Attachments

- Added bytes round-trip, including `0x00` and bytes above `0x7F`. `/Params` `/Size` is the byte length. Names are stored in `EmbeddedFiles` and `/AF` and come back sorted. An attachment can be retrieved by name. A missing name throws `PdfAttachmentNotFoundException`. `Remove` drops the name from both.
- An existing FlateDecode embedded file is inflated on `Open`. DCTDecode throws `PdfUnsupportedFilterException` and does not return the compressed bytes. Copying a new attachment requests reads of at most 64 KiB. The content stream must be seekable.
- `LZWDecode` is inflated, including `EarlyChange` 0 and 1, a clear code, and the code that is not in the table yet. `/Filter [/ASCII85Decode /LZWDecode]` decodes ASCII85 first. The abbreviations `LZW`, `AHx`, `A85`, and `Fl` are accepted. A decoded stream above the caller cap throws `PdfObjectTooLargeException`.
- `RunLengthDecode` copies a length of 0–127 and repeats a length of 129–255. A length of 128 ends the stream, and bytes after it are ignored. The abbreviation `RL` is accepted. A truncated run throws `PdfParseException`.
- Tolerated writer quirk: a Flate stream whose `/Length` also counts the CR, LF, or CR LF before `endstream` decodes, in an embedded file and in a cross-reference stream. The embedded file of the IRS 2026 Form 1040-ES (Antenna House PDF Output Library 6.6) decodes to the 15,003 bytes pypdf decodes. Any other bytes after the Adler-32 (a space, a letter, two LFs, LF CR, CR CR, or CR LF LF), and a checksum that does not match, throw `PdfParseException`.
- An `/EmbeddedFiles` name-tree key is a string, not necessarily a text string (ISO 32000-1 7.9.6). A key that is a text string names its attachment. A key that is not, such as UTF-16LE without a byte-order mark, does not fail the listing: the attachment is named by its file specification's `/UF`, then `/F`, and opens by that name. A later attachment edit keeps that key's bytes. The FAA Form 8710-1 attachment (Acrobat PDFMaker 15) is `FAA_Form_8710-1_.pdf.accreport.html`, and its bytes match the file's `/Params /CheckSum`. A `/UF` that is not a valid text string still throws `PdfParseException`.
- `/EmbeddedFiles` keys are written in byte order, a shorter key before a longer one with the same leading bytes, and in one encoding (ISO 32000-1 7.9.6; ISO 32000-2 7.9.6 as corrected by PDF Association issue 214). Keys the tree already holds keep their bytes, and so does the key of a replaced attachment. Any other key, for a new attachment or a file listed only in `/AF`, is UTF-16BE with a byte-order mark when the tree holds no keys or only UTF-16BE ones, and otherwise PDFDocEncoded when every character has a code. Adding `usage-rights.txt` to the IRS 2026 Form 1040-ES, whose `Press Quality(1).joboptions` key is UTF-16BE, writes a UTF-16BE key: `qpdf --check` (12.4.2) passes with no warnings, `qpdf --show-attachment` finds both files, pypdf 6.21.1 reads both, and the added attachment keeps `/UR3` on every Reader-extended corpus form whose transform grants `/EF Create`. Limitation: a name that PDFDocEncoding cannot hold, added to a tree with PDFDocEncoded keys, is UTF-16BE and sorts after every PDFDocEncoded key, as `A日本.txt` sorts after `z.txt`.
- `PdfAttachmentOptions.Relationship` writes `/AFRelationship` with each of `Unspecified` (the default), `Source`, `Data`, `Alternative`, `Supplement`, `EncryptedPayload`, `FormData`, and `Schema`, and `PdfAttachment.Relationship` reads it back. An absent value, or a name outside ISO 32000-2 Table 43, reads as `Unspecified`, and an undefined enum value throws `ArgumentOutOfRangeException` before the content is read. pypdf 6.21.1 reads each written value. No PDF/A-3, Factur-X, or ZUGFeRD conformance is claimed.
- `/Params` holds `/CreationDate` and `/ModDate`, the caller's dates to the second with their UTC offset or else the time of `Add`, and `/CheckSum`, the MD5 of the uncompressed bytes. `PdfAttachment.CreationDate` and `ModificationDate` read the dates, direct or indirect; a date that is not a PDF date throws `PdfParseException` only when that property is read, and the listing and the other attachments still work. pypdf reads the dates and a checksum equal to the MD5 of the content, compressed or not.
- `Compress = true` writes `/Filter /FlateDecode`; it is off by default. A 40 MiB attachment, above the 32 MiB structural cap, is read twice in requests of at most 64 KiB, once by `Add` and once by the save, and the library, `qpdf --show-attachment` (12.4.2), and pypdf return it byte for byte, as they do every byte value and an empty file. `qpdf --check` passes.
- `OpenAttachmentsPanel = true` sets catalog `/PageMode /UseAttachments`, which pypdf reads and `qpdf --check` accepts. Without it an existing `/PageMode` is kept.
- Attachment content that changes length or bytes between `Add` and the save, compressed or not, makes the save throw `InvalidOperationException`, and the opened stream and an empty destination are unchanged.
- On a 40-bit RC4 file under the user password, a 128-bit RC4 file under the owner password, and AES-128 and AES-256 files under each password, a compressed attachment with dates is Flate-encoded and then encrypted, its dates and `/CheckSum` are encrypted strings, `/Encrypt` and `/ID` are kept, and the original is a prefix. pypdf reads the relationship and decrypts the content, the dates, and the checksum.
- After an approval signature or a document timestamp, adding an attachment leaves the earlier signature intact and valid, but some checkers report it as a change the signature does not permit. On a built form, with and without an existing attachment listed in `/AF`, that pyHanko approved or the library time-stamped, the library's attachment add passes `qpdf --check` (12.4.2), and pyHanko 0.38.0 reports the earlier signature intact and valid with modification level `OTHER`. pyHanko reports `OTHER` for any attachment add, whichever tool writes it, because its policy allows no `/Names` change after signing (W-92). A metadata write on the same signed forms is not `OTHER`. Callers should add attachments before signing where they can: attach the invoice XML, then sign.

## AcroForm

- No AcroForm means no fields. Widgets report the dotted full name, partial name, widget index, rectangle in bottom-left user space, 1-based page, rotation, and media box. `GetFields` returns every widget with that full name.
- A parent with kids is not a row. Kids inherit `/FT`, `/V`, `/Ff`, and `/DA`. A widget with no `/P` is found through the page `/Annots`. The value belongs to the field dictionary (ISO 32000-1 12.7.3.1): a kid without `/T` is a widget, even when it carries `/FT` as LibreOffice writes it, so a fill writes the field's `/V` and a `/V` on such a widget is not read; pypdf reads the filled value. Radio widgets that share a name are separate rows. The on-state is whichever `/AP` `/N` key is not `Off`. Button `/Opt` does not remap that public on-state value. A check box is checked when its value is a name other than `Off`. A radio widget is checked when the group value equals its on-state. `Pages` reports number, media box, crop box, and rotation. An omitted crop box is the inherited crop box, or the media box when none is inherited.
- A simple WinAnsi text field, including multiline and quadding, gets a Helvetica appearance and `/NeedAppearances false`. A right-aligned or wrapped Helvetica appearance uses a wider advance for `W` than for `i`. A `/DA` font size of zero is chosen from field height, clamped to 6 through 14 points; for single-line text it is reduced as needed to fit the field width, with 6 points as the floor. A regenerated text or choice appearance paints `/MK /BG` and `/MK /BC` gray, RGB, and CMYK colors behind the text; a solid border uses `/BS /W` and is painted inside the box. A field without `/MK` keeps the appearance stream it had before this color support. `/MaxLen` overflow throws `PdfFieldValueException` and does not dirty the document. Non-WinAnsi text and comb set `/NeedAppearances` and return `NeedsViewer`. A WinAnsi choice value gets a Helvetica appearance of the display text. A check box with no appearance gets a generated `Yes`/`Off` appearance. Checking a field whose widgets advertise different on-state names throws `PdfFieldValueException` and does not dirty the document. A radio mark is drawn with cubic Bezier curves; `arc` is not a PDF content operator. Password, signature, and push-button fields throw `PdfFieldValueException`. A value of the wrong kind throws `PdfFieldValueException` and does not dirty the document: a text field takes text, a check box a Boolean, a radio an on-state name or no value, and a choice field export values or no value. Read-only throws `PdfFieldReadOnlyException`. An unknown name throws `PdfFieldNotFoundException`.
- Choice fields expose `/Opt`, including export/display pairs. A value that is not listed throws `PdfFieldValueException` and does not dirty the document, unless the Edit flag is set. Several values on a single-select field throw. A multi-select value is written as a PDF array. Filling removes a stale `/I` array so it cannot disagree with `/V`. The deliberately small list-box appearance draws the selected display values, not the full option list and selection highlight. The Required flag is reported.
- `Fill(fullName, value)` fills one field and `Fill(values)` fills several, from `PdfFieldValue`s that convert implicitly from a string, a Boolean, and a string array; each returns the appearance disposition, by name for a bulk fill. No value turns every radio widget off (`/V` and each `/AS` become `/Off`) and clears a choice field (`/V` and `/I` are removed and an empty appearance is generated); an empty list also clears a choice field. A null value array is no value, and a null item in a list throws `ArgumentException`.
- A bulk fill is all or nothing (spec W2). Every entry is checked before any field changes: an unknown name, a value of the wrong kind, read-only, password, signature, and push-button fields, `/MaxLen`, an unlisted option, several values on a single-select field, check-box widgets with different on-states, a radio state that no widget has, FieldMDP, DocMDP, and the permission bits. A null or repeated name throws `ArgumentException`. One failure throws, `Export` is unchanged, and a later save writes nothing. A failure while the checked fills apply, such as a `/DR` that does not parse, restores every edit. The fills apply in the order given and write the same revision, byte for byte, as the same single fills in that order. A 500-field bulk fill on a 1,000-page file and its same-stream save do not read the page content. The usage-rights rule applies once to the whole set. AES-256 bulk fills under the user and the owner password are encrypted, keep the original bytes as a prefix, and are read back by `qpdf --check` and pypdf; a user password without the fill bit refuses the whole set. DocMDP `P` 1 refuses a bulk fill and `P` 2 and `P` 3 allow it. A FieldMDP lock on one entry refuses the whole set.
- XFA forms (spec R12 and W4, W-76). A form has XFA when the AcroForm `/XFA` is a stream or an array (ISO 32000-1 Table 218); a null, dangling, or other value is not XFA. `IsXfaOnly` is true when the form has XFA and the catalog `/NeedsRendering` is true or the form has no field widgets; `IsHybridXfa` is true when it has XFA and is not XFA-only. Classification reads no XFA packet. On the corpus, the IRS W-9 and VA 21-4138 are hybrid, Grants.gov SF-424 is XFA-only, and no other file has XFA, as the corpus probe's pypdf reading of `/XFA` agrees. A fill or bulk fill of a hybrid form removes `/XFA` from the AcroForm dictionary in the same revision, before the fills apply, and `IsHybridXfa` is false from then on; the packets stay in the file, unreferenced. A bulk fill writes the same revision, byte for byte, as the same single fills. A refused fill (an unknown name, a value of the wrong kind, read-only, DocMDP `P` 1, FieldMDP, or the permission bits) and an empty bulk fill keep `/XFA` and do not dirty the document. D-48 (W-105): the fill of an unsigned hybrid form also removes `/UR3` from `/Perms` in the same revision, whatever its transform grants; a fill of a form without XFA keeps it under `FillIn`. A fill or non-empty bulk fill of a hybrid form that has a signature (a `P` 2 or `P` 3 certification, an approval signature, or a document timestamp, as section 7.3 counts them) throws `PdfSignatureConflictException` after the DocMDP `P` 1 and FieldMDP checks, and keeps `/XFA` and `/UR3`; a later save writes nothing. A signature field whose `/V` does not resolve, and `/UR3` alone, do not make the form signed. A fill and a `Sign` of an unsigned hybrid form in one session remove `/XFA` and `/UR3` and add the signature. A fill or non-empty bulk fill of an XFA-only form throws `PdfUnsupportedFormException` before any field, permission, or certification check and does not dirty the document; its pages, metadata, attachments, fields, and export still read. On the W-9 and VA 21-4138, the corpus fill and the bulk fill of every fillable field pass `qpdf --check` 12.4.2, and pypdf 6.21.1 reads the values, no `/XFA`, and no `/UR3`; Poppler 26.09.0 draws the filled value in the widget on each. On a Reader-extended hybrid form encrypted with AES-256 or 128-bit RC4, a fill under the user or the owner password removes `/XFA` and `/UR3`, keeps the original bytes as a prefix and `/Encrypt` and `/ID`, writes no AcroForm string in plaintext, and `qpdf --check` and pypdf read it with the password; a user password without the fill bit refuses and keeps `/XFA` and `/UR3`. After a pyHanko approval signature or `P` 2 certification of the W-9, a fill throws `PdfSignatureConflictException` and leaves the file unchanged, and pyHanko 0.38.0 finds the signature intact and valid. Before D-48, W-76 measured that the fill made pyHanko report modification level `OTHER`, not permitted, naming `/XFA`: its difference analysis allows no `/XFA` change in the AcroForm dictionary. Poppler renders and pypdf reads the AcroForm and ignore XFA, so no independent tool here shows the XFA-aware viewer behavior W4 addresses; Acrobat was not run.
- `Export` (spec R6) returns one entry per terminal field, not per widget: text as a string, empty when unset; a check box as a Boolean; a radio as its selected on-state name, or no value when no widget is on; a single-select choice as its export value or no value; and a multi-select choice as a list. Signature fields, push buttons, and password fields are left out, and read-only fields are included. pypdf, walking the field tree itself, reads the same values on built forms and on every corpus form with fields. Filling a copy with another copy's export, less its read-only fields, gives an equal export both ways, filling a blank copy and clearing a filled one, and `qpdf --check` and pypdf accept the result. On every corpus form with fields, one bulk fill that changes every field it can fill passes `qpdf --check` with no warnings, keeps the original bytes as a prefix in one new revision, keeps earlier signatures intact and valid in pyHanko, keeps the `/UR3` state, and pypdf reads the new values.
- Flatten (spec W3, 7.1, and 7.2, W-77). `Flatten()` flattens every field except signature fields; `Flatten(names)` flattens the named fields, an unsigned signature field included. Each flattened widget's normal appearance (`/AP /N`, selected by `/AS`; without `/AS`, a lone state, otherwise `Off`) is painted as a form XObject on each page whose `/Annots` lists it, in `/Annots` order, by the matrix ISO 32000-1 12.5.5 computes from the appearance `/BBox` and `/Matrix` and the normalized `/Rect`; a widget with `/OC` is painted inside `/OC` `BDC`…`EMC`. The page `/Contents` becomes an array of a `q` stream, the existing streams unread, and a stream that starts with `Q` and paints the appearances. The page gets a copy of its effective, possibly inherited, `/Resources` with `/XObject` names it did not use. An appearance stream without `/Subtype` gains `/Subtype /Form`. Hidden and NoView widgets, a widget whose field shows no value and that has no appearance, an `Off` state without an appearance, and a box without area paint nothing. Flattened widgets leave every page's `/Annots`, an indirect array being edited in place; flattened fields leave `/Fields`, their parents' `/Kids`, and `/CO`, and a parent left without kids goes too. When no field remains, `/XFA` and `/NeedAppearances` are removed, and a flatten of a hybrid XFA form removes `/XFA`. The original bytes are a prefix, `qpdf --check` accepts the output, and pypdf finds no flattened widget or field. Poppler renders each flattened page with `pdftoppm -hide-annotations` as it renders the filled page with its widgets, within 48 anti-aliased pixels, and `pdftotext -bbox` finds the same words in the same places: on built forms (generated text, choice, check box, and radio appearances, quadding, clipping, font sizes, a `/Rotate 90` page, a crop-box offset, a rotated `/Matrix`, a `/BBox` off the origin, a scaled appearance, and a media box off the origin) and on eight corpus forms after a fill. Flattening a field on the last of 1,000 pages reads no other page's content.
- A refused flatten changes nothing, and a later save writes nothing: a null, repeated, or unknown name (`ArgumentException`, `PdfFieldNotFoundException`); an XFA-only form, `/NeedAppearances true`, a widget whose field shows a value that has no usable appearance, and a NoRotate widget on a rotated page (`PdfUnsupportedFormException`); DocMDP `P` 1, 2, or 3, with or without the opt-in, and a FieldMDP lock on a flattened field (`PdfCertificationLockedException`); a named signed signature field, and a document with a signature unless `PdfDocumentEditor.AllowBreakingSignatures` is set (`PdfSignatureConflictException`); a user password without the modify or the annotate bit (`PdfEncryptionRestrictedException`). An empty name set changes nothing. A flatten removes `/UR3` on an unsigned document and leaves `/Perms` unchanged on a signed one. AES-256 and 128-bit RC4 files from qpdf flatten under the user and the owner password, the new streams encrypted and `/Encrypt` and `/ID` kept, and qpdf and pypdf read the result. After a pyHanko approval signature, an opted-in flatten keeps the signed field, pyHanko 0.38.0 finds the signature intact and valid with modification level `OTHER`, which its policy does not permit, and pdfsig verifies it and reports that it does not cover the whole file; under a FieldMDP `Include` lock, flattening the locked field refuses and flattening another field keeps the signature intact and valid. On every corpus form with fields, a flatten after a bulk fill of the values the library can draw passes `qpdf --check`, leaves pypdf only signature fields, leaves no `/XFA`, and keeps the earlier signatures intact and valid, the CMS-40B approval among them; the certified GPO bill and OPM OF-306 refuse.
- Fields stored in several object streams return the same values on a second read. A later edit of one field still round-trips, and the fields that were not edited keep their values.
- A DocMDP certification that does not resolve blocks fills and signing, including a `/Perms`, `/Reference` entry, or `/TransformParams` that resolves as null. A FieldMDP `/Reference` entry, `/TransformParams`, `/Fields` array, or `/Fields` entry that resolves as null locks the field. A direct `null` counts as resolving as null (W-18). Field reads still work. DocMDP `P` 2 allows a fill and `Sign`, and blocks a metadata write and a flatten. FieldMDP `All` blocks a fill and still allows a read.
- FieldMDP follows ISO 32000-1 12.8.2.4. `Include` locks only the named fields, and a fill of another field succeeds. `Exclude` locks every field except the named ones, and a fill of a named field succeeds. Names match full field names exactly, and a named field covers its descendants, as pyHanko applies it. An unknown `/Action` locks every field. A locked fill throws `PdfCertificationLockedException`.
- Usage rights follow spec 7.3. A fill keeps the catalog `/Perms /UR3` signature when its UR3 transform parameters list `FillIn` in `/Form`, except a fill that removes `/XFA` from a hybrid form, which `FillIn` does not grant (spec W4, D-48). Adding, replacing, or removing an attachment keeps it when `/EF` lists `Create`, `Modify`, or `Delete`. The relationship, dates, checksum, and compression are part of that grant. `OpenAttachmentsPanel` changes the catalog `/PageMode`, which no UR3 right grants, so an add that changes it removes `/UR3` on an unsigned document; on a signed one `/Perms` stays unchanged. A CMS `Sign` into an existing signature field that has no signature dictionary keeps it when `/Signature` lists `Modify` (ISO 32000-1 Table 255). A metadata write, a flatten, a rotation, a `Sign` that creates a signature field, a document timestamp, and every other case remove `/UR3` from `/Perms` in the same revision, and the write proceeds: a `/Reference` that is absent or empty; a `/UR3`, `/Reference`, `/Reference` entry, `/TransformParams`, `/V`, or listed right that does not resolve; a `/UR3`, `/Reference`, `/Reference` entry, `/TransformParams`, or rights entry of the wrong type; a `/TransformMethod` other than `UR3`, a `/V` other than the name `2.2`, or a second transform; and rights that do not list the write. Each part may be indirect, and an omitted `/V` is `2.2`. A file without `/UR3` gets no `/Perms` change. On a document that already has a signature, no write changes `/Perms`, so `/UR3` stays whatever the transform grants (W-90). A document has a signature when the catalog `/Perms` has `/DocMDP` or a signature field in the AcroForm tree has a `/V` that resolves to a dictionary; the `/UR3` signature does not count, and a `/V` that does not resolve leaves the field unsigned. The check runs before `Sign` adds its own signature dictionary, so the revision that adds the first signature follows the unsigned rules. Refusals, DocMDP, FieldMDP, and the permission bits are unchanged: `P` 2 and `P` 3 still refuse metadata, attachment, and rotation writes. On an unsigned document, a fill and a metadata write in one save remove `/UR3`. A write refused by the permission bits or by validation, including a `Sign` into a field that is not a signature field, is read-only, or is already signed, keeps `/UR3` and does not dirty the document, and a failed `Sign` restores it. The usage-rights signature is not validated. The Reader-extended IRS 1040-ES and CMS-40B forms keep `/UR3` after a fill, the hybrid XFA IRS W-9 and VA 21-4138 lose it because the fill also removes `/XFA` (spec W4, D-48), the XFA-only Grants.gov SF-424 refuses a fill, and all five lose it after a metadata write or a signature into a new field, as pypdf reads the output, except the CMS-40B copy with a pyHanko approval signature, which keeps it after both. Each grants `/Signature Modify`: signing the empty `Signature-1` or `Signature-2` of CMS-40B, the empty `Signature-2` of CMS-40B beside its pyHanko approval signature, and the empty `Digital_Signature[0]` of VA 21-4138 keeps `/UR3`, `qpdf --check` passes, and pyHanko finds the new signature and the earlier one intact and valid. Adding an attachment keeps it on every one of them except the unsigned CMS-40B, which grants no `/EF` rights, and replacing or removing the 1040-ES attachment keeps it. On built Reader-extended forms that pyHanko certified at `P` 2 or `P` 3 or approved, every fill, signature into the existing or a new field, and document timestamp into the existing or a new field keeps `/UR3`, `qpdf --check` passes, and pyHanko 0.38.0's difference analysis reports the earlier signature `FORM_FILLING` or `LTA_UPDATES` with `docmdp_ok`. On the CMS-40B copy with the approval signature, pyHanko never reports a `/Perms` change after a fill, a metadata write, an attachment, a signature, or a document timestamp, and accepts the metadata write and the signature and document timestamp into a new field.

## Sealing

- `/ByteRange` is four 10-digit integers. The gap is `<` plus the reserved hex plus `>`. The digest of the two ranges (SHA-256 unless `DigestAlgorithm` says otherwise) ignores the gap, so changing `/Contents` does not change the digest. The original bytes stay a prefix. A second save's `/Prev` points at the previous xref. A fill and a metadata edit in one save are one revision. Xref lines are 20 bytes and end in CRLF. `SaveIncremental()` and `Sign(options, provider)` append to the opened stream. A read-only opened stream is rejected. `SaveIncremental(Stream)` and `Sign(Stream, ...)` copy into an empty destination and leave the opened stream's bytes unchanged.
- A token larger than `ReservedContentsBytes` throws `PdfSignatureTooLargeException` and does not extend the file. Signing while `/NeedAppearances` is true throws `PdfSignException` and does not extend the file. A provider whose kind differs from `PdfSignatureOptions.Kind` throws `PdfSignException` and does not extend the file. A generated text appearance can be signed in the same revision.
- A `FieldName` that matches an empty signature field reuses that widget and does not add another. `/V` points at the new signature dictionary, the existing rectangle and page stay, and `/SigFlags` still includes signatures-exist and append-only. Signing that field again throws `PdfSignException` and does not grow the file. A text-field name throws `PdfSignException` and does not extend the file, as does any field that is not a signature. A read-only field throws `PdfFieldReadOnlyException`.
- An existing `/ID` is copied. A missing `/ID` is created on sign and not on a metadata-only save. `SigningTime` is written to `/M`, and in the default `AdbePkcs7Detached` format also to the CMS signing-time attribute.
- `CmsDetachedSignatureProvider` verifies with `SignedCms.CheckSignature(verifySignatureOnly: true)`, and the signed `messageDigest` is the SHA-256 of the byte ranges by default. Additional certificates are embedded beside the leaf. An `ITimestampAuthority` passed to the provider receives a request whose imprint is the SHA-256 of the signature value as the SignerInfo stores it, whatever the signature's digest, and the token is the unsigned attribute `1.2.840.113549.1.9.16.2.14`. Certificate inclusion in a timestamp token is checked separately from cryptographic validity and trust; the library performs no trust validation.
- RSA 2048, ECDSA P-256, and ECDSA P-384 keys each sign with `PdfDigestAlgorithm` `Sha256`, `Sha384`, and `Sha512` (spec W15, W16). The signer is called once with the 32-, 48-, or 64-byte digest of the signed attributes and the matching `HashAlgorithmName`. The SignedData and SignerInfo digest algorithm is `sha256`, `sha384`, or `sha512` with NULL parameters. The SignerInfo signature algorithm is `sha256WithRSAEncryption`, `sha384WithRSAEncryption`, or `sha512WithRSAEncryption` with NULL parameters for an RSA leaf, and `ecdsa-with-SHA256`, `-SHA384`, or `-SHA512` with no parameters for an ECDSA leaf. The `messageDigest` is that digest of the byte ranges, the signature value verifies over the signed attributes with the leaf's public key on every target, and `SignedCms.CheckSignature(verifySignatureOnly: true)` accepts it on net8.0 and later. The host's P1363 ECDSA value is stored as a DER SEQUENCE of two minimal INTEGERs: a value whose high bit is set gains a zero byte, leading zeros are dropped, and zero is `02 01 00`.
- `PdfSignatureOptions.Format` `PadesBaselineB` (spec W17, ETSI EN 319 142-1, W-71) writes `/SubFilter /ETSI.CAdES.detached`, keeps the signing time in `/M`, and writes no `/Cert`. Its CMS signs exactly content-type (id-data), message-digest, and signing-certificate-v2, and no signing-time. The signing-certificate-v2 value is one ESSCertIDv2 whose certHash is the SHA-256 of the leaf, with the default hash algorithm omitted, and whose issuerSerial names the leaf's issuer as a directoryName and its serial number. This holds for every key and digest above, from `Sign` and `SignAsync`, the original bytes stay a prefix, and `SignedCms.CheckSignature(verifySignatureOnly: true)` accepts it on net8.0 and later. With an `ITimestampAuthority`, the one unsigned attribute is the signature-time-stamp, which makes the signature PAdES baseline B-T. The default format stays `AdbePkcs7Detached`. A document timestamp with any format but the default, and an undefined format, each throw `PdfSignException`, leave the signer and the authority uncalled, and do not extend the file.
- pyHanko trusts PAdES B-B output for RSA 2048, P-256, and P-384 with SHA-256, SHA-384, and SHA-512 under the test root, and its signing-certificate-v2 check passes. pdfsig reports `Signature Type: ETSI.CAdES.detached`, the digest, the signed ranges, and a valid, trusted signature. The EN 319 142-1 6.3 checklist in `validate_signature.py`, which reads the file and the CMS with pyHanko and asn1crypto, accepts it: `/SubFilter`, `/M`, no `/Cert`, exactly the three signed attributes, content-type id-data, signing-certificate-v2 matching the signer, the signer certificate embedded, and no unsigned attribute. With an OpenSSL RFC 3161 authority, an RSA and a P-256 signature pass as B-T: pyHanko trusts the token under the TSA root, and the checklist finds exactly one signature-time-stamp. On a file that qpdf encrypted with AES-128 under the owner password and with AES-256 under the user password, the PAdES signature passes the same pyHanko, pdfsig, and checklist checks, and pypdf reads the encrypted dictionary strings as passed.
- `PdfDocument.Signatures` (spec R9, W-72) lists each terminal signature field once, not once per widget, in field-tree order, signed or not. A field is signed when its `/V` resolves to a dictionary. A signed field reports `/SubFilter`; the certificate the SignerInfo identifies by issuer and serial number or by subject key identifier, and every certificate in the CMS certificate set; the digest and signature algorithm identifiers; `/M` and the CMS signing-time attribute, which a PAdES signature lacks; `/Name`, `/Reason`, `/Location`, and `/ContactInfo`, decrypted on an encrypted file; `/ByteRange` and the end of its second range; whether the newest cross-reference section starts at or after that end, which a same-stream save makes true at once; the `genTime` of the first signature-time-stamp token, or of the token that is an `ETSI.RFC3161` `/Contents`; and DocMDP `P` when a DocMDP `/Reference` certifies, with the write rules' reading of a `P` that does not resolve. The CMS is read for `adbe.pkcs7.detached`, `adbe.pkcs7.sha1`, `ETSI.CAdES.detached`, and `ETSI.RFC3161`; another sub-filter, such as `adbe.x509.rsa_sha1`, reports the dictionary only. An unsigned field reports its name and nulls. Nothing is validated. Listing a signed sparse file past 1 GiB reads less than 2 MiB and never the unread middle.
- Inspection throws `PdfParseException`, and field reads still work, for a `/ByteRange` that is not four non-negative integers or ends past the largest offset, a `/M` that is not a date, a CMS sub-filter without a `/Contents` string, and a CMS that is not SignedData, has other than one SignerInfo, has bytes other than zero padding after it, is truncated, uses a high tag number or a length of more than four bytes, nests past 64 levels, has an indefinite length on a primitive value or without its end, has a time without a zone, repeats the signing-time attribute, or has more than 65,536 choices in its certificate set. The certificate set is walked choice by choice, so 65,536 non-certificate choices allocate less than 512 KiB on net10.0 (W-18).
- On every corpus file that opens, the pyHanko fixtures, and this library's own output (RSA 2048, P-256, and P-384 with SHA-256, SHA-384, and SHA-512 in both formats; a PAdES B-T signature with an OpenSSL token followed by an OpenSSL document timestamp; a signature followed by a metadata revision; and a signature on a qpdf AES-256 file opened with the user password), the listing agrees with pyHanko 0.38.0 and asn1crypto on the field names, the signed state, and every property above, and with `pdfsig` on the field names, the signed state, the signer common name, the sub-filter, the hash algorithm, the signed ranges, and whole-file coverage. `pdfsig` does not parse an `ETSI.RFC3161` document timestamp, so for one it confirms only the name, the ranges, and the coverage. The corpus's three signed fields are the GPO bill's Acrobat certification (`P` 1), the OPM OF-306 pyHanko certification (`P` 2), and the CMS-40B pyHanko approval.
- Tolerated writer quirk: a signature `/Contents` CMS in BER with indefinite lengths, where ISO 32000-1 12.8.3.3.1 requires DER, reads as its DER form does. Acrobat's certification of the GPO enrolled bill H.R. 815 uses indefinite lengths on the outer CMS containers, and inspection reports the values `pdfsig` and pyHanko report. Other BER forms, such as a constructed string, are refused.
- A leaf whose key is ECDSA P-521, an undefined `PdfDigestAlgorithm`, and a document timestamp with `Sha384` or `Sha512` each throw `PdfSignException` and do not extend the file; the leaf and digest cases leave `SignHashAsync` uncalled, and the document timestamp leaves the authority uncalled. A P-256 or P-384 signer that returns a DER-encoded value, or a P1363 value one byte short or long, throws `PdfSignException` and does not extend the file.
- An exception from `IPdfExternalSigner.SignHashAsync`, the `CertificateDer` getter, the `AdditionalCertificates` getter, or its enumeration surfaces as a fresh generic `CryptographicException` with no provider message, data, or inner exception, and the destination bytes stay unchanged. A null or empty leaf certificate, a leaf that is not one DER-encoded certificate (truncated, wrongly tagged, or followed by trailing bytes), and a null or empty additional certificate or signature value each throw `PdfSignException` and do not extend the file. A leaf failure leaves `SignHashAsync` uncalled.
- `CertificateDer` is read once and `AdditionalCertificates` is read and enumerated once on a successful sign, and a leaf getter that changes after its first read does not affect the signature. A CMS value from `CmsDetachedSignatureProvider` that is larger than `ReservedContentsBytes` throws `PdfSignatureTooLargeException` whose `ActualBytes` is its exact length (W-71): for an oversize chain, signature value, or time-stamp token, reserving exactly that many bytes fits with no padding (signing, or for a token that does not parse, reaching the token parser), and one byte fewer reports the same length again. The signer and the authority run before that comparison, and a time-stamp token is wrapped verbatim to measure the CMS and parsed only once the CMS fits. `DocTimeStampSignatureProvider` refuses a token larger than the reserved size before parsing it, with the token's length. Certificates whose running total exceeds 1,048,576 bytes, the largest reservation, throw `PdfSignException` before the leaf is parsed and leave `SignHashAsync` uncalled, and an endless `AdditionalCertificates` enumeration stops at the first certificate past that total. In each case the source stream and an empty cross-stream destination stay unchanged.
- `Rfc3161TimeStampRequest.Create` of SHA-256("abc") is the 59-byte vector in the tests, has no nonce, and explicitly sets `certReq` TRUE. `CmsDetachedSignatureProvider` and `DocTimeStampSignatureProvider` call the nonce overload with a random nonce and `certReq` TRUE. Both reject a token that does not include the TSA signing certificate identified by its single ESSCertID or ESSCertIDv2 signing-certificate attribute. `HttpTimestampAuthority` POSTs `application/timestamp-query`, accepts status 0, rejects status 2, and returns the time-stamp token. A response body larger than 2,097,152 bytes throws `PdfTimestampException` after reading at most 2,179,072 bytes and does not extend the file. A header- or body-phase timeout throws `TaskCanceledException` with a `TimeoutException` inner exception on every target; unrelated cancellation is not reclassified as a timeout. The caller's cancellation, in the header or the body phase, throws `OperationCanceledException` carrying the caller's token, not a `TaskCanceledException` and not a timeout, and a body that ignores the token is aborted by disposing the response. `DocTimeStampSignatureProvider` sends the request for the signed-range hash and embeds the returned token.
- A time-stamp token whose message imprint does not match the request throws `PdfTimestampException` and does not extend the file.
- A time-stamp token whose digest algorithm does not match the request throws `PdfTimestampException` and does not extend the file.
- A time-stamp token with a missing or mismatched nonce throws `PdfTimestampException` and does not extend the file.
- An exception from a host `ITimestampAuthority`, a `PdfTimestampException` with a secret in its message included, surfaces from `CmsDetachedSignatureProvider` and `DocTimeStampSignatureProvider` as a fresh `PdfTimestampException` with the message `The timestamp authority failed.` and no provider message, data, or inner exception, and does not extend the file. `HttpTimestampAuthority` exceptions pass through as described above.
- `SaveIncrementalAsync` and `SignAsync` write the same bytes as `SaveIncremental` and `Sign`, on the opened stream and into an empty destination: a fill, a fill plus a CMS signature from a signer that completes asynchronously, which the synchronous `Sign` waits for, and a fill plus a signature on a 128-bit RC4 file opened with the user or the owner password. A `SignAsync` that the permission bits refuse throws `PdfEncryptionRestrictedException` and leaves the destination empty.
- A canceled token makes `SaveIncrementalAsync` and `SignAsync` throw `OperationCanceledException` with that token before anything is written; the pending edits remain, and a later save or sign writes the bytes an uncanceled one writes. Cancellation inside the signer, or inside a host timestamp authority called by either provider, throws a fresh `OperationCanceledException` with the caller's token and no inner exception, data, or host message, including when the host throws its own exception after the cancellation; the source and the destination stay unchanged, and the document then signs as if never canceled. Cancellation between the 1 MiB blocks of a cross-stream copy truncates the partly written destination to empty, and the document then saves and signs as if never canceled.
- A cross-stream save or sign whose destination fails part way through the copy, and a same-stream save or sign whose append fails part way, synchronous or asynchronous, rethrows the failure and leaves the destination at its starting length. So does a failure after the append is written, from the destination's `Length` or from disposing a source the document owns when a cross-stream save or sign switches to the destination; the pending edits remain, and a retry writes the bytes an unfailed save or sign writes (W-18).

## Revisions

- `PdfDocument.Revisions` (spec R10) lists logical revisions oldest first. Each `PdfRevision` has its 1-based number, exclusive end offset, and whether a terminal signature field has a `/ByteRange` ending at exactly that offset. `PdfSignatureInfo.SignedRevisionNumber` reports the same number, or null when its byte range does not end at a listed revision. These are structural claims, not signature validation, and no signed byte range is read.
- Revision boundaries come from the cross-reference sections, trailers, and bounded `startxref` / `%%EOF` footers. A classic table and its hybrid `/XRefStm` are one revision. A linearized file's main and first-page cross-reference sections are one logical revision, including the IRS W-9 whose later incremental section makes pyHanko expose three physical sections and the library expose two logical revisions. A missing historical footer makes `Revisions` throw `PdfParseException`; page and signature reads remain available.
- Counts, end offsets, signature coverage, and signed-revision numbers agree with pyHanko 0.38.0 on every corpus file that opens, the pyHanko signed fixture, and the library's signature followed by an unsigned revision. Listing a signed sparse file past 1 GiB reads less than 2 MiB and never the unread middle.

## Workflows

`jaytwo.Ergonomics.Pdf` workflows (spec F1 to F15 and F17, W-142 to W-144). The tests use only the public API of both libraries.

- `From`, `FromFile`, and the operation methods do not read a counting input stream, attachment stream, or `IPdfSource`, and `FromFile` and `AttachFile` do not open their files, which a test holds exclusively. A null `PdfMetadataChanges` throws `ArgumentNullException` when described.
- A borrowed input stream, destination stream, or `IPdfSource` is not disposed after success, an engine failure, or a cancellation partway through the copy. A file opened from a path reopens with exclusive access after each.
- After a terminal call begins, whether it succeeds, fails with `PdfEncryptionRestrictedException`, is canceled, or rejects its own arguments, every sync and async terminal call and operation method throws `InvalidOperationException`. An operation described while a run reads its input throws, and the output does not contain it. Of two concurrent terminal calls, exactly one runs and the other throws `InvalidOperationException`.
- A metadata workflow appends one revision, keeps the input as an exact prefix, and reads back the same title, author, subject, keywords, creator, producer, and revision count as the direct `PdfDocumentEditor` edit. Each of the six properties can be set or removed; an assigned `null` removes, an unassigned property is unchanged, and a change with nothing assigned writes a copy. Several operations apply in order in one revision.
- `Save` to a stream and to a path, and `AppendToSource`, sync and async, from a stream, file, or `IPdfSource` input (`AppendToSource` from a stream or file only), append one revision and report `Modified` and the output length.
- With no operations, a stream or path save writes an exact copy, and `AppendToSource` leaves the stream or file bytes and the file's last-write time unchanged. A non-empty, read-only, or non-seekable destination stream, or the input stream itself, throws `ArgumentException` before the input is read. `AppendToSource` on an `IPdfSource` or a read-only stream throws `InvalidOperationException` before the input is read.
- On a fill-only file that opens with the empty user password, a title change throws `PdfEncryptionRestrictedException` with nothing written: a destination stream stays empty, an appended stream or file is unchanged, a path destination stays absent or keeps its bytes, and no temporary file remains.
- A path save publishes a new file, refuses an existing one without `Overwrite` with `IOException` before the input is read, and replaces it with `Overwrite`. A missing destination directory throws `DirectoryNotFoundException` before the input is read. `FlushToDisk` defaults to true, and with it false the published file is still complete.
- Cancelling an asynchronous path save after its temporary file `.out.pdf.<8 hex digits>.tmp` appears leaves no temporary file and the destination absent or unchanged.
- The input's own path, the same path through `./` or `sub/../`, and the name of an input `FileStream` throw `ArgumentException` before the input opens; so does a case variant on Windows and macOS. With `Overwrite`, a copy of the input with its length and last-write time throws `IOException` saying the destination may be the input, and is unchanged; a same-length copy with another last-write time is replaced. Replacing a hard link to the open input throws `IOException` on Windows and Linux and leaves the input unchanged. On Linux, a symbolic-link destination is replaced as a link and its target is unchanged, and a symbolic link to the input is refused.
- On a 6 MiB input, a metadata workflow reads no more source bytes, and requests no larger read, than the direct engine edit.
- A fill workflow, a fill-and-flatten workflow, a named flatten, and a flatten of every field each append one revision, keep the input as an exact prefix, and write the same bytes as the direct `PdfDocumentEditor` sequence. Fills described after `FlattenForm()` apply before it. Fills and metadata share one revision.
- A field filled more than once sends only its last value: an earlier value the engine cannot draw does not appear in `FieldAppearances`, which holds one `Generated` entry for each field. A value the engine cannot draw reports `NeedsViewer`. `FlattenForm("Name")` with `FlattenForm("City", "Name")` flattens both fields in one engine call, and with `FlattenForm()` flattens every field.
- An unknown field, a read-only field, and a value longer than `/MaxLen` throw `PdfFieldNotFoundException`, `PdfFieldReadOnlyException`, and `PdfFieldValueException` with the destination unwritten. When one of three fills described in separate calls is refused, `AppendToSource` leaves the input unchanged. A fill the engine cannot draw followed by `FlattenForm()` throws `PdfUnsupportedFormException` with nothing written.
- On a document with an approval signature, a flatten throws `PdfSignatureConflictException` with nothing written, and with `AllowBreakingExistingSignatures()` it flattens every field except the signed signature field. On a document certified with DocMDP `P` 2, a flatten with the opt-in throws `PdfCertificationLockedException`.
- A null field name, value set, or name list throws when described. Changing a `FillForm` dictionary or a `FlattenForm` array after describing it does not change the output.
- A workflow that attaches a stream, a `.JSON` file, and a `.bin` file, with explicit dates, appends one revision, keeps the input as an exact prefix, and writes the same bytes as the direct `PdfAttachmentCollectionEditor.Add` calls, reading the stream from the position recorded when described even after the caller moves it. The stream stays open.
- Add then remove, remove then add, and two adds under one name each read back the same attachments, names, and content as the same engine calls in order. Removing a missing name throws `PdfAttachmentNotFoundException` with nothing written. A stream truncated below its recorded position throws `InvalidOperationException`, and a missing attachment file throws `FileNotFoundException`, with nothing written.
- An attachment file reopens with exclusive access after a successful run, after `PdfAttachmentNotFoundException` from a later removal, after `PdfEncryptionRestrictedException` from the engine's add, and after a cancellation partway through the copy.
- `AttachFile` takes the MIME type the caller supplies, or else `text/xml`, `application/json`, `application/pdf`, `text/csv`, or `text/plain` for `.XML`, `.Json`, `.pdf`, `.csv`, and `.TXT`. A `.bin` file or a name without an extension has no MIME type.
- A rotation workflow writes the same bytes as the direct `PdfPageEditor.Rotation` changes: two relative rotations accumulate, an absolute rotation after a relative one sets the value, an angle of -450 normalizes, and `RotateAllPagesBy(90)` turns pages at 0, 90, and 270 to 90, 180, and 0.
- A page number below 1 and an angle that is not a multiple of 90 throw `ArgumentOutOfRangeException` when described. A page number above the page count throws it with nothing written. A null attachment name, stream, or path, an empty path, and a stream that is closed or not seekable throw when described.
- On a document with an approval signature, a rotation throws `PdfSignatureConflictException` with nothing written and succeeds with `AllowBreakingExistingSignatures()`. On a document certified with DocMDP `P` 2, a rotation with the opt-in throws `PdfCertificationLockedException`.

## Foreign files

These fixtures are written by pypdf, qpdf, and pyHanko, then committed. The library does not create them. `qpdf --check` and pyHanko must be available; the tests fail when they are not.

- A qpdf file with an xref stream and an object stream opens, reports the title `Foreign base` and the author `pypdf`, and an incremental title change keeps the original bytes. `qpdf --check` accepts the revision.
- A qpdf revision 6 file with user password `user-secret` rejects a wrong password with `PdfEncryptedException`. A title change plus a CMS signature keeps the original bytes. Reopening with the user password reads the new title. `qpdf --check --password=user-secret` accepts the file, and pyHanko reports the signature intact, trusted, and covering the entire file.
- A qpdf attachment named `note.txt` returns the bytes `foreign-attachment` after an incremental title change. `qpdf --check` accepts the revision.
- A pypdf text field `Name` and check box `Agree`, neither of which has an appearance, generate appearances. The text value `Ada` and the checked state round-trip, and `/NeedAppearances` stays false. `qpdf --check` accepts the revision.
- A pyHanko signature appended to a pypdf file keeps that file as a prefix. A later title change keeps the signed bytes as a prefix. pyHanko reports the original signature intact, trusted, and covering the signed revision.
- An empty signature field named `ExistingSig`, created by pyHanko, is signed in place. The original bytes stay a prefix. pyHanko reports the new signature intact, trusted, and covering the entire file.
- A CMS signature that embeds an intermediate and a root is trusted by pyHanko when only the root is supplied as a trust anchor. The signature stays intact and cryptographically valid.
- `HttpTimestampAuthority` posts the RFC 3161 request to a timestamp server. pyHanko reports the embedded time-stamp token intact, valid, and trusted using only the configured trust root; the TSA signing certificate comes from the token.
- `SignAsync`, with a signer and an OpenSSL timestamp authority that complete asynchronously, writes a signature that `pdfsig` reports valid and trusted over the whole file and pyHanko reports intact and trusted, with its time-stamp token intact and trusted. A `SignAsync` signature on a qpdf AES-256 file opened with the user or the owner password is valid and trusted in `pdfsig` and intact and trusted in pyHanko.
- SoftHSM 2 RSA 2048, P-256, and P-384 keys sign through `IPdfExternalSigner` with SHA-256, SHA-384, and SHA-512: `CKM_RSA_PKCS` over a DigestInfo the host builds, and `CKM_ECDSA` over the raw digest, which returns the P1363 value. `RSA.VerifyHash` and `ECDsa.VerifyHash` accept each value. For each key and digest, pyHanko trusts the chain built from the token leaf plus the embedded intermediate and root and reports that digest and signature mechanism, and `pdfsig` reports the signature valid and trusted from the root, over the whole file, with that signing hash algorithm.
- With in-memory RSA 2048, P-256, and P-384 leaves issued by an RSA root, each key with each of SHA-256, SHA-384, and SHA-512 gives a signature that pyHanko reports intact, valid, and trusted with that digest and mechanism (`sha384_ecdsa`, for example), and that `pdfsig` reports valid and trusted over the whole file with `Signing Hash Algorithm` `SHA-256`, `SHA-384`, or `SHA-512`.
- Byte-range integrity and the modification policy are separate results. Changing one byte inside a signed revision makes pyHanko report the signature not intact. A metadata append after an approval signature stays intact and valid; pyHanko reports the change as `LTA_UPDATES` and allows it. A pyHanko certification with `P` 1 blocks a fill and a metadata write. A certification with `P` 2 allows a fill, blocks metadata, and pyHanko then reports the signature intact with modification level `FORM_FILLING` and an accepting DocMDP result.
- Poppler extracts `Ada` and `Blue` from a pypdf form after those appearances are generated, and its 72 dpi raster of the text, choice, check box, and radio rectangles changes. The unfilled file does not contain `Ada`, and `Blue` is already present.
- Opening a dense file larger than 32 MiB, including one qpdf rewrote with an object stream, and saving a metadata change allocates under 8 MiB. The allocation for a 32 MiB file stays within 3 MiB of the allocation for an 8 MiB file of the same shape. The sampled managed-heap peak stays under 8 MiB.

## iText

iText Core 9.8.0 reads this library's output (W-112). A read for which iText had to rebuild the cross-reference table fails, because that is iText recovering from a file it could not parse.

- On built files with a classic cross-reference table, and on the same files rewritten by qpdf with object streams, which end in a cross-reference stream (W-117):
  - iText reads an Info title, an XMP packet, an attachment's exact bytes, and a page rotation.
  - It reads a single fill and a 10-page bulk fill, and finds no fields after a flatten.
  - `PdfPKCS7.VerifySignatureIntegrityAndAuthenticity` accepts RSA 2048, P-256, and P-384 signatures in `adbe.pkcs7.detached` and PAdES B-B, each covering the whole file, and accepts each as intact after a later metadata revision that it no longer covers.
  - On qpdf AES-256 and 128-bit RC4 files, under the user and the owner password, iText reads a fill and verifies a signature.
- On every corpus file that opens, the 14 that end in a cross-reference stream included, each output ends in the format its source does, and iText reads the output of the corpus metadata revision, text fill, bulk fill, and flatten:
  - the page count;
  - the distinct terminal field names this library reads;
  - the filled value pypdf reads;
  - each earlier signature, as intact.

  A field is terminal when none of its kids has a `/T`, as pypdf's reading counts it. iText counts a kid without `/T` that carries a field key such as `/DA` as a nameless child field (some widgets on the USCIS I-9 and FAA 8710-1), and the comparison does not. iText names a kid whose `/T` is empty with a trailing period (the LibreOffice radio groups), and the comparison drops it.
