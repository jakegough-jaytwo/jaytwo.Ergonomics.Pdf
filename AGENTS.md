# Agent Instructions

## Authority (constraint)

- Read [the charter](docs/charter.md), [supported capabilities](docs/supported.md), and relevant adopted [operation specifications](docs/spec/README.md) before planning behavioral changes.
- Normative precedence: charter > supported > adopted specifications. Draft notes are not binding.
- These documents govern product requirements. Agent instructions and skills govern execution, not product scope.
- If governing documents conflict, stop the affected work and request an owner decision, citing the conflict.
- An adopted specification differing from current implementation represents an implementation gap, not a governance conflict.

## Approval (constraint)

- Changes to `AGENTS.md`, the charter, supported capabilities, or adopted specifications require owner approval.
- Approval may be granted in the assigned task. Otherwise, propose the change without editing the governing document.
- Scope expansion, architectural exceptions, weakened acceptance requirements, and changes to qualification criteria require owner approval.
- Existing code, historical decisions, and work items do not independently authorize requirements or changes.

## Decision-making (constraint)

- Within an approved task and the governing contracts, agents decide routine implementation details, including algorithms, internal structure, error handling, fixtures, and minor interoperability choices. Do not turn each such choice into an owner question.
- For a caller-visible detail that an adopted contract does not settle, choose the simplest predictable behavior that handles common business PDFs reliably. Where mainstream PDF libraries do not converge, treat that as evidence the distinction is unlikely to be critical to intended users, unless correctness, security, data preservation, or an existing public compatibility commitment is at stake.
- Prefer explicit refusal over guessing, silent loss, or destructive changes. Do not add mechanisms for unusual inputs solely for theoretical completeness. A minor open detail should receive one clear rule and proportionate verification, rather than a new decision tree.
- Record the rationale for a consequential choice briefly in the task or draft contract. Research or escalate only when concrete evidence shows a material user benefit, a significant compatibility-complexity trade-off, or a conflict with governing requirements.
- Owner approval remains required for the changes listed under Approval, for adopting an operation contract, for a new full-document rewrite strategy, and for significant trade-offs reserved by the charter. Bring the owner a concrete recommendation with its consequences. Batch related contract choices into one review; do not seek separate approval for routine clauses.
- An unadopted draft does not authorize implementation of a new operation contract. When that is the blocker, finish a coherent draft and request adoption of the contract as a whole.

## References (routing)

- [Behavior](docs/behavior.md) records current implementation; [acceptance](docs/acceptance.md) records enforced test outcomes; [qualification](docs/qualification.md) records release evidence.
- Code and executed tests are evidence of current behavior. Correct stale descriptive documentation without silently changing governing requirements.
- [Work items and decisions](agents/) and [retired records](docs/_retired_/) provide historical evidence, not authority.
- [../pdfdocs](../pdfdocs) is the authoritative local reference for ISO 32000-1 and ISO 32000-2 (with errata), ISO/TS 32001 to 32005, and the PDF 2.0 application notes. Read its [README](../pdfdocs/README.md) and [AGENTS.md](../pdfdocs/AGENTS.md) for how to build and search it (its `text/` tree is generated by `make build`). Consult it, not memory, for normative PDF questions. It does not contain ETSI EN 319 142-1 (PAdES).
- Discover relevant skills in [.agents/skills/](.agents/skills/). For code changes, use the [task workflow](.agents/skills/pdf-task-workflow/SKILL.md) and [verification](.agents/skills/pdf-change-verification/SKILL.md) skills.

## Execution (process)

- Work from an approved task or direct owner instruction. Do not independently expand the backlog.
- Use focused verification by default; expand testing according to risk and documented checkpoints.
- Follow the task protocol, including `make agents-check` and `make task-check` where applicable. Run `make docker-builder docker-test` at required integration checkpoints.
- Missing tools or unexecuted checks must be reported as blocked or not run, never as passing.
- Update behavior, acceptance records, and qualification evidence when verified outcomes change; do not weaken requirements or declare release qualification.
- Report delivered behavior, checks actually executed, known limitations, and decisions requiring owner approval.
