# Competitor-informed expectations: assembly and bulk filling

Research note for owner questions Q-01 and Q-02, checked 2026-10-27. This is documentation/source review, not execution against competitor libraries, an interoperability result, or an adopted contract. The sources are primary vendor/project documentation and Apache source. Checked versions are named where pinned; vendor documentation without a version is not assumed to describe every historical release.

## Extraction and concatenation

| Tool and source | Documented/source behavior | Implication for the question |
| --- | --- | --- |
| [qpdf 12.4.2 page-selection limitations](https://qpdf.readthedocs.io/en/stable/cli.html#limitations) | Document-level structures are not fully merged: forms/outlines and other data come from the primary input; page labels have separate handling. Bookmarks to excluded pages can cease to work. Repeated pages can share underlying data. | A qpdf-experienced caller may expect a useful page transformation with documented feature-specific limitations, rather than a universal preservation-or-refusal guarantee. |
| [PDFBox 3.0.5 merger source](https://raw.githubusercontent.com/apache/pdfbox/3.0.5/pdfbox/src/main/java/org/apache/pdfbox/multipdf/PDFMergerUtility.java) | Merge modes differ in retained elements. Legacy form handling renames colliding fields as independent; join mode combines same-name fields. AcroForm I/O errors are rethrown unless the caller enables ignoring them. | Mode, field identity and error policy matter. Neither unconditional silent omission nor universal refusal describes all cases. |
| [iText 9.5 PdfMerger](https://api.itextpdf.com/iText/java/9.5.0/com/itextpdf/kernel/utils/PdfMerger.html) and [form-copying guidance](https://kb.itextpdf.com/itext/how-to-merge-forms-from-different-files-into-one-p) | The default merger copies tags and outlines when present. Form-copying guidance uses a form-aware page copier and explains that independent same-name fields need renaming. | A caller using the appropriate API can expect more than painted page content, but must select feature-aware copying and identity behavior. |
| [Aspose.PDF .NET concatenation guidance](https://docs.aspose.com/pdf/net/concatenate-pdf-documents/), [CopyOutlines](https://reference.aspose.com/pdf/net/aspose.pdf.facades/pdffileeditor/copyoutlines/) and [CopyLogicalStructure](https://reference.aspose.com/pdf/net/aspose.pdf.facades/pdffileeditor/copylogicalstructure/) | The facade exposes field-uniqueness/suffix handling and options for document structures. | Rich preservation controls are a plausible caller expectation; those options do not establish that every unsupported structure causes refusal. Defaults and corner cases require separate verification before any compatibility claim. |

Inference from these sources: there is no uniform industry contract of either dropping everything unsupported or refusing every loss. Callers can reasonably expect selected pages to remain useful, with documented handling of interactive features and document structures. The exact result depends on tool, API, mode and feature.

Recommendation for owner review: define preservation, intentional omission and refusal **per feature**. Preserve the features the operation promises; never silently omit one of those promised features when copying fails. State intentional new-document omissions in the contract. For other material losses, decide explicitly whether refusal or an opt-in lossy result is appropriate. This is a recommendation, not adoption of every preservation feature, diagnostic, consent mode or exception rule.

## Bulk form population and in-memory atomicity

| Tool and source | What the evidence supports | What it does not establish |
| --- | --- | --- |
| [qpdf command reference](https://qpdf.readthedocs.io/en/stable/cli.html#update-from-json) | Object/JSON updates and appearance-generation facilities. | These are not a directly comparable high-level typed bulk-fill transaction contract. No all-or-nothing form guarantee is inferred. |
| [PDFBox 3.0.5 PDAcroForm.importFDF](https://raw.githubusercontent.com/apache/pdfbox/3.0.5/pdfbox/src/main/java/org/apache/pdfbox/pdmodel/interactive/form/PDAcroForm.java) and [PDField.importFDF](https://raw.githubusercontent.com/apache/pdfbox/3.0.5/pdfbox/src/main/java/org/apache/pdfbox/pdmodel/interactive/form/PDField.java) | The import walks fields and invokes setters individually, skipping missing fields; the shown path has no batch checkpoint/rollback. | Source-based inference: earlier in-memory mutations can survive a later failure. This is not a measured failure case or a statement about file publication. |
| [iText form-filling tutorial](https://kb.itextpdf.com/itext/chapter-4-making-a-pdf-interactive) | The tutorial fills multiple fields through successive individual setters. | The example supplies no multi-field rollback promise. Its sequential model is not proof of every iText API's failure behavior. |
| [Aspose .NET Form.FillFields](https://reference.aspose.com/pdf/net/aspose.pdf.facades/form/fillfields/) and [FillField](https://reference.aspose.com/pdf/net/aspose.pdf.facades/form/fillfield/) | A bulk text-box convenience reports success and saves output; individual setters also expose per-field success. | The cited docs do not promise restoration of all prior in-memory changes on an invalid field/value. A transaction guarantee or its absence needs further evidence; the closed implementation was not tested here. |

An experienced caller should not assume all-or-nothing in-memory bulk mutation is a universal competitor guarantee. Avoiding save/publication after an error is different from restoring an editor's pending changes.

Recommendation for owner review: make a single bulk population call all-or-nothing, because it gives the ergonomic operation a clear failure boundary. Scope rollback to that call, preserving edits that succeeded before it. This is an explicit product choice, consistent with the older recorded bulk policy, rather than a claim that the other tools universally provide it. Exact treatment of missing fields, duplicates, unsupported values, cancellation and appearance generation still needs decisions.
